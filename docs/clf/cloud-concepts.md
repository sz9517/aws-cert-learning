# 雲端概念：為什麼大家都往雲端搬？

> 這是 CLF 的第一個領域（Domain 1，佔 24%）。這一關不要你會動手架設系統，而是要你**懂雲端的好處與價值**。觀念題超多，讀通這篇就贏一半。

<Analogy title="☕ 比喻：自己開咖啡店 vs. 進駐美食街">

- **自建機房** = 自己租店面開咖啡店：裝潢、水電、桌椅全要先砸一大筆錢，生意好壞都得付房租。
- **用雲端** = 進駐美食街的攤位：水電桌椅都現成，**用多少付多少**，人潮暴增隨時擴攤，收掉也不心疼。

</Analogy>

## 為什麼要上雲？先看自建機房有多累

在雲端出現以前，一家公司要上線一個網站或系統，得**自己扛下整條流程**：預估流量、採購伺服器、租機房、裝冷氣、牽網路、請人 24 小時顧機器，還要定期汰換老舊硬體。這條路有幾個很痛的地方：

- **要先猜未來、還得一次砸大錢**：你得在「還沒有半個使用者」時，就賭「未來會有多少人用」，照這個數字買硬體。猜多了，機器整天空轉燒錢；猜少了，一爆紅就當機。
- **錢卡在硬體上動不了**：伺服器一買下去就是一筆大錢，而且買了就只能一直用，想換方向、想收掉都很難回頭。
- **成長很慢**：想多加一台機器，從採購、進貨到安裝設定常常要等好幾週，好點子只能排隊等硬體。
- **心力花錯地方**：你的本業可能是賣東西、做遊戲、開餐廳，結果一半人力在顧機房、修伺服器，沒花在真正賺錢的事情上。

<Analogy title="💡 比喻：自己發電 vs. 接電力公司">

早年工廠要自己蓋發電機才有電用——又貴又要專人維護，電還不一定穩。後來大家都改**接電力公司的電**：插上插座、用多少繳多少，不用管電怎麼來的。**上雲就是這個轉變**：把「運算能力」當成像水電一樣的公共服務來用，而不是自己蓋一座電廠。

</Analogy>

:::note[上雲的意義，一句話]
上雲不只是「把機器搬到別人家」，而是**把要先猜、先砸大錢、還得自己養的苦差事，換成隨開隨用、看帳單付費**——讓你把錢和人力專心放在本業上。
:::

## 雲端的六大優勢（考試最愛考）

這是 AWS 官方整理的「<Term en="Six Advantages of Cloud Computing" desc="AWS 官方歸納採用雲端的六大好處，CLF 幾乎必考。">雲端運算六大優勢</Term>」，請把它當成口訣記起來。

| 優勢 | 白話解釋 |
| --- | --- |
| **把前期資本支出換成變動支出** | 不用一次砸大錢買伺服器（<Term en="Capital Expenditure" desc="資本支出：一次性購置硬體、機房的大筆前期投資。">CapEx</Term>），改成用多少付多少的日常花費（<Term en="Operating Expenditure" desc="營運支出：隨用量產生的經常性費用，像水電帳單。">OpEx</Term>）。 |
| **享受規模經濟帶來的優惠** | AWS 服務全球上百萬客戶，採購量超大，成本被攤平，所以你用的單價比自己買便宜。 |
| **不用再猜容量** | 以前要先猜「會有多少人用」來買機器，猜太多浪費、猜太少當機。雲端要多少開多少，隨時調整。 |
| **提升速度與敏捷** | 需要一台新伺服器？幾分鐘內就開好，不用等採購、進貨、安裝好幾週，想法能更快落地。 |
| **省下維運機房的錢** | 不用再花錢租機房、養冷氣、請人 24 小時顧機器，把錢和心力放在真正賺錢的業務上。 |
| **幾分鐘內布及全球** | 滑鼠點幾下，就能把服務部署到世界各地的機房，讓各國使用者都連得又快又順。 |

:::note[一句話記重點]
雲端把「**先大筆投資、還要自己養機房**」變成「**隨開隨用、看帳單付費**」。這六點只要能認得、分得出來，CLF 的觀念題就穩了。
:::

### 換個角度：每個優勢在解決哪個痛點？

六大優勢其實就是在一個一個回答上面「自建機房有多累」的痛點。對照著記，比死背更好懂：

| 優勢 | 它在解決的痛點 |
| --- | --- |
| **把前期資本支出換成變動支出** | 解決「**還沒賺錢就要先砸大錢買硬體**」——改成用多少付多少，門檻變超低。 |
| **享受規模經濟帶來的優惠** | 解決「**小公司自己買很貴**」——搭 AWS 的大採購量順風車，單價被壓低。 |
| **不用再猜容量** | 解決「**得先賭未來流量，猜錯不是浪費就是當機**」——要多少開多少，隨時增減。 |
| **提升速度與敏捷** | 解決「**加一台機器要等好幾週**」——幾分鐘就開好，好點子馬上能試。 |
| **省下維運機房的錢** | 解決「**人力都卡在顧機房**」——機房、冷氣、硬體汰換交給 AWS，專心做本業。 |
| **幾分鐘內布及全球** | 解決「**想服務海外使用者得在當地蓋機房**」——點幾下就部署到各國，大家連線都快。 |

:::tip[💡 怎麼記得牢]
兩個最常被單獨考的是：**「不用再猜容量」**（對應雲端的彈性）和 **「幾分鐘內布及全球」**（對應全球布局）。看到題目在描述「不必預估用量、隨需調整」或「快速擴展到世界各地」，答案就往這兩個靠。
:::

## 三種雲端部署模型

部署模型講的是「你的系統到底放在哪裡」。CLF 要你分得出三種的差別與適用情境。

| 模型 | 是什麼 | 什麼時候用 |
| --- | --- | --- |
| **雲端（Cloud）** | 整套系統都蓋在雲上，不碰自家機房 | 新創、新專案，想完全享受雲端彈性與免維運 |
| **混合（Hybrid）** | 一部分放雲端、一部分留在自家機房，兩邊打通 | 有法規或舊系統綁在地端，但想逐步把其他部分搬上雲 |
| **地端（On-Premises）** | 全部自己買硬體、放自家機房（也叫私有雲） | 法遵或資安要求極嚴、資料不能出門的情況 |

<Scenario title="情境：一家傳統銀行要上雲">

銀行的核心帳務系統受法規限制，資料得留在自家機房；但新推出的手機 App、行銷活動網站想享受雲端的彈性擴展。這時最合理的選擇就是**混合（Hybrid）**：核心留地端、對外服務上雲，兩邊安全連線。

</Scenario>

### 三種模型怎麼選？用兩個問題判斷

考試常給你一段情境，要你選對模型。其實只要問自己兩個問題：

1. **資料／系統「非留在自家機房不可」嗎？**（法規、資安、或是搬不動的舊系統）
   - 完全沒有這種限制 → 直接選 **雲端（Cloud）**，全部上雲最省事、最彈性。
   - 有一部分非留不可、但其他想上雲 → 選 **混合（Hybrid）**，兩邊打通。
   - 幾乎全部都不能出門 → 留 **地端（On-Premises）**。
2. **你是全新專案、還是已經有一堆舊系統在地端？**
   - 全新專案、沒有包袱 → 偏向 **雲端**。
   - 有舊系統要慢慢搬、不能一次斷掉 → **混合** 常是過渡期的務實答案。

<div className="flow">
  <div className="flow-node">有東西非留地端不可？</div>
  <div className="flow-arrow">→</div>
  <div className="flow-node">完全沒有 → 雲端（Cloud）</div>
  <div className="flow-arrow">→</div>
  <div className="flow-node">只有一部分 → 混合（Hybrid）</div>
  <div className="flow-arrow">→</div>
  <div className="flow-node">幾乎全部 → 地端（On-Premises）</div>
</div>

:::tip[💡 考試小撇步]
題目一出現 **「法規要求資料留在境內／自家」「要串既有地端系統」「逐步移轉」** 這類字眼，答案八成是 **混合（Hybrid）**。若情境是「一間新創、從零開始、想要最大彈性」，那就是純 **雲端（Cloud）**。
:::

## 雲端經濟與 TCO

<Term en="Pay-as-you-go" desc="隨用隨付：用多少算多少，不綁約、不用預先買斷。">隨用隨付</Term>是雲端省錢的核心精神，但考試更愛問一個更完整的概念：**總持有成本**。

<Term en="Total Cost of Ownership" desc="總持有成本：把一項資產從購置到維運、淘汰的所有花費全部加總，而不只看購買價。">TCO（總持有成本）</Term>的意思是：算一套系統要花多少錢，**不能只看買機器的錢**，還要把機房租金、電費、冷氣、網路、維運人力、硬體汰換通通加進去。

<Analogy title="🚗 比喻：養一台車的真實成本">

買車不是付完車價就沒事了——還有油錢、保養、保險、停車位、折舊。這些全加起來才是「養這台車」的真實成本，也就是 TCO 的概念。自建機房的「隱藏費用」往往比想像中高很多。

</Analogy>

:::info[為什麼雲端通常比較省？]
自建要**先付一大筆、還得養著整個機房**，而且常常買太多、用不滿。雲端用多少付多少、不用養機房、硬體汰換是 AWS 的事，把這些隱藏成本都算進 TCO 後，長期算下來通常更划算。
:::

## Well-Architected 六大支柱

AWS 用「<Term en="Well-Architected Framework" desc="AWS 架構完善的框架：評估雲端系統好壞的六個面向。">架構完善的框架</Term>」來衡量一套雲端系統蓋得好不好，共有**六大支柱**。CLF 層級不用深究細節，只要**知道有這六根、認得名字**即可。

| 支柱 | 白話 |
| --- | --- |
| **卓越營運** | 系統能順利運作、持續改善 |
| **安全性** | 保護資料、系統與資產 |
| **可靠性** | 出事能恢復、該在的時候都在 |
| **效能效率** | 用對資源、跑得又快又有效率 |
| **成本最佳化** | 花在刀口上，不浪費錢 |
| **永續性** | 減少環境衝擊、節能減碳 |

:::tip[💡 CLF 常見考點提示]
CLF 這個領域最愛考**概念題**，最常見的是：
- **雲端的好處**（六大優勢，尤其「不用猜容量」「幾分鐘布及全球」）
- **CapEx vs OpEx**（把前期資本支出換成變動支出）
- **彈性與敏捷**（想開就開、用多少付多少）

看到題目在問「採用雲端的好處」「為什麼比自建省」，答案幾乎都往這幾個方向走。
:::

:::warning[🚑 常踩雷／常見誤解]
這三個是初學者（也是考生）最容易栽的坑：

- **以為「上雲一定比較便宜」**：不一定。雲端是**用多少付多少**，用得巧才省；若把機器整天開著不關、資源大開小用、忘了清掉不用的東西，帳單可能比自建還貴。雲端省的是「不用先砸大錢、不用養機房」，不是「不管怎麼用都更便宜」。
- **以為「上雲就不用管安全了」**：大錯。AWS 採**責任共擔模型（Shared Responsibility Model）**——AWS 顧「雲**本身**」的安全（機房、硬體、底層軟體），但「雲**裡面**」的安全（你的資料、密碼、權限設定、誰能存取）**還是你的責任**。設定錯照樣外洩。
- **搞混 CapEx 與 OpEx**：**CapEx（資本支出）**是「**先一次付一大筆**買斷硬體機房」，是自建的典型花法；**OpEx（營運支出）**是「**隨用量產生、像水電帳單一樣月月付**」，是雲端的典型花法。上雲最核心的財務轉變，就是**把 CapEx 換成 OpEx**。別把兩個講反。
:::
