# AI 輔助開發：Amazon Q Developer（C03 新重點）

DVA-C03 和舊版 C02 最大的差別，就是**正式把「AI 輔助開發」寫進考綱**。這不是行銷話術，而是在反映**開發者現在真正的工作方式**：打開 IDE、一邊寫程式一邊有 AI 助理幫你補程式、解釋別人寫的程式、挑出可能的 bug、產生單元測試。AWS 想確認你除了會用 SDK 串服務，也懂得**把 AI 工具納入開發流程、而且會負責任地使用它**。

<Scenario title="真實情境：你平常就在做的事">

你接到需求，要寫一個 <Term en="Lambda">AWS Lambda</Term> 函式去處理 <Term en="Simple Queue Service">SQS</Term> 訊息、寫進 <Term en="DynamoDB">DynamoDB</Term>。以前你得翻文件、複製貼上樣板、自己慢慢湊。現在你在 IDE 裡用自然語言描述需求，AI 就先幫你把骨架、SDK 呼叫、錯誤處理產出來，你再逐行審查、修正、補上測試。寫得更快，但**判斷對不對的責任還是在你身上**——這正是 C03 想考的重點。

</Scenario>

## 為什麼 C03 要納入 AI 輔助開發

<Analogy title="🏢 生活比喻：資淺同事 vs. 萬能保母">

把 AI 助理想成一個**很勤快、讀過海量程式碼的資淺同事**：它出手快、樣板熟、常常給你不錯的起點；但它**不保證每次都對**，也不懂你專案的商業規則與安全要求。你是資深的那個，負責**審查、把關、負責**。考試會站在「資深開發者」的角度問你：AI 給的東西，你怎麼判斷能不能用。

</Analogy>

開發現場早就在用 AI 補程式，AWS 把這件事納入認證，是要你具備三種能力：

- **會用**：知道 AI 工具能幫你做什麼、在哪個環節省時間。
- **會看**：看得懂 AI 產出的程式在做什麼，能解釋、能挑錯。
- **會把關**：知道哪些地方不能盲信（安全、正確性、成本），該人工審查就審查。

## 為什麼開發者要用它？好處與優缺點

先講白話的「好處」——為什麼大家搶著用：

- **快**：樣板、SDK 呼叫、設定格式不用再翻文件慢慢湊，描述一句話就先有骨架，開發速度明顯變快。
- **少樣板**：重複性高、沒什麼思考含量的程式（例如標準的錯誤處理、分頁迴圈、建立 client），交給它產，你省力氣專注在商業邏輯。
- **幫你找 bug / 解釋程式**：貼上出錯的片段或看不懂的舊程式，它能指出可能的問題、用白話解釋，接手別人的程式特別有用。
- **補測試**：單元測試的樣板最煩，讓它先產一批含邊界條件的案例，你再補專案特有情境。

但好處背後都有對應的代價，考試與實務都要能講清楚這組對照：

| 優點（好在哪） | 缺點 / 風險（要當心的） |
| --- | --- |
| 快、省時間，起步門檻低 | 可能產生**看似正確但其實錯**的程式（幻覺、商業規則不符） |
| 幫你補樣板、少打重複碼 | 可能給**過寬的 IAM 權限**（例如 `*`），埋下安全洞 |
| 能解釋程式、加速接手 | 有**安全疑慮**：把金鑰寫死、漏掉輸入驗證、用過時寫法 |
| 自動產測試、提高覆蓋率 | 它**不懂你的專案脈絡**（商業規則、法遵、成本上限） |

:::info[🔑 一句話抓重點]
AI 的價值是**把你從樣板和查文件裡解放出來**，讓你專注在判斷與設計；但「快」不等於「對」，省下的時間有一部分要**還回去做審查**。
:::

## 什麼時候要特別小心 / 不能全交給它

不是每種程式都適合「生成了就用」。**越牽涉金流、權限、安全、個資的地方，越不能全交給 AI**，一定要人工審查、甚至重寫：

- **金流 / 計費邏輯**：扣款、退款、對帳、冪等性（同一筆交易重試不能重複扣款）。這類錯誤直接變成金錢損失，AI 不懂你的對帳規則。
- **權限設定（IAM）**：AI 很愛圖方便給 `Action: "*"` 或 `Resource: "*"`。正式環境必須收斂到**最小權限**，由你判斷到底需要哪幾個動作、哪些資源。
- **安全與機敏資料**：加解密、金鑰與祕密的處理、輸入驗證與注入防護、驗證 / 授權流程——錯了就是資安事故。
- **合規 / 法遵**：個資、稽核紀錄、資料保留政策，這些規則只有你（和你的公司）知道。

:::tip[💡 判斷原則]
問自己一句話：**「這段程式錯了，最糟會怎樣？」** 只是版面跑掉，可以大膽用 AI 起草；但只要可能造成**金錢損失、資料外洩、權限過大**，就把 AI 產出當「草稿」，逐行審查後再上。
:::

## Amazon Q Developer：IDE 裡的 AI 助理

<Vocab title="📌 先認識這些名詞">

- **Amazon Q Developer**：AWS 的 AI 開發助理，整合進 VS Code、JetBrains 等 IDE，也有 CLI 版本。可以對話、產程式、解釋程式、審查、轉換升級。
- **行內建議（inline suggestions）**：你一邊打字，它一邊根據上下文補完後面的程式碼，按 Tab 接受。
- **程式轉換 / 升級（code transformation）**：自動把舊版語言或框架升級到新版（例如 Java 版本升級），省去大量手動改寫。

</Vocab>

**Amazon Q Developer** 是 AWS 提供、整合在 IDE 內的 AI 助理。對 DVA-C03 來說，記住它涵蓋的這幾類能力就夠了：

| 能力 | 它幫你做什麼 | 開發時的用法 |
| --- | --- | --- |
| **程式生成** | 依自然語言或上下文產生程式碼、樣板 | 「幫我寫一個讀 S3 物件的 Lambda」直接給骨架 |
| **解釋既有程式** | 用白話說明一段程式在做什麼 | 接手別人的程式、看不懂時問它 |
| **自動審查** | 掃描找出潛在 bug、品質與安全問題 | 送審前先讓它掃一遍 |
| **程式轉換 / 升級** | 把舊版語言 / 框架自動升級 | 大量 Java 版本升級、相依套件更新 |
| **產生單元測試** | 針對函式產生測試案例 | 補測試覆蓋率，省掉手寫樣板 |

:::tip[💡 考試重點]
考試不會考你「Amazon Q Developer 按鈕在哪」，而是考**概念與定位**：它是 **IDE 內的 AI 開發助理**，能**產碼、解釋、審查、轉換、產測試**；重點永遠是「**AI 加速、但人仍需把關**」。
:::

## 在實際開發流程怎麼用

把一個典型的 Lambda 開發流程走一遍，看 AI 在每一步怎麼幫忙：

<div className="flow">
<div className="flow-node">描述需求</div>
<div className="flow-arrow">→</div>
<div className="flow-node">生成骨架 / 樣板</div>
<div className="flow-arrow">→</div>
<div className="flow-node">人工審查修正</div>
<div className="flow-arrow">→</div>
<div className="flow-node">產生單元測試</div>
<div className="flow-arrow">→</div>
<div className="flow-node">找 bug / 最佳化建議</div>
</div>

1. **寫 Lambda、生成樣板**：用自然語言描述（「處理 SQS 事件、寫入 DynamoDB、含重試」），讓它先給出函式骨架、SDK 呼叫、基本錯誤處理。你省掉翻文件與打樣板的時間。
2. **解釋既有程式**：接手別人寫的程式看不懂時，請它逐段說明，快速進入狀況。
3. **找 bug**：貼上出錯的程式或錯誤訊息，請它分析可能原因、給修正方向。
4. **寫測試**：請它針對函式產生單元測試案例（含邊界條件），你再補上專案特有的情境。
5. **最佳化建議**：請它看一段程式，建議更有效率或更符合最佳實務的寫法（例如用批次寫入取代逐筆呼叫）。

<Scenario title="真實情境：把它當起點，不是終點">

AI 給你的 Lambda 骨架可能**漏了冪等性處理**、**用了過寬的 IAM 權限**、或**沒處理部分批次失敗**。這些正是 DVA 很愛考的開發細節。AI 幫你起步，但這些「對不對」的判斷，考試要的是**你**會做。

</Scenario>

## 負責任使用：人仍需把關

這是 C03 在 AI 這塊**最想強調的觀念**，也是最容易出考題的角度：**AI 是助理，不是最終決策者。**

:::warning[🚑 別盲信 AI 產出]
AI 生成的程式**不保證正確、不保證安全、不保證最佳**。常見風險：

- **正確性**：邏輯看似合理但有隱藏 bug，或不符合你的商業規則。
- **安全性**：可能給出過寬的 IAM 權限、把金鑰寫死在程式裡、忽略輸入驗證。
- **最佳實務**：可能用了過時或低效的寫法。

**每一段 AI 產出都要人工審查**，就像審查資淺同事的 Pull Request 一樣。
:::

:::info[🔑 一句話記住]
**AI 負責加速，人負責負責。** 產出要經過你的理解、審查與測試，才算數。考試問到 AI 時，選項裡**「仍需人工審查 / 驗證」那個方向通常是對的**。
:::

:::warning[🚑 常踩雷]
以下幾個是 AI 輔助開發最容易出事的地方，也是考試愛設計的陷阱選項：

- **盲信產出直接上**：看起來跑得動就當作對的，沒逐行理解、沒測試就送上正式環境。
- **把金鑰 / 祕密貼進提示**：為了讓 AI「看懂」，直接把 access key、密碼、連線字串、正式資料貼進對話框——等於把機敏資料送出去。要用**佔位符**（如 `<YOUR_API_KEY>`）代替。
- **未審查就上正式**：AI 產出只當「草稿」，一定要經過 code review、測試、安全檢查才併入主幹。
- **忽略最小權限**：直接採用 AI 給的 `"*"` 權限圖方便，沒收斂到真正需要的動作與資源。
- **讓它亂動你不懂的程式**：請它「升級 / 重構」一大段你看不懂的程式卻不驗證，出事時連哪裡壞了都不知道。
- **忽略成本影響**：AI 可能給出「能跑但很貴」的寫法（逐筆呼叫、沒分頁、沒快取），正式流量一上帳單爆增。
:::

## 具體例子：請 Q 產一個 Lambda handler，你該檢查什麼

假設你請 Amazon Q Developer：「幫我寫一個處理 SQS 訊息、寫入 DynamoDB 的 Node.js Lambda handler」。它很快給你一段看起來完整的程式。**先別急著用**——照下面這張清單逐點把關：

<div className="flow">
<div className="flow-node">AI 產出骨架</div>
<div className="flow-arrow">→</div>
<div className="flow-node">檢查權限與祕密</div>
<div className="flow-arrow">→</div>
<div className="flow-node">檢查正確性與重試</div>
<div className="flow-arrow">→</div>
<div className="flow-node">補測試 → 送審</div>
</div>

| 檢查點 | 你要問自己 / 要修的地方 |
| --- | --- |
| **IAM 權限** | 它給的執行角色是不是 `dynamodb:*`、`Resource: "*"`？收斂成只有需要的動作（如 `dynamodb:PutItem`）與**那一張表**的 ARN。 |
| **金鑰 / 祕密** | 有沒有把金鑰、連線字串**寫死在程式裡**？改用**環境變數**，機敏值用 Secrets Manager / Parameter Store。 |
| **冪等性** | SQS 可能**重送同一則訊息**。寫入 DynamoDB 有沒有做冪等（條件寫入、用訊息 ID 當鍵）？不然會重複寫、金流情境會重複扣款。 |
| **部分批次失敗** | 一批多則訊息處理到一半失敗，有沒有回報 `batchItemFailures`？否則整批重試、已成功的被重做。 |
| **錯誤處理** | 例外有沒有被吞掉？失敗訊息會不會進 DLQ？還是默默消失。 |
| **輸入驗證** | 直接信任 `event` 內容？惡意或畸形訊息要先驗證再處理。 |
| **成本 / 效率** | 是逐筆 `PutItem` 還是用 `BatchWriteItem`？量大時逐筆呼叫又慢又貴。 |

:::tip[💡 重點不是產碼，是把關]
AI 產的那段骨架幫你省了翻文件的時間，但上面這張清單裡的判斷——**權限收斂、冪等、重試、成本**——正是 DVA-C03 Domain 1 最愛考的開發細節，也是 AI **代替不了你**的部分。把 AI 當成「交草稿的資淺同事」，你負責 review。
:::

## AI 如何貫穿 DVA 四大領域

C03 不是把 AI 塞在某一章，而是讓它**融進四大領域**。用一條線串起來看：

<div className="flow">
<div className="flow-node">Domain 1 產碼</div>
<div className="flow-arrow">→</div>
<div className="flow-node">Domain 3 產測試</div>
<div className="flow-arrow">→</div>
<div className="flow-node">Domain 3 CI/CD 核准</div>
<div className="flow-arrow">→</div>
<div className="flow-node">Domain 4 除錯</div>
<div className="flow-arrow">→</div>
<div className="flow-node">Domain 4 效能建議</div>
</div>

| 領域 | AI 輔助的切入點 |
| --- | --- |
| **1. 用 AWS 服務開發（30%）** | 生成 Lambda / SDK 樣板、解釋既有程式、自動審查 |
| **3. 測試與部署（22%）** | 產生單元 / 回歸測試；CI/CD 流程裡的自動化部署核准 |
| **4. 疑難排解與最佳化（22%）** | 錯誤分析與除錯建議、效能最佳化建議 |

（安全領域 Domain 2 則反過來——AI 產出本身也要通過**安全審查**，權限與金鑰別交給它亂給。）

:::tip[💡 本站做法]
本站把 AI 輔助開發當成**貫穿各領域的加分亮點**單獨講一篇（就是這篇），各領域文章裡則點到為止、不重複展開。你只要記住「AI 幫手在每個環節都能出現、但人要把關」這條主線即可。
:::
