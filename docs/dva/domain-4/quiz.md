# Domain 4 原創練習題（仿官方考題風格）

先自己點選答案，再按「**顯示答案與解析**」。本頁對齊 DVA-C03 官方題型：**情境式題幹、開發者的維運與最佳化視角**，考的是**疑難排解與最佳化**這塊的開發細節與取捨——可觀測性（CloudWatch 自訂指標／告警、Logs Insights 查詢、日誌保留、CloudWatch vs CloudTrail）、分散式追蹤（X-Ray 的 annotation vs metadata、用 service map 找慢段、怎麼啟用追蹤）、錯誤處理（指數退避加抖動、冪等、遇到 429／Throttling 怎麼辦、DLQ、Lambda 部分批次失敗回報、可重試 vs 不可重試）、效能最佳化（Lambda 記憶體調校、連線放 handler 外、冷啟動、快取層怎麼選、DynamoDB 避免 Scan）、除錯（403 權限問題 vs 程式 bug、IAM policy simulator、AI 輔助除錯仍需人工驗證）。選項皆為合理的 AWS 做法（誘答選項不會明顯錯誤），部分題用「**最符合最佳實務／最有效／最可能的原因**」等**限定詞**逼你比較。包含**單選**與**複選（Choose TWO）**兩種題型。題目為**原創**內容（非真實考題）。

  options={[
    '只看 Lambda 的 CloudWatch 指標平均值',

**正解：B**

跨多個服務的請求要靠**分散式追蹤**：啟用 **AWS X-Ray** 後，它會把同一筆請求在各服務的處理串成一條 **trace**，用 **service map** 呈現服務拓撲與各段延遲，點進 trace 的時間軸即可看出是哪一段（某個 Lambda？DynamoDB 查詢？下游 API？）最慢，快速定位瓶頸。A 平均指標看不出單筆請求的分段耗時；C 人工計時零散又難跨服務拼接；D 錯，X-Ray 正是為跨服務追蹤而設計。

**正解：B**

在 X-Ray 裡，**annotation（註解）**是 key-value、會被**索引**，可用在**過濾運算式**裡搜尋、分組 trace（所以「顧客等級」「訂單金額」這種想拿來篩選的維度要放 annotation）；**metadata（中繼資料）**則**不被索引**，只是附加的詳細資訊，能在 trace 裡查看但**不能**用來過濾搜尋。A、C、D 都把兩者的「可否索引搜尋」搞反或搞混。

<Quiz
  qnum={9}
  total={20}
  question="某函式呼叫下游 API 時偶爾收到暫時性錯誤。團隊想重試，但擔心「大家同時失敗、又同時在固定間隔一起重試，造成尖峰把下游壓垮（retry storm）」。最符合最佳實務的重試策略是？"
  options={[
    '固定每 1 秒重試一次，重試到成功為止',
    '指數退避（exponential backoff）加抖動（jitter）：每次重試的等待時間指數成長並加入隨機抖動，分散重試時間點、設定重試上限',
    '完全不重試，一失敗就讓請求直接失敗',
    '立刻無間隔地連續重試上百次',
  ]}
  answer={1}>

**正解：B**

對暫時性錯誤重試的最佳實務是**指數退避（exponential backoff）加抖動（jitter）**：等待時間隨重試次數指數成長（如 1、2、4 秒…）避免密集重試，再加入**隨機抖動**打散各用戶端的重試時間點，避免大家同時重試形成尖峰（retry storm），並設**重試次數上限**。A 固定間隔仍會同步尖峰；C 完全不重試會把本可自癒的暫時性錯誤變成失敗；D 無間隔猛重試會直接把下游打垮。

</Quiz>

    '這是節流（throttling）訊號，屬可重試錯誤：以指數退避加抖動重試；若持續發生則檢討是否要提高容量或平滑流量',

    '忽略 429，當作成功回應繼續往下走',
  ]}
  answer={1}>

**正解：B**

**429 / ThrottlingException** 代表你送太快被**節流（throttling）**，是典型的**可重試（retryable）**錯誤：正確做法是以**指數退避加抖動**稍後重試；若長期頻繁出現，代表實際需求超過目前容量，應從源頭解決——提高佈建容量（或改用隨需容量）、使用快取、或平滑／排隊流量。A 把它當永久 bug 是誤判；C 調更高只會被節流得更兇；D 忽略 429 會造成資料遺失或邏輯錯誤。

</Quiz>

<Quiz
  qnum={11}
  total={20}
  question="某付款函式可能被同一筆請求重試多次（網路重送、SQS at-least-once 等）。為避免「重試導致同一筆款項被扣兩次」，開發上最該落實的是？"
  options={[
    '假設訊息永遠只會送達一次，不做任何防護',
    '設計成冪等（idempotent）：用唯一的冪等鍵（如請求 ID）記錄已處理過的請求，重複收到同一鍵時不重複執行副作用',
    '把重試整個關掉就不會重複',
    '每次都新增一筆扣款，之後再人工對帳刪除重複',
  ]}
  answer={1}>

**正解：B**

分散式系統常是 **at-least-once** 傳遞，同一請求可能被重送，因此付款這類有副作用的操作必須做成**冪等（idempotent）**：用**唯一冪等鍵**（如用戶端產生的請求 ID）在資料庫（如 DynamoDB 條件寫入）記錄「這筆已處理」，重複收到同鍵時直接回既有結果、不重複扣款。A 假設 exactly-once 不切實際；C 關掉重試會犧牲可靠性、且重送來源不只重試；D 事後人工對帳既慢又易錯。

</Quiz>

<Quiz

對非同步叫用或佇列觸發，應設定**死信佇列（DLQ）**或 Lambda 的**失敗目的地（on-failure destination）**：當事件重試耗盡仍失敗，就把它送到 SQS／SNS 保存，團隊便能**檢視失敗內容、分析原因、修復後重放**，而不是靜悄悄遺失。A 讓失敗消失等於丟資料且無從追查；C 無限重試會卡住後續訊息且浪費資源；D 調逾時與這種處理失敗無關，解決不了問題。
