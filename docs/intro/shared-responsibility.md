# 責任共擔模型：哪些 AWS 顧、哪些你顧

在雲端裡，安全不是「AWS 一手包辦」，也不是「全部丟給你」，而是**兩邊各顧一半**。搞不清楚界線在哪，就是資料外洩最常見的起點。這篇用最白話的方式帶你畫清楚這條線。

## 為什麼要先搞懂「誰負責什麼」？

<Analogy title="🏠 生活比喻：租房子，房東和房客各顧各的">

想像你租了一間套房。

- **房東（= AWS）** 負責「**房子本身**」：結構安不安全、水電管線、大門門鎖、社區保全，甚至房子蓋在哪塊地。這些壞了找房東。
- **房客（= 你）** 負責「**房子裡面**」：出門有沒有鎖門窗、貴重物品要不要放保險箱、要不要讓陌生人進來。房東鎖再好的大門，你自己忘了鎖門，東西被偷也不能怪房東。

雲端完全是同一回事：**AWS 把房子蓋得又穩又安全，但「你有沒有鎖好自己的門」是你的事。**

</Analogy>

搞懂這條界線，你才知道出事時該檢查哪一端、平常該把力氣花在哪裡——這也是 AWS 原廠文件開宗明義的 **責任共擔模型（<Term en="Shared Responsibility Model" desc="AWS 與客戶分工負責安全的框架：AWS 顧雲的底層，客戶顧放進雲裡的東西。">Shared Responsibility Model</Term>）**。

## 核心：一句話分清楚兩邊

| 誰 | 負責什麼 | 白話說法 |
| --- | --- | --- |
| **AWS** | 雲的安全（**Security OF the Cloud**） | 蓋房子、顧地基的人 |
| **客戶（你）** | 雲中的安全（**Security IN the Cloud**） | 住在房子裡、要自己鎖門的人 |

**AWS 負責「雲的安全」**——也就是你碰不到、也管不到的底層：

- 全球**實體機房**的門禁、保全、消防、斷電備援
- **硬體**（伺服器、硬碟、網路設備）的維護與汰換
- **底層網路**基礎建設
- **虛擬化層**（讓一台實體機跑出很多台虛擬機的那層軟體）

**客戶負責「雲中的安全」**——也就是你放進去、設定出來的一切：

- 你的**資料**本身（最重要！）
- **IAM 權限設定**：誰能動哪些資源（還記得上一篇的門禁系統嗎？）
- 作業系統（**OS**）的**修補更新**（視服務而定，見下一節）
- **網路設定**：安全群組（<Term en="Security Group" desc="AWS 的虛擬防火牆，控制進出一台伺服器的流量。">Security Group</Term>）、哪些埠對外開放
- **加密**要不要開、金鑰怎麼管

:::note[一句話總結]
**AWS 顧「雲本身」，你顧「放進雲裡的東西」。** 房子很安全，不代表你放在房裡的東西自動安全。
:::

## 關鍵觀念：責任界線會「滑動」

這是整個模型最容易被忽略、卻最常考的一點：**你要顧多少，取決於你用的是哪種服務。** 越「全託管」的服務，AWS 幫你顧得越多，你要操心的越少。

<Scenario title="情境：同樣跑一個網站，用不同服務，你的責任差很多">

- 用 **EC2** 自己架：等於房東只租你一間**毛胚屋**，裝潢、家具、鎖門全你來。
- 用 **S3 / RDS**：等於**附家具的套房**，房東多顧了不少，但你還是要鎖門、收好貴重物品。
- 用 **Lambda**：等於**住飯店**，連床單、保全、消防都有人包辦，你幾乎只要顧好自己的行李（程式和權限）。

</Scenario>

| 服務類型 | 代表服務 | OS 修補誰顧 | 你主要要顧的事 |
| --- | --- | --- | --- |
| 自己租機器（IaaS） | **EC2** | **你自己** | OS 修補、安全群組、裝的軟體、資料、權限 |
| 託管服務（PaaS 傾向） | **S3、RDS** | **AWS**（底層 OS、資料庫引擎） | 資料、存取權限、加密選項、別設成公開 |
| 全託管 / 無伺服器 | **Lambda** 等 | **AWS 全包** | 幾乎只剩**你的程式碼**與**IAM 權限** |

:::tip[💡 考試重點]
看到題目描述某個服務，先問自己：「**OS 修補是誰的事？**」
- **EC2** → 修補、更新是**客戶**責任（最常考的陷阱，很多人誤以為 AWS 會自動幫你修）。
- **RDS、S3、Lambda** → 底層 OS 與執行環境由 **AWS** 負責。

界線會隨服務滑動——這就是 SAA 想考你的核心判斷。
:::

## 最常見的初學者誤解

:::warning[🚑 「上了雲就自動安全」是錯的]
很多人以為把東西丟上 AWS 就萬無一失。真相是：**絕大多數雲端資料外洩，問題出在「客戶這一端」設定不當**，而不是 AWS 被攻破。

最經典的災難就是——**S3 貯體（Bucket）被誤設成「公開」**，結果整批客戶資料被全世界搜得到。AWS 把倉庫蓋得固若金湯，但「你自己把門大開」，AWS 救不了你。這正是「雲中的安全」是**你**的責任的最佳反面教材。
:::

## 和 SAA 的關聯

責任共擔模型是 SAA 考試「**安全領域**」的**底層思維**。考試不會只問定義，而是把它藏在情境題裡：

- 題目問「如何確保 EC2 上的 OS 有最新修補？」——先認清這是**客戶責任**，答案才會對。
- 題目問「如何避免 S3 資料外洩？」——考的是你有沒有把「雲中的安全」做好（關閉公開存取、開加密、用 IAM）。

**先內化這條界線，後面所有安全題你都會有判斷依據，而不是死背答案。**

## 🛠️ 檢查清單：身為客戶，這幾件事一定要自己做

這些全都落在「雲中的安全」，AWS 不會幫你，但每一項都是血淚換來的基本功：

1. **幫 Root 使用者和所有 IAM User 開 <Term en="Multi-Factor Authentication" desc="多因素驗證：登入除了密碼，還要再輸入手機動態驗證碼，被盜密碼也擋得住。">MFA</Term>**——多一道手機驗證，密碼被盜也進不來。
2. **遵守最小權限原則**——只給剛好夠用的權限，別圖方便就給 `AdministratorAccess`。
3. **開啟加密**——資料在儲存時（at rest）和傳輸中（in transit）都加密。
4. **絕對不要把 S3 貯體設成公開**，除非你 100% 確定那是要給全世界看的靜態網站。
5. **別把金鑰（Access Key）寫死在程式或上傳到 GitHub**——用 IAM Role 代替（還記得上一篇嗎？）。
6. **定期檢查誰有哪些權限**，離職員工、沒在用的金鑰要即時關掉。

:::note[心法]
把這張清單想成「搬進新家第一天該做的事」：換鎖、裝監視器、重要文件鎖進保險箱。AWS 把房子交給你了，接下來鎖不鎖門，是你的責任。
:::
