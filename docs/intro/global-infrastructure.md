# 全球基礎建設：Region、可用區與邊緣節點

> 這一篇是後面所有服務的地基。搞懂 AWS 的「機房分佈」，你才會明白為什麼設計要「跨區」、為什麼使用者連得快或慢。

<Analogy title="💡 比喻：連鎖超商的分店、貨架與超商取貨點">

想像一家全國連鎖超商：

- **Region（區域）** = 一個**大都市**（例如「台北」「高雄」）。每個城市自成一格，台北的倉庫和高雄的倉庫互不干擾。
- **Availability Zone（可用區）** = 同一個城市裡的**好幾間分店**，分散在不同街區、各自有獨立的電力和供貨。某一間分店跳電，其他間照常營業。
- **Edge Location（邊緣節點）** = 巷口的**超商取貨點**，數量超多、離你超近，讓你不用大老遠跑去大倉庫，就近拿常用的東西最快。

AWS 的全球基礎建設，就是把這三層「由大到小、由遠到近」組合起來，讓服務又穩又快。

</Analogy>

## 為什麼要有「全球」基礎建設？

<Scenario title="情境：你的客人散在台灣、日本、美國">

假設你的伺服器只放在美國，台灣的使用者每點一下，資料都要繞半個地球來回，網頁就會卡卡的。而且萬一那個美國機房整個停電，全世界的客人同時連不上。

「全球基礎建設」要解決的就是這兩個痛點：

1. **就近（低延遲）**：在離使用者近的地方放伺服器，連線才快。
2. **容錯（高可用）**：雞蛋不要放同一個籃子，一處壞掉其他地方頂得住。

</Scenario>

### 一句話：為什麼要分這麼多層？

說穿了，這三層就是在同時解決兩件事——**「夠近夠快」**跟**「死不了」**：

- **夠近夠快**：使用者在哪，就在附近放東西。全球有很多 **Region**，你把主機開在離客人最近的那個；**邊緣節點**又比 Region 更多更近，把常看的內容（圖片、影片）直接擺到使用者巷口。距離越短，連線越快。
- **死不了**：同一個 Region 裡又切出多個互相獨立的 **AZ（機房）**，電力、冷卻、網路各自獨立。這樣就算一整座機房掛了，服務照樣在別的 AZ 活著。

換句話說：**層數多，不是為了複雜，而是為了「又快又不會倒」**。你只要記得「一層負責快、一層負責不倒」，整張圖就通了。

:::note[💬 閱讀小提示]
看到帶<Term desc="像這樣！滑鼠移到有虛線的名詞上（手機點一下）就會跳出白話解釋。">虛線底線的名詞</Term>，把滑鼠移上去就會跳出白話解釋。

本篇出現的三個層級，大小關係是：**Region ＞ 可用區（AZ）＞ 邊緣節點**。
:::

## Region（區域）：地理上的大區塊

<Term en="Region" desc="AWS 在世界各地的一個地理區塊，例如東京、新加坡、維吉尼亞北部；每個 Region 彼此獨立運作。">Region（區域）</Term> 是 AWS 在世界某個地理位置劃出的一大塊基礎建設，例如「亞太（東京）」「亞太（新加坡）」「美國東部（維吉尼亞北部）」。

**各個 Region 彼此完全獨立**：你在東京開的資源，預設不會自動出現在新加坡；資料也不會自己跨 Region 搬動（除非你明確設定）。這種「獨立」正是法規與容錯的基礎。

### 怎麼挑 Region？四個考量

| 考量點 | 白話說明 | 例子 |
| --- | --- | --- |
| **延遲（就近）** | 選離你使用者最近的 Region，連線最快 | 客人在台灣 → 選東京或新加坡 |
| **法規／資料落地** | 有些法律規定資料必須留在特定國境內 | 歐盟資料常要求放在歐洲的 Region |
| **價格** | 同一個服務，不同 Region 的收費不一樣 | 某些 Region 單價較低 |
| **服務可用性** | 新服務不是每個 Region 一開始都有 | 想用某項新功能，要先確認該 Region 有沒有 |

白話記法：**延遲**管「快不快」、**法規**管「能不能放這裡」、**價格**管「貴不貴」、**服務可用性**管「這裡有沒有你要用的服務」。一般新手最常只看「延遲」就選了，但真正會卡住你的，往往是**法規（資料不准出境）**和**服務可用性（想用的新服務該 Region 還沒上）**——所以四個都要順手確認一下。

:::tip[💡 給初學者的實用建議]
剛開始練習時，固定用**一個離你近的 Region**（例如東京 `ap-northeast-1` 或新加坡 `ap-southeast-1`）就好。最常見的新手帳單意外，就是**在 A Region 開了資源、卻跑去 B Region 找，以為沒開成、結果兩邊都在計費**。
:::

## Availability Zone（可用區，AZ）：Region 裡的多個獨立機房

一個 Region 裡面，其實是由好幾個 <Term en="Availability Zone" desc="一個 Region 內彼此獨立的資料中心（機房）群；各自有獨立電力、冷卻與網路，用來做高可用。">可用區（AZ）</Term> 組成的。每個 AZ 是一到多座**彼此獨立的資料中心（機房）**，各自有獨立的電力、冷卻和網路，而且彼此之間用高速專線相連，距離夠近（延遲低）又夠遠（不會同時遭殃）。

<Analogy title="🏢 為什麼要「跨 AZ」？">

把你的網站只開在**一個** AZ，就像把公司所有員工塞進**同一棟大樓**——這棟樓一跳電、一失火，公司就全停擺。

把服務**同時部署到兩個以上的 AZ**（這叫 **Multi-AZ，多可用區**），等於在不同棟大樓各留一組人馬。一棟出事，另一棟立刻接手，客人幾乎無感。

</Analogy>

:::info[這就是 SAA 的核心精神]
SAA 考試一再強調「**高可用（High Availability）**」。只要題目在意「某個機房掛掉服務還要能活」，標準答案方向幾乎都是：**把資源跨多個 AZ 部署**。像資料庫的「Multi-AZ 備援」、負載平衡器把流量分散到多個 AZ 的執行個體，都是建立在這個基礎上。
:::

## Edge Location（邊緣節點）：離使用者最近的加速點

<Term en="Edge Location" desc="AWS 散佈在全球各城市、數量遠多於 Region 的小型節點，主要給 CloudFront 等服務做內容快取與就近加速。">邊緣節點（Edge Location）</Term> 是 AWS 散佈在全球各大城市的**小型據點**，數量遠比 Region 多。它主要給 <Term en="Content Delivery Network" desc="內容傳遞網路：把網站的圖片、影片等內容快取到離使用者最近的節點，讓載入更快。">CDN</Term> 服務 CloudFront 使用，把網站的圖片、影片、靜態檔案**快取（cache）在離使用者最近的地方**。

<Scenario title="情境：台灣使用者看你放在美國的影片">

沒有邊緣節點：每次播放都要從美國機房拉資料，又慢又貴。

有了邊緣節點：影片第一次被看過後，就**快取在台灣的邊緣節點**。之後台灣的其他使用者再看，直接從巷口（台灣節點）拿，秒開，也省了跨國流量費。

</Scenario>

### 三者差在哪？一張表看懂

| 層級 | 數量 | 主要用途 | 一句話 |
| --- | --- | --- | --- |
| **Region** | 少（大區塊） | 部署你的主要資源 | 你的「總部所在城市」 |
| **可用區（AZ）** | 一個 Region 內數個 | 高可用、跨機房容錯 | 城市裡「不同街區的分店」 |
| **邊緣節點** | 非常多 | CDN 快取、就近加速 | 巷口的「超商取貨點」 |

:::warning[🚑 常見觀念混淆]
**邊緣節點不是拿來跑你的伺服器或資料庫的**。你的 EC2 執行個體、資料庫是開在 **Region 的 AZ 裡**；邊緣節點只做「快取與加速」這類就近任務。把兩者搞混是新手常見的誤解。
:::

## 🛠️ 動手做：切換 Region、查看目前有哪些 AZ

不用花錢，純看介面就能體會這三層結構：

1. 登入 AWS 主控台，看**右上角**的區域（Region）選單（例如顯示「東京」或「N. Virginia」）。
2. 點開它，試著**切換到另一個 Region**（例如從東京切到新加坡）。你會發現：原本在東京看到的執行個體、貯體，在新加坡這邊「不見了」——因為 **Region 彼此獨立**，這正是前面講的重點。
3. 切回你要用的 Region。到搜尋列輸入 `EC2` 進入服務，開始建立執行個體時，在網路設定裡的「可用區」下拉選單，就能看到**目前這個 Region 有哪些 AZ**（例如 `ap-northeast-1a`、`1c`、`1d`）。

也可以用 CLI 直接列出某個 Region 的 AZ（不會產生費用）：

```bash
# 列出東京 Region 目前可用的 AZ
$ aws ec2 describe-availability-zones --region ap-northeast-1 \
    --query "AvailabilityZones[].ZoneName"
[
    "ap-northeast-1a",
    "ap-northeast-1c",
    "ap-northeast-1d"
]
```

看到了嗎？光東京一個 Region，就有好幾個 AZ 可以讓你「跨機房」部署。

:::warning[🚑 常踩雷／常見誤解]
- **開錯 Region，找不到資源**：在東京開了執行個體，卻把主控台切到新加坡去找，當然「看不到」。Region 彼此獨立，記得先確認右上角選的是哪個 Region。更糟的是兩邊都不小心開了東西——**兩邊都在計費**。
- **開錯 Region，連線變慢**：客人在台灣，你卻把主機開在美國 Region，每次連線都要繞地球——**不是程式慢，是 Region 選太遠**。先把資源搬到就近的 Region（東京／新加坡）通常立刻改善。
- **開錯 Region，可能觸法規**：某些資料（如歐盟個資）法律規定不能離開特定國境。隨手選了別洲的 Region，可能就**違反資料落地（data residency）規定**。涉及個資／合規時，Region 要先查清楚。
- **以為每個服務每個 Region 都有**：新服務、新功能常常**先在少數 Region 上線**。照教學操作卻找不到某個服務，很可能不是你做錯，而是**你所在的 Region 還沒有**——換個 Region 或查官方的服務地區對照表。
- **把 AZ 當成 Region**：`ap-northeast-1` 是 Region，`ap-northeast-1a` 才是它底下的一個 AZ。「跨 AZ」是在**同一個 Region 內**分散到不同機房（求高可用）；「跨 Region」是跨到**另一個地理區塊**（求異地備援或就近）。兩者不是同一件事，別混用。
:::

## 這跟 SAA 考試的關係

全球基礎建設是**整個 SAA 架構思維的地基**：

- 講「高可用」→ 幾乎都回到**跨多個 AZ（Multi-AZ）部署**。
- 講「低延遲、全球使用者體驗」→ 回到**選對 Region** 加上 **邊緣節點（CloudFront）**。
- 講「法規、資料落地」→ 回到 **Region 的選擇與獨立性**。

先把這三個詞和它們的大小關係刻進腦子裡，後面讀 EC2、負載平衡、資料庫備援、CloudFront 時，就會發現全部都在這張地圖上。
