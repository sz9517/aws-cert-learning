# Well-Architected：AWS 幫你評分「這個架構蓋得好不好」

> 這篇幫你把後面所有 SAA 內容串成一張地圖。讀完你會知道「好架構」到底在追求什麼，以及每個考試領域在這張地圖的哪個位置。

## 為什麼需要一套「架構準則」？

<Analogy title="🏠 比喻：蓋房子要有建築規範，不是想到哪蓋到哪">

你要蓋一棟房子，如果沒有任何規範，可能牆蓋歪了、沒做防震、電線亂拉、下雨就漏水，住進去才發現問題一堆。

所以政府有一套**建築規範**：地基要多深、鋼筋要多粗、逃生動線怎麼留。照著蓋，房子才會**安全、耐用、住得舒服、又不會花冤枉錢**。

蓋雲端系統也一樣。你可以東拼西湊把服務接起來讓它「能動」，但能不能**撐住流量、擋得住駭客、帳單不爆、壞了能救回來**？這就需要一套準則來檢查——這就是 **Well-Architected Framework**。

</Analogy>

## Well-Architected 是什麼？

**Well-Architected Framework（良好架構框架）** 是 AWS 累積大量實戰經驗後，歸納出來的一套「**什麼才算好架構**」的評估框架。

它把「好架構」拆成**六個面向（稱為「支柱」，Pillar）**，每個面向都有一串設計原則和檢查問題，讓你能有系統地檢視自己的系統，而不是憑感覺。

:::note[💬 一句話定位]
Well-Architected 不是一個你要去「開通」的服務，而是一份**思考清單**。考試會問你「在某某情境下，哪個做法比較符合良好架構原則」——所以懂這六根支柱在乎什麼，答題就有方向。
:::

## 六大支柱逐一看懂

| 支柱 | 白話：它在乎什麼 | 一句實例 |
| --- | --- | --- |
| **卓越營運**<br/>(Operational Excellence) | 系統**好不好管、好不好改、出事找不找得到原因** | 用程式自動部署、記錄 Log，半夜出錯會自動發警報通知值班人員 |
| **安全性**<br/>(Security) | **誰能碰資料、資料有沒有加密、被攻擊擋不擋得住** | 只給員工最小必要權限（IAM），資料庫密碼存進保險箱而非寫死在程式 |
| **可靠性**<br/>(Reliability) | **壞掉能不能自己復原、流量變大撐不撐得住** | 一台伺服器掛掉，流量自動導到另一台，使用者完全無感 |
| **效能效率**<br/>(Performance Efficiency) | **有沒有用對工具、跑得夠不夠快、資源有沒有浪費** | 把圖片放到全球 CDN 快取，讓各地使用者載入都很快 |
| **成本最佳化**<br/>(Cost Optimization) | **有沒有花冤枉錢、關掉沒在用的資源** | 離峰時段自動把閒置伺服器關掉，只在需要時才開 |
| **永續性**<br/>(Sustainability) | **用最少的運算資源達成目標，減少對環境的衝擊** | 選用更節能的執行個體、把工作排到資源使用率高的時段，降低碳足跡 |

<Scenario title="情境：把六大支柱套到同一個購物網站">

同一個購物網站，六根支柱各問你一個問題：
**卓越營運**問「上新功能要不要手動搬檔案？」、**安全性**問「刷卡資料有沒有加密？」、**可靠性**問「雙 11 當機怎麼辦？」、**效能效率**問「首頁載入要幾秒？」、**成本最佳化**問「半夜沒人逛，伺服器還開著燒錢嗎？」、**永續性**問「同樣的流量，能不能用更省電的方式扛？」

你會發現：一個真正的好架構，是**同時**對這六個問題都有交代。

</Scenario>

:::tip[💡 考試重點：注意「取捨（Trade-off）」]
六大支柱常會**互相拉扯**：想更可靠（多開幾台備援）往往就更花錢（成本變高）。SAA 題目最愛考這種取捨——例如題目強調「**成本最低**」，那答案就要往成本靠；強調「**不能有任何停機**」，就往可靠性靠。先看懂題目在乎哪根支柱，是答對的關鍵。
:::

## 關鍵對照：六大支柱 ↔ SAA 四大考試領域

這段對初學者超重要——它能幫你把整個 SAA 考綱一眼看懂定位：

| Well-Architected 支柱 | 大致對應的 SAA 考試領域 |
| --- | --- |
| 安全性 (Security) | **Domain 1：設計安全的架構** |
| 可靠性 (Reliability)、彈性 | **Domain 2：設計具彈性的架構** |
| 效能效率 (Performance Efficiency) | **Domain 3：設計高效能的架構** |
| 成本最佳化 (Cost Optimization) | **Domain 4：設計符合成本效益的架構** |
| 卓越營運 (Operational Excellence)、永續性 (Sustainability) | **橫向貫穿**：沒有單一領域，但觀念散落在各題中 |

:::info[📌 所以你該怎麼讀這個站？]
後面的 SAA 四大領域，其實就是帶你把「安全、可靠、效能、成本」這四根最常考的支柱逐一練熟。現在先把這張對照表記在腦中，接下來每讀一篇，你都知道「這在補哪根支柱」。
:::

## 順手認識：AWS Well-Architected Tool

**AWS Well-Architected Tool** 是 AWS 主控台裡一個**免費**的工具，可以幫你為自己的架構做一次「體檢」。

用法很單純：你在裡面建立一個 workload（你的某個系統），工具會**一根支柱一根支柱地問你一連串問題**（例如「你有沒有為關鍵元件做備援？」）。你照實回答後，它會列出**高風險項目**與**改善建議**，等於有一位資深架構師免費幫你健檢。

<Scenario title="實務：上線前先跑一次體檢">

你剛做好一個系統準備上線，心裡不太確定有沒有漏掉什麼。這時打開 Well-Architected Tool 跑一輪，它可能會提醒你「你的資料庫沒有設定自動備份」「這個貯體對外公開了」——在出事之前就先抓出來，比半夜被叫起來救火好太多了。

</Scenario>
