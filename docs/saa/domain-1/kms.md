# 資料加密與 KMS：幫資料上鎖的「金鑰保險箱」

> 加密是 Domain 1 的核心考點之一。這篇帶你從「為什麼要加密」一路到「KMS 怎麼用」，完全不用密碼學背景。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **加密（Encryption）**：把看得懂的資料（明文）用一把「鑰匙」轉成亂碼（密文），沒鑰匙就看不懂。
- **金鑰（Key）**：加密和解密用的那把「鑰匙」，本質是一串很長的亂數。
- **KMS（Key Management Service）**：AWS 幫你**集中保管與管理金鑰**的服務，像一個上鎖的「金鑰保險箱」。
- **靜態加密（At Rest）**：資料**存放在硬碟上**時是加密的（例如存在 S3、EBS 裡）。
- **傳輸中加密（In Transit）**：資料**在網路上傳送**時是加密的（就是網址前面的 `https` / TLS）。

</Vocab>

## 為什麼需要加密？

<Scenario title="真實情境：一顆硬碟被偷走">

公司的伺服器硬碟被偷，裡面有幾十萬筆客戶資料。如果資料**沒加密**，小偷插上電腦就能直接讀取，公司得上新聞、挨罰、賠償。如果資料**有加密**，小偷拿到的只是一堆亂碼——**沒有鑰匙，等於廢鐵**。

</Scenario>

加密要做好兩個方向，**兩個都要**：

| 方向 | 白話 | 怎麼達成 |
| --- | --- | --- |
| **靜態加密（At Rest）** | 資料**躺在硬碟**時是鎖住的 | S3、EBS、RDS 開啟加密（背後用 KMS） |
| **傳輸中加密（In Transit）** | 資料**在路上移動**時是鎖住的 | 用 HTTPS / TLS 連線 |

## KMS 是什麼？用保險箱比喻

<Analogy title="🔐 生活比喻：把 KMS 想成銀行的金庫 + 鑰匙管理室">

- 你的資料 = 保險箱裡的貴重物品
- **資料金鑰（Data Key）** = 開你那個保險箱的鑰匙
- **KMS 主金鑰（KMS Key / CMK）** = 「鑰匙管理室」裡那把**用來鎖住所有鑰匙的總鑰匙**，它**永遠不離開 KMS**（連你都拿不出來，只能請 KMS 代為加解密）
- 這樣就算有人偷到你的「資料金鑰」，那把鑰匙本身也是被 KMS 總鑰匙鎖住的，沒 KMS 幫忙解不開

這套「用一把金鑰去加密另一把金鑰」的做法，叫 **信封加密（Envelope Encryption）**，是 KMS 的核心設計。

</Analogy>

## 為什麼要用 KMS 管金鑰？（而不是自己管）

<Scenario title="真實情境：自己管金鑰有多累">

你想自己加密資料，於是產了一把金鑰。問題馬上來了：這把金鑰**存哪**？存程式碼裡 → 被翻 Git 就外流；存設定檔 → 同樣危險；存資料庫 → 那資料庫又要誰的金鑰來保護？接著還有：**誰能用這把金鑰**（權限）、**多久換一次**（輪替）、**上次是誰、什麼時候用過**（稽核）、**金鑰外洩了怎麼全面換掉**……這些你全都得自己想辦法，而且一個環節做錯就滿盤皆輸。

</Scenario>

KMS 的意義，就是把上面這些「金鑰生命週期的麻煩事」整包交給 AWS 專業硬體與服務處理。白話對照：

| 自己管金鑰 | 交給 KMS |
| --- | --- |
| 金鑰存哪都怕外洩；主金鑰**可能被人拷貝走** | 主金鑰**鎖在硬體安全模組（HSM）裡，永遠匯不出來**，連你都拿不到明文 |
| 權限靠自己寫程式控制，容易漏 | 用 **金鑰政策 + IAM** 統一控管誰能加／解密 |
| 輪替要自己排程、自己換，容易忘 | CMK 可**一鍵開啟每年自動輪替**，舊資料照樣解得開 |
| 「誰用過這把金鑰」沒人知道 | 每次 encrypt/decrypt 都進 **CloudTrail**，可完整稽核 |
| 要跟 S3／EBS／RDS 整合得自己接 | AWS 服務**原生整合**，勾一下就用 KMS 加密 |

:::tip[💡 一句話抓重點]
KMS 幫你解決的不是「加密演算法」（那早有標準），而是**「金鑰本身要怎麼安全地保管、授權、輪替、稽核」**——這才是加密實務上最難、最容易出包的部分。
:::

## KMS 金鑰的三種類型（考試常考）

| 類型 | 誰建立／管理 | 特色 | 費用 |
| --- | --- | --- | --- |
| **AWS 擁有的金鑰（AWS owned）** | AWS 全權管理 | 你看不到、不用管，多個帳號共用 | 免費 |
| **AWS 託管金鑰（AWS managed）** | AWS 管理、對應某服務 | 名稱像 `aws/s3`、`aws/ebs`，自動輪替 | 免費（但 API 呼叫計費） |
| **客戶託管金鑰（Customer managed / CMK）** | **你自己建立與控制** | 可自訂權限、輪替、停用、稽核 | **每把 $1/月** + API 呼叫費 |

:::tip[💡 考試重點：什麼時候要用「客戶託管金鑰（CMK）」？]
當題目強調你需要**自己控制金鑰權限、自訂輪替週期、或要能稽核誰用了金鑰**時，答案就是 **Customer managed key**。如果只是「要加密、但不在意誰管鑰匙」，用 AWS managed key 就夠了（而且免月費）。
:::

### AWS 託管金鑰 vs 客戶託管金鑰（CMK）：到底怎麼選？

兩者都把主金鑰鎖在 AWS 的 HSM 裡、你都拿不到明文；差別在**「你能控制多少」與「要付多少錢」**：

| 比較項 | AWS 託管金鑰（`aws/s3` 等） | 客戶託管金鑰（CMK） |
| --- | --- | --- |
| 建立／擁有 | AWS 幫你建、綁定某個服務 | **你自己建、自己擁有** |
| 金鑰政策（誰能用） | 固定，**你不能改** | **可自訂**，精細到某個角色／帳號 |
| 自動輪替 | 固定**每年**一次，不能關也不能調 | **可自選開關**，可每年自動輪替 |
| 停用／排程刪除 | 不行（由 AWS 控管） | **可停用、可排程刪除** |
| 跨帳號分享 | 不行 | **可以**（透過金鑰政策授權別的帳號） |
| 匯入自己的金鑰材料 | 不行 | **可以**（BYOK，Import key material） |
| 月費 | **免費** | **每把 US$1／月** |

**白話選法**：

- **只是想「東西加密就好」、不想管** → 用 AWS 託管金鑰。省錢、零維護，考試裡「just encrypt it」類的描述多半選它。
- **需要自己掌控**（自訂誰能用、要稽核特定金鑰、要能隨時停用、跨帳號分享、自備金鑰材料、合規要求「金鑰由客戶掌控」）→ **非 CMK 不可**。

:::info[🔑 一個容易混的差異：都能稽核，但「可控程度」不同]
AWS 託管與客戶託管金鑰的使用紀錄**都會進 CloudTrail**，所以「要稽核」本身不足以斷定選 CMK。真正逼你選 **CMK** 的關鍵字是：**自訂金鑰政策／跨帳號／停用或刪除金鑰／自選輪替／自備金鑰材料（BYOK）**。只有「看得到誰用過」用託管金鑰也做得到。
:::

### 信封加密為什麼要這樣設計？（白話）

你可能會想：**幹嘛這麼麻煩？直接把資料丟給 KMS 加密不就好了？** 原因有三個很實際的限制：

1. **KMS 主金鑰永遠不出門，但資料很大**：主金鑰鎖死在 HSM 裡出不來，而 KMS 的 `Encrypt` API 一次最多只能處理 **4 KB** 的資料。你要加密一個 5 GB 的影片檔，不可能整包丟進 KMS。
2. **所以改成「兩段式」**：跟 KMS 要一把**一次性的資料金鑰**（KMS 回你「明文版」和「被主金鑰加密版」兩份）→ 你用**明文資料金鑰**在本地端飛快地把那 5 GB 加密（本地對稱加密，不受 4 KB 限制、也不用來回打 KMS）→ 用完**立刻把明文資料金鑰從記憶體丟掉**，只留「被加密的資料金鑰」跟密文存在一起。
3. **解密時反過來**：把「被加密的資料金鑰」丟回 KMS 解開（這段 ≤ 4 KB 沒問題）→ 拿回明文資料金鑰 → 在本地解開那 5 GB。

<Analogy title="🔐 生活比喻：為什麼不把保險箱整個搬進銀行金庫">

與其把一整個大保險箱（5 GB 資料）搬進銀行金庫請行員鎖（丟進 KMS），不如：自己在家用一把**小鑰匙**鎖保險箱（資料金鑰在本地加密），再把**這把小鑰匙**放進銀行金庫鎖起來（KMS 用主金鑰加密資料金鑰）。大東西留在家、只有小鑰匙進金庫——又快、又安全、又不受金庫「一次只收一小包」的限制。

</Analogy>

:::tip[💡 考試重點：信封加密解決什麼]
看到題目說**「要加密大型檔案／大量資料，又想用 KMS 管金鑰」**、或問**「為什麼不直接用 KMS 加密整份資料」** → 答案方向就是 **Envelope Encryption（信封加密）**：用 `GenerateDataKey` 拿資料金鑰在本地加密大資料，KMS 只負責保護那把資料金鑰。
:::

## 對稱 vs 非對稱金鑰：何時用哪種？

KMS 的金鑰預設是**對稱（Symmetric）**，但也能建**非對稱（Asymmetric）**金鑰。多數人只會用到對稱，但考試會考你分得清：

| | 對稱金鑰（Symmetric） | 非對稱金鑰（Asymmetric） |
| --- | --- | --- |
| 白話 | **同一把鑰匙**加密也解密 | 一對鑰匙：**公鑰加密、私鑰解密**（或私鑰簽章、公鑰驗章） |
| 金鑰出不出 KMS | 永遠**不出 KMS** | **公鑰可以匯出**給 AWS 外部的人用 |
| 典型用途 | S3／EBS／RDS 加密、信封加密（**絕大多數情況**） | 對方在 **AWS 之外**、拿不到你的 KMS，只能給他公鑰去加密；或做**數位簽章／驗章** |
| 速度／成本 | 快、便宜 | 較慢 |

**白話選法**：

- **預設一律用對稱金鑰**——AWS 服務整合、信封加密都是它，又快又省。
- **只有這兩種情況才用非對稱**：(1) 加密／解密的另一方在 **AWS 外部**、根本碰不到你的 KMS，你只能把**公鑰**交給他拿去加密；(2) 你需要**數位簽章**來證明「這份東西是我發的、沒被竄改」。

:::info[🔑 常見誤會：不是「比較安全」就選非對稱]
非對稱不是更高級、更安全的版本。對稱金鑰同樣鎖在 HSM 裡、同樣安全。選非對稱**只因為「對方拿不到 KMS」或「要做簽章」**這類相容性／功能需求，沒有這需求就別用——又慢又複雜。
:::

## S3 的三種加密方式（高頻考點）

當題目問「S3 怎麼加密」，記住這三個選項的差別：

| 方式 | 全名 | 金鑰誰管 | 重點 |
| --- | --- | --- | --- |
| **SSE-S3** | Server-Side Encryption with S3 keys | AWS 全包 | 最省事，預設選項 |
| **SSE-KMS** | Server-Side Encryption with KMS | 用 KMS（可用你的 CMK） | 可控制權限、可稽核，考題要「稽核／控制」時選它 |
| **SSE-C** | Server-Side Encryption with Customer keys | **你自己提供並保管金鑰** | AWS 不幫你存鑰匙，鑰匙丟了資料就沒了 |

## 實務應用

### 🛠️ 動手做：讓 S3 貯體預設就加密

1. 進 AWS 主控台 → 搜尋 `S3` → 點進你的貯體
2. 上方頁籤選 **屬性（Properties）**
3. 找到 **預設加密（Default encryption）** → 編輯
4. 加密類型選 **SSE-KMS**，金鑰選 `aws/s3`（或你自己的 CMK）→ 儲存
5. 之後上傳的檔案就會**自動加密**，不用每次手動設定

用 CLI 上傳一個檔案並指定 KMS 加密：

```bash
# 上傳檔案並用 KMS 加密
$ aws s3 cp report.csv s3://my-company-reports/ \
    --sse aws:kms

# 查看物件確認已加密
$ aws s3api head-object \
    --bucket my-company-reports \
    --key report.csv
# 回應裡會看到 "ServerSideEncryption": "aws:kms"
```

### 🛠️ 動手做：建一把 CMK，親手 encrypt / decrypt 一段文字

這個練習讓你**看到信封加密以外、KMS 最基本的 `Encrypt`／`Decrypt`**（記得 ≤ 4 KB）。

```bash
# 1) 建立一把客戶託管金鑰（CMK），順便加描述
$ aws kms create-key --description "my-first-cmk"
# 預期結果：回傳一包 JSON，裡面有 "KeyId": "1234abcd-...."、"Arn": "arn:aws:kms:..."
# 這個 KeyId 等等會用到；此時金鑰狀態 "KeyState": "Enabled"

# 2) 給它取個好記的別名（選用，比 KeyId 好認）
$ aws kms create-alias \
    --alias-name alias/my-first-cmk \
    --target-key-id 1234abcd-....
# 預期結果：沒有輸出就是成功（exit code 0）

# 3) 用這把金鑰加密一小段文字
$ aws kms encrypt \
    --key-id alias/my-first-cmk \
    --plaintext "hello-kms" \
    --query CiphertextBlob --output text
# 預期結果：印出一長串 base64 密文，例如 AQICAHh...（看不懂是正常的，那就是密文）

# 4) 把密文解回明文（密文要先 base64 解碼成檔案再丟進去）
$ echo 'AQICAHh...' | base64 --decode > ciphertext.bin
$ aws kms decrypt \
    --ciphertext-blob fileb://ciphertext.bin \
    --query Plaintext --output text | base64 --decode
# 預期結果：印回 hello-kms —— 代表加解密成功
# 注意：decrypt 不用指定 --key-id，KMS 會從密文的中繼資料認出該用哪把金鑰
```

```bash
# 練完清理：排程刪除金鑰（最短 7 天等待期，期間可反悔取消）
$ aws kms schedule-key-deletion \
    --key-id alias/my-first-cmk \
    --pending-window-in-days 7
# 預期結果：回傳 "KeyState": "PendingDeletion" 與一個 "DeletionDate"
# 想反悔：aws kms cancel-key-deletion --key-id ...
```

:::tip[💡 看懂這個練習的重點]
- `encrypt` 要**指定金鑰**，但 `decrypt` **不用**——因為該用哪把金鑰的資訊已經包在密文裡（這就是為什麼密文那麼長）。
- 真實世界加密大檔案不會這樣直接 `encrypt`（有 4 KB 限制），而是走**信封加密**（`generate-data-key`）。這個小練習只是讓你摸到 KMS 最底層的加解密動作。
:::

<Cost>

- **客戶託管金鑰（CMK）**：每把 **US$1／月**（不滿一個月按比例），外加每次加解密的 **API 呼叫費**（每萬次約 US$0.03）。
- **AWS 託管金鑰**（`aws/s3` 等）：**不收月費**，只收 API 呼叫費。
- 練習建議先用 `aws/s3` 這種託管金鑰，不會產生每月 $1 的固定費用。真的建了測試用 CMK，練完記得**排程刪除**（KMS 刪金鑰有 7~30 天等待期）。

</Cost>

:::warning[🚑 常踩雷]
- **金鑰是「區域性（Regional）」的！** 一把 KMS 金鑰只存在它被建立的那個區域，**不會自動跨區**。你在 `us-east-1` 建的金鑰，在 `ap-northeast-1` 的服務看不到、也用不到。要跨區用同一把金鑰，得改用**多區域金鑰（Multi-Region Key）**。
- **跨區複製加密資料，別忘了金鑰也要跟上**：把 `us-east-1` 用 CMK 加密的 EBS 快照／S3 物件**複製到另一個區域**時，目的區域要有能解密的金鑰——否則複製過去也**解不開**。做 S3 跨區複製（CRR）或 EBS 快照跨區複製時，要在目的區域指定一把當地的 KMS 金鑰（或用多區域金鑰）。
- **把金鑰刪掉／停用 = 資料永久救不回來，且不可逆！** 用該金鑰加密的所有資料都會解不開。所以 KMS **不給你「馬上刪」**——只能**排程刪除**，有 **7～30 天等待期**，期間可 `cancel-key-deletion` 反悔；一旦真的刪掉就**無法復原**。（想暫時停用但保留反悔空間，用 `disable-key` 而不是刪除。）
- **以為「有 IAM 權限就能用金鑰」**：KMS 金鑰還有自己的 **金鑰政策（Key Policy）**，**IAM 允許 + 金鑰政策允許兩個都要過**才行（雙重授權）。很多 `AccessDeniedException` 就是金鑰政策沒放行那個角色。新建 CMK 時若把預設金鑰政策刪光，可能連自己都鎖在外面。
- **SSE-C 的鑰匙自己弄丟**：AWS 完全不幫你保管，丟了就是丟了。
:::

:::tip[💡 一句話記住傳輸中 vs 靜態]
- 看到 **HTTPS / TLS / SSL** → 在講**傳輸中加密（In Transit）**
- 看到 **S3 / EBS / RDS 加密、KMS** → 在講**靜態加密（At Rest）**
:::
