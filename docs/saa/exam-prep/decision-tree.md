# 服務選型決策樹（看需求選服務）

這一頁把 SAA-C03 最常考的**選型題**整理成一棵棵「決策樹」。考場上看到題幹的需求關鍵字，就照著樹**一步步往下問**，很快就能定位到該選的服務，不用從零推理。

:::tip[怎麼用這頁]
每棵樹的用法都一樣：**先在題幹圈出需求關鍵字**（要控制 OS？要免維運？要跨區域？），再從樹的最上面往下走，每個分岔問自己一個是非題，走到葉子就是答案方向。平常複習時把每一條路徑念成一句話（「要 X 又要 Y → 選 Z」），考場就能變成反射。
:::

## 運算選型

<Term en="Compute" desc="運算服務：決定你的程式碼跑在哪裡" />。先問「要不要自己掌控作業系統」。

- 要完整控制 OS、長時間執行、特殊環境？→ **EC2**
- 事件驅動、短任務、按執行付費、最少維運？→ **Lambda**
- 要用容器，但不想管底層節點？→ **Fargate**
- 要用容器且需要編排叢集？→ **ECS**（AWS 原生）或 **EKS**（要 Kubernetes）

```text
運算需求
├─ 要控制 OS／長時間跑／特殊環境 ──────────→ EC2
├─ 事件驅動／短任務／免維運 ──────────────→ Lambda
└─ 用容器？
   ├─ 不想管節點 ───────────────────────→ Fargate
   └─ 要編排叢集 ───────────────────────→ ECS / EKS
```

## 儲存選型

先問「存的是物件、區塊，還是檔案（共享）」。

- 物件、海量非結構化檔案、靜態網站？→ **S3**
- 單台 EC2 專用的區塊硬碟？→ **EBS**
- 多台 Linux 要同時共享的檔案系統？→ **EFS**
- Windows、要 SMB 通訊協定的共享檔案？→ **FSx for Windows File Server**
- HPC、要極高吞吐的檔案系統？→ **FSx for Lustre**
- 只要極低延遲的暫存空間（可消失）？→ **Instance Store**

```text
儲存需求
├─ 物件／海量檔案 ───────────────────────→ S3
├─ 區塊硬碟
│  ├─ 單台 EC2 專用 ────────────────────→ EBS
│  └─ 極低延遲暫存（可消失）────────────→ Instance Store
└─ 檔案共享
   ├─ 多台 Linux 共享 ─────────────────→ EFS
   ├─ Windows / SMB ──────────────────→ FSx for Windows
   └─ HPC 高吞吐 ─────────────────────→ FSx for Lustre
```

## 資料庫選型

先問「要關聯式（SQL）還是非關聯式（NoSQL）」。

- 關聯式、交易型（<Term en="OLTP" desc="線上交易處理，重視即時讀寫一筆筆交易" />）、標準需求？→ **RDS**
- 關聯式，但要更高效能、更高可用或全球讀寫？→ **Aurora**
- NoSQL、鍵值、超大規模、個位數毫秒、無伺服器？→ **DynamoDB**
- 要記憶體快取、減輕資料庫壓力？→ **ElastiCache**
- 專門幫 DynamoDB 把毫秒變微秒的讀取快取？→ **DAX**
- 資料倉儲、<Term en="OLAP" desc="線上分析處理，重視大量資料的彙總分析報表" /> 分析報表？→ **Redshift**

```text
資料庫需求
├─ 關聯式（SQL）
│  ├─ 標準交易型（OLTP）─────────────────→ RDS
│  └─ 要更高效能／全球 ──────────────────→ Aurora
├─ NoSQL 鍵值／超大規模 ───────────────────→ DynamoDB
├─ 快取
│  ├─ 一般記憶體快取 ────────────────────→ ElastiCache
│  └─ 專給 DynamoDB 的微秒快取 ──────────→ DAX
└─ 資料倉儲／OLAP 報表 ────────────────────→ Redshift
```

## 訊息與整合選型

先問「這是點對點緩衝、一對多廣播、即時串流，還是依規則路由事件」。

- 要解耦、緩衝、削峰，一則訊息被消費一次？→ **SQS**
- 要一對多、把同一則訊息扇出給多個訂閱者？→ **SNS**
- 要即時串流、可保留與重播、要保順序？→ **Kinesis**
- 要事件匯流排、依規則把事件路由到不同目標？→ **EventBridge**

```text
訊息／整合需求
├─ 解耦／緩衝／削峰（一對一消費）──────────→ SQS
├─ 一對多廣播（扇出）─────────────────────→ SNS
├─ 即時串流（可重播／保順序）─────────────→ Kinesis
└─ 事件依規則路由 ────────────────────────→ EventBridge
```

## 網路連通選型

先問「要連外網、連 AWS 服務、連另一個 VPC，還是連地端」。

- 私有子網路要主動連外網（上網更新、呼叫外部 API）？→ **NAT Gateway**
- VPC 內要免費私下存取 S3／DynamoDB？→ **Gateway Endpoint**
- 兩個 VPC 要私下互連？→ **VPC Peering**
- 很多 VPC 或跨帳號要集中互連？→ **Transit Gateway**
- 地端要穩定、低延遲、高頻寬的專線？→ **Direct Connect**
- 地端要便宜、快速建立的加密通道（走網際網路）？→ **Site-to-Site VPN**

```text
網路連通需求
├─ 連外網（私有子網路主動出外）──────────→ NAT Gateway
├─ 連 AWS 服務（VPC 內免費存取 S3/DynamoDB）→ Gateway Endpoint
├─ 連另一個 VPC
│  ├─ 只有兩個 VPC ─────────────────────→ VPC Peering
│  └─ 很多 VPC／跨帳號 ─────────────────→ Transit Gateway
└─ 連地端（混合雲）
   ├─ 要穩定低延遲專線 ──────────────────→ Direct Connect
   └─ 要便宜快速加密通道 ────────────────→ Site-to-Site VPN
```

## 內容傳遞與效能選型

先問「要加速的是可快取的 HTTP 內容，還是非 HTTP 流量，或只是讀取太多」。

- 可快取的 HTTP／靜態內容要全球加速？→ **CloudFront**
- 非 HTTP（TCP／UDP）、要固定 IP、要全球低延遲？→ **Global Accelerator**
- 資料庫讀取流量太大、要分攤？→ **Read Replica（讀取複本）**

```text
傳遞／效能需求
├─ 可快取的 HTTP 全球加速 ─────────────────→ CloudFront
├─ 非 HTTP（TCP/UDP）固定 IP 全球低延遲 ────→ Global Accelerator
└─ 分攤資料庫讀取 ───────────────────────→ Read Replica
```

:::info[CloudFront 與 Global Accelerator 怎麼分]
看到「可快取、網站、影片、靜態內容」就是 **CloudFront**；看到「非 HTTP、遊戲、需要固定（Anycast）IP、不快取」就是 **Global Accelerator**。
:::

## 高可用與災難復原選型

先問「要撐的是單一 AZ 故障，還是整個 Region 故障」。

- 要抵抗單一 AZ 故障、在同區域內維持服務？→ **跨多 AZ 部署**：ALB + Auto Scaling Group + RDS Multi-AZ
- 要抵抗整個 Region 故障？→ 依 <Term en="RTO" desc="復原時間目標：可以接受停機多久" /> 與 <Term en="RPO" desc="復原點目標：可以接受遺失多少資料" /> 的嚴格程度，由便宜到貴選一種 DR 策略：
  - RTO／RPO 可以很寬鬆、最省錢？→ **Backup & Restore（備份還原）**
  - 要快一點，保留最小核心？→ **Pilot Light（指示燈）**
  - 要更快，跑一個縮小版環境隨時待命？→ **Warm Standby（暖備）**
  - 幾乎零停機、零資料遺失、最貴？→ **Multi-Site Active/Active（多站點）**

```text
高可用／DR 需求
├─ 撐單一 AZ 故障（同區域）──────────────→ 跨多 AZ + ALB + ASG + RDS Multi-AZ
└─ 撐整個 Region 故障（看 RTO/RPO，由便宜到貴）
   ├─ RTO/RPO 最寬鬆、最省 ─────────────→ Backup & Restore
   ├─ 要快一點 ────────────────────────→ Pilot Light
   ├─ 要更快（縮小版待命）──────────────→ Warm Standby
   └─ 幾乎零停機、最貴 ─────────────────→ Multi-Site
```

## 遷移選型

先問「搬的是大量資料、持續的地端儲存、線上檔案同步，還是資料庫」。

- PB 等級資料、頻寬不足、用網路搬太久？→ **Snowball**
- 地端要持續用雲端儲存、想取代實體磁帶？→ **Storage Gateway**
- 要在網路上大量、持續同步檔案到 AWS？→ **DataSync**
- 要遷移資料庫（含不同引擎的異質遷移）？→ **DMS**（異質遷移再搭 **SCT** 轉換結構）

```text
遷移需求
├─ PB 級資料 + 頻寬不足 ───────────────────→ Snowball
├─ 地端持續用雲端儲存／取代磁帶 ───────────→ Storage Gateway
├─ 線上大量檔案同步 ─────────────────────→ DataSync
└─ 資料庫遷移
   ├─ 同引擎 ────────────────────────────→ DMS
   └─ 異質（換引擎）────────────────────→ DMS + SCT
```

## 成本選型

先問「負載是穩定長期、可中斷批次、存取頻率未知，還是長期封存」。

- 穩定、可預測、長期運行要省錢？→ **Reserved Instances／Savings Plans**
- 可被中斷的批次、容錯、無狀態工作要最省？→ **Spot**
- 存取頻率未知或會變、不想手動搬層？→ **S3 Intelligent-Tiering**
- 長期封存、幾乎不取回、可接受慢慢取回？→ **S3 Glacier Deep Archive**

```text
成本需求
├─ 穩定長期負載 ─────────────────────────→ RI / Savings Plans
├─ 可中斷的批次／容錯工作 ─────────────────→ Spot
├─ 存取頻率未知或會變 ───────────────────→ S3 Intelligent-Tiering
└─ 長期封存、幾乎不取回 ─────────────────→ S3 Glacier Deep Archive
```

## 安全選型

先問「要解決的是跨帳號存取、金鑰管理、密碼輪替，還是擋攻擊」。

- 跨帳號、要臨時憑證、不想散播長期金鑰？→ **STS AssumeRole**
- 要集中管理加密金鑰？→ **KMS**
- 要集中保管密碼／憑證並自動輪替？→ **Secrets Manager**
- 要擋第 7 層（應用層）攻擊（SQL injection、XSS）？→ **WAF**
- 要擋 DDoS 攻擊？→ **Shield**

```text
安全需求
├─ 跨帳號臨時存取 ───────────────────────→ STS AssumeRole
├─ 集中管理加密金鑰 ─────────────────────→ KMS
├─ 密碼／憑證自動輪替 ───────────────────→ Secrets Manager
└─ 擋攻擊
   ├─ 第 7 層應用層攻擊 ───────────────────→ WAF
   └─ DDoS ──────────────────────────────→ Shield
```

:::note[這頁只是總整理]
決策樹是幫你在考場**快速定位方向**用的，每個服務的細節、計費陷阱、容易混淆的對決，請回各領域文章與[考前衝刺重點](./cram.md)複習。真正的判別點永遠在題幹的**限定詞**（最省錢、最少維運、最高可用、即時…），先圈限定詞，再走決策樹。
:::
