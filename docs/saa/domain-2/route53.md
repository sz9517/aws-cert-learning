# Route 53：網路世界的「總機與導航」

> 使用者在瀏覽器打的是 `www.example.com`，但電腦之間其實是用 IP 位址溝通。把人類看得懂的網域名稱翻譯成 IP，就是 DNS 的工作——而 Route 53 是 AWS 的 DNS 服務，還能幫你把流量「導」到最健康、最近、最適合的伺服器。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **DNS（Domain Name System）**：把網域名稱（`example.com`）翻譯成 IP 位址（`52.1.2.3`）的「**網路電話簿**」。
- **網域名稱（Domain Name）**：人類好記的網站地址，例如 `example.com`。
- **記錄（Record）**：電話簿裡的一筆資料，告訴大家「這個名字對應到哪個 IP 或哪個資源」。
- **健康檢查（Health Check）**：Route 53 定時去「敲門」問伺服器還活著嗎，壞掉就不再把人導過去。

</Vocab>

## 一句話先懂 Route 53

**Route 53** 是 AWS 的 <Term en="Domain Name System" desc="把網域名稱翻譯成 IP 位址的網路電話簿。">DNS</Term> 服務（名字取自 DNS 使用的 53 埠）。它做兩件事：**（1）把網域名稱翻譯成 IP**，**（2）依照你設定的「路由策略」決定要把每個使用者導向哪一台伺服器**。第二件事，正是它在高可用架構裡的關鍵角色。

<Analogy title="☎️ 生活比喻：把 Route 53 想成一間大公司的總機">

- 你打電話報上要找的「部門名稱」（網域名稱）
- **總機（Route 53）** 幫你轉接到正確分機（IP 位址）
- 聰明的總機還會：看哪個客服最閒（加權）、幫你轉到離你最近的分點（延遲／地理位置）、發現某分機沒人接就自動轉到備援分機（故障轉移 + 健康檢查）

</Analogy>

## DNS 怎麼運作（白話流程）

當你輸入 `www.example.com`：

1. 電腦先問 DNS：「這個名字的 IP 是多少？」
2. 查詢最後會問到管理這個網域的 Route 53
3. Route 53 依你設定的記錄與路由策略回一個 IP
4. 瀏覽器拿到 IP，才真正連上網站

## 路由策略一次看懂（考試最愛考）

Route 53 的威力在於「同一個網域名稱，可以有多筆記錄，用不同策略決定回哪一筆」：

| 路由策略 | 做什麼 | 典型用途 |
| --- | --- | --- |
| **簡單（Simple）** | 一筆記錄對一個或多個 IP，隨機回傳 | 最單純的網站，沒有特殊需求 |
| **加權（Weighted）** | 依你設定的比例分流（例如 90% / 10%） | <Term desc="新舊版本同時上線，用比例慢慢把流量導到新版，有問題可立刻縮回。">藍綠／金絲雀部署</Term>、A/B 測試 |
| **延遲（Latency）** | 回傳「對使用者延遲最低」的區域端點 | 多區域部署，要讓使用者連到最快的那區 |
| **故障轉移（Failover）** | 主要端點健康就用主要，掛了自動切備援 | 主備（Active-Passive）高可用 |
| **地理位置（Geolocation）** | 依使用者**所在國家／地區**回傳不同結果 | 內容在地化、法規限制（某國只能看某版） |
| **地理鄰近（Geoproximity）** | 依地理距離分流，還能用 bias 調整偏向 | 精細控制「哪區服務哪些人」 |
| **多值回應（Multivalue）** | 一次回多個健康的 IP，客戶端自己挑 | 簡易的分散與容錯（非正式負載平衡器） |

:::tip[💡 考試重點]
- 題目說「讓全球使用者連到**延遲最低**的區域」→ 選 **延遲路由（Latency）**。
- 題目說「依**使用者所在國家**提供不同內容／擋特定國家」→ 選 **地理位置路由（Geolocation）**。這兩個最容易被混淆，關鍵字一個是「速度」、一個是「地點」。
- 「主站掛掉要**自動**切到備援站」→ **故障轉移路由 + 健康檢查**。
- 要做**藍綠／金絲雀**慢慢導流 → **加權路由**。
- **Alias vs CNAME**：指向 AWS 資源（ELB、CloudFront、S3 靜態網站）請用 **Alias 記錄**，它**免費**且**根網域（Zone Apex，如 `example.com`）只能用 Alias**，CNAME 無法用在根網域。
:::

## 為什麼要用 Route 53？（而不是別的 DNS）

一般的 DNS 服務只做一件事：把名字翻成 IP。Route 53 多做的是**「依狀況把流量導到對的地方」**，而且和 AWS 的其他服務深度整合：

- **健康檢查內建**：Route 53 自己會定時敲門確認端點還活著，壞了就不再導過去——這是「自動故障轉移」的基礎，純 DNS 做不到。
- **Alias 記錄免費指向 AWS 資源**：指到 ELB、CloudFront、S3 靜態網站時，不但免查詢費，資源 IP 變了還會**自動跟著變**（下面詳述）。
- **多種路由策略**：同一個網域名稱可以依「最低延遲、使用者所在國家、權重比例、健康狀態」回不同答案，等於把一部分流量控制邏輯交給 DNS 層。
- **高可用的服務本身**：Route 53 是 AWS 少數掛著 **100% 可用性 SLA** 的服務。

:::info[🔑 一句話釐清常見誤會]
Route 53 是**把人導到哪台伺服器**，不是**處理連線本身**。它在使用者「還沒連上去」的查名字階段作用；真正接住連線、做連線層負載平衡與擋流量的是 **ELB / WAF / Shield**，不是 Route 53。這個分界考試和實務都很關鍵（下面「常踩雷」還會再提）。
:::

## 路由策略怎麼選？何時用哪個（優缺點 + 搭配健康檢查）

上面的表格告訴你「每個策略做什麼」，這一段補「**為什麼選它、什麼時候別用、要不要配健康檢查**」——這正是情境題在考的。

<Analogy title="☎️ 先用總機比喻記住七種轉接方式">

- **簡單**：只有一組分機，照名單隨便給一個。
- **加權**：九成轉舊客服、一成轉新客服，試水溫。
- **延遲**：轉到「接通最快」的那個分點。
- **故障轉移**：主分機沒人接，自動轉備援分機。
- **地理位置**：看你**從哪個國家打來**，轉不同分點（法規／在地化）。
- **地理鄰近**：看你**實際距離多近**轉，還能用 bias 手動把某區的服務範圍「調大調小」。
- **多值回應**：一次給你好幾支健康的分機號碼，你自己挑一支打。

</Analogy>

| 策略 | 為什麼選它 | 缺點／限制 | 要配健康檢查嗎 |
| --- | --- | --- | --- |
| **簡單（Simple）** | 設定最省事，單一端點網站夠用 | **不支援健康檢查**；回傳的 IP 掛了也照給 | 不能配（這正是它的最大限制） |
| **加權（Weighted）** | 能按比例慢慢放量，藍綠／金絲雀、A/B 測試首選 | 要自己維護權重；非真正負載平衡 | 建議配（壞掉的端點權重自動視為 0，不再導入） |
| **延遲（Latency）** | 多區域部署時，讓每個使用者連到**對他最快**的那區 | 比的是「網路延遲」不是「地理距離」，兩者不一定一致 | 建議配（某區掛了要能排除） |
| **故障轉移（Failover）** | 主備（Active-Passive）高可用的標準答案 | 只有主／備兩種角色，不做多端點分流 | **必須配**（沒健康檢查就不知道何時該切） |
| **地理位置（Geolocation）** | 依**使用者所在國家／洲**給不同內容；做法規封鎖、在地化語言版 | 以「使用者在哪」為準，**不保證最快**；建議設一筆 `Default` 接住沒對應到的地區 | 建議配 |
| **地理鄰近（Geoproximity）** | 要**精細控制「哪一區服務多大範圍」**，用 bias 擴大／縮小某區勢力範圍 | 設定較複雜，需搭配 **Traffic Flow**；比延遲路由難懂 | 建議配 |
| **多值回應（Multivalue）** | 想要「簡單的分散 + 只回健康的 IP」，比 Simple 多了健康過濾 | **不是負載平衡器**：只是隨機回多筆、由客戶端挑，無連線層分流 | 建議配（會自動濾掉不健康的 IP） |

:::tip[💡 考試重點：關鍵字 → 策略 對照]
- 「全球使用者要連**最快**的區域」→ **延遲（Latency）**（關鍵字：速度／延遲）。
- 「依**使用者所在國家**給不同內容／封鎖某國」→ **地理位置（Geolocation）**（關鍵字：國家／地區／法規）。← 和延遲最常被混，一個比速度、一個比地點。
- 「主站掛掉要**自動**切備援」→ **故障轉移（Failover）＋ 健康檢查**（缺一不可）。
- 「新版**慢慢放量**、有問題能縮回」→ **加權（Weighted）**。
- 「要**精細調整某區服務範圍**（bias）」→ **地理鄰近（Geoproximity）**。
- 「回**多個健康 IP** 讓客戶端自己挑、但又不想架 ELB」→ **多值回應（Multivalue）**。
- 看到 **Simple 搭健康檢查**的選項直接刪——Simple **不支援**健康檢查。
:::

## Alias vs CNAME：為什麼優先用 Alias

這題幾乎每次都考，而且實務上很容易卡住。兩者都是「把一個名字指到另一個目標」，但差別很關鍵：

| 比較項 | **Alias（別名記錄，Route 53 專屬）** | **CNAME（標準 DNS 記錄）** |
| --- | --- | --- |
| **能用在根網域（Zone Apex，如 `example.com`）嗎** | ✅ 可以 | ❌ **不行**（DNS 規範不允許，最常見卡關點） |
| **指向 AWS 資源的查詢費用** | **免費** | 照一般查詢計費 |
| **目標 IP 變動** | Route 53 **自動跟著變**（如 ELB 換 IP 你不用動） | 指到一個**名字**，名字背後 IP 由對方管 |
| **能指向什麼** | AWS 資源（ELB、CloudFront、S3 靜態網站、API Gateway、另一筆同區 Route 53 記錄…） | 任何網域名稱（含非 AWS 的外部網域） |
| **回應型態** | DNS 查詢時直接回 **A/AAAA**（IP） | 回一個 **CNAME**（名字），用戶端要再查一次 |

**所以為什麼優先用 Alias？**

1. **根網域只能用 Alias**——想讓 `example.com`（不是 `www.example.com`）直接指到 ELB／CloudFront，**只有 Alias 辦得到**，CNAME 在 Zone Apex 是違規的。
2. **免費**——指向 AWS 資源的 Alias 查詢不收費，CNAME 查詢要錢。
3. **少一跳、少一層維護**——Alias 直接回 IP（少一次 DNS 查詢往返），而且目標資源換 IP 時自動跟上，不用你手動改記錄。

**那什麼時候還是得用 CNAME？** 當你要指向的是**非 AWS 的外部網域名稱**（例如第三方 SaaS 給你的 `xxx.vendor.com`），Alias 指不到，就用 CNAME——但記得**只能用在子網域**（如 `www`、`app`），不能用在根網域。

<Scenario title="真實情境：老闆要 example.com（不是 www）直接開我的網站">

你把網站放在 CloudFront 後面，想讓使用者打 `example.com` 就直接進站。你第一直覺是加一筆 CNAME 指到 CloudFront 網域——結果 Route 53 根本不給你在根網域存 CNAME。正解：在根網域 `example.com` 建一筆 **Alias 記錄（type A）指向該 CloudFront 分配**即可；順手再給 `www` 也建一筆 Alias 或 CNAME 指到同一處。

</Scenario>

## 實務應用：不只是考試

<Scenario title="真實情境：你負責的官網不能有『打不開』的時候">

老闆說：「這個官網是公司門面，主機房如果出事，**不能讓客戶看到錯誤頁**，要自動切到另一區的備援站。」——這正是「故障轉移路由 + 健康檢查」的標準解法。下面帶你做一次。

</Scenario>

### 🛠️ 動手做：用 Failover + 健康檢查做主備高可用

1. 登入 AWS 主控台 → 搜尋列輸入 `Route 53` → 進入服務
2. 先建**健康檢查**：左側 **Health checks** → **Create health check** → 填主站的網域／IP 與監控的路徑（例如 `/health`）→ 建立
3. 進入你的 **託管區域（Hosted Zone）** → **Create record**
4. 建立**主要記錄**：Record name 填 `www`、Routing policy 選 **Failover**、Failover record type 選 **Primary**、關聯剛剛的健康檢查、值填主站（建議對 AWS 資源用 **Alias**）
5. 再建一筆**備援記錄**：同名、Failover 選 **Secondary**、值填備援站
6. 測試：把主站停掉或讓健康檢查失敗，稍待 TTL 後查詢 `www` 會自動回備援站

```bash
# 查詢某網域目前解析到的 IP，驗證切換是否生效
$ dig +short www.example.com
# 預期結果：主站健康時回主站 IP（例如 52.1.2.3）；
# 讓主站的健康檢查失敗、等過了 TTL 再查，應改回備援站 IP（例如 54.9.8.7）。

# 用 nslookup 也可以（Windows 常用）
$ nslookup www.example.com
# 預期結果：Name / Address 兩行，Address 就是目前 Route 53 回給你的 IP。
```

:::tip[💡 怎麼確認故障轉移真的生效]
別只看主控台顯示「Unhealthy」。實際做法：讓主站健康檢查轉紅 → **等超過你設的 TTL** → 用上面的 `dig`／`nslookup` 查，看回來的 IP 是否換成備援站。TTL 沒過就查，很可能拿到被快取的舊 IP，誤以為沒切換。
:::

<Cost>

Route 53 的計費很小但不是全免：每個**託管區域**約 **$0.50/月**，查詢量另計（每百萬筆查詢數美分等級），**健康檢查**每個約 **$0.50/月**（AWS 端點）。**Alias 記錄指向 AWS 資源的查詢免費**，這是相對 CNAME 的一大好處。練習完把不需要的託管區域與健康檢查刪掉即可。

</Cost>

:::warning[🚑 常踩雷]
- **TTL 設太長，切換好慢？** DNS 結果會被各層（使用者電腦、ISP）**快取到 TTL 過期為止**。若主備記錄 TTL 設成 3600 秒，故障轉移後最糟要等一小時舊使用者才看到新 IP。**切換前先把 TTL 調短（例如 60 秒）**，穩定後再視需要調回。這是「設了故障轉移卻感覺切換超慢」的頭號原因。
- **想在根網域 `example.com` 用 CNAME？** 不行！根網域（Zone Apex）只能用 **Alias**；CNAME 只能用在子網域（如 `www`）。這是最常見的卡關點，記起來直接送分。
- **設了故障轉移卻沒建健康檢查？** 那 Route 53 根本不知道主站掛了，**永遠不會切換**，等於白設。故障轉移**一定**要綁健康檢查，而且確認健康檢查監控的路徑（如 `/health`）真的會在故障時回非 2xx／3xx。
- **以為 Route 53 能「擋流量」？** Route 53 只負責**回一個 IP**，使用者拿到 IP 後是**直接連你的伺服器**，流量根本不經過 Route 53。所以它**擋不了 DDoS、也做不了 WAF 規則**——那是 **Shield / WAF / ELB** 的事。別把 Route 53 當防火牆或負載平衡器。
- **把多值回應當負載平衡器？** 多值回應只是「隨機回多個健康 IP、由客戶端挑」，沒有連線層級的健康偵測與分流能力，正式負載平衡請用 **ELB**。
:::
