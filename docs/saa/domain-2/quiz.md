# Domain 2 原創練習題（仿官方考題風格）

先自己點選答案，再按「**顯示答案與解析**」。本頁對齊 SAA-C03 官方題型：**情境式題幹**、選項皆為合理的 AWS 服務（誘答選項不會明顯錯誤），並刻意用「**最具成本效益／最少營運負擔／最高可用**」這類**限定詞**逼你比較取捨。包含**單選**與**複選（Choose TWO）**兩種題型。題目為**原創**內容（非真實考題）。

<Quiz
  qnum={1}
  total={12}
  question="某公司的 Web 應用程式目前部署在單一可用區（AZ）內的多台 EC2 上，前面有一個 Application Load Balancer。公司希望在「單一 AZ 發生故障時服務仍可用」，且架構變更越少越好。下列哪個做法最合適？"
  options={[
    '改用規格更大的 EC2 機型並增加每台資源',
    '在第二個可用區新增 EC2，並確認 ALB 與 Auto Scaling Group 橫跨兩個 AZ',
    '把整套應用程式複製到另一個 AWS Region',
    '為每台 EC2 開啟每小時快照',
  ]}
  answer={1}>

**正解：B**

高可用的核心是**跨多個 AZ** 消除單點故障。讓 ALB 與 ASG 橫跨兩個 AZ，一個 AZ 整個故障時另一個仍能服務，且改動最小。A 是垂直擴展，單台還是會壞；C 跨 Region 是災難復原層級，成本與複雜度過高、非此題最佳解；D 的快照只是備份，無助於「持續可用」。

</Quiz>

<Quiz
  qnum={2}
  total={12}
  question="某遊戲公司需要一個負載平衡器處理每秒數百萬筆 TCP 連線、延遲要極低，而且合作廠商的防火牆只允許白名單中的「固定靜態 IP」。最適合的方案是？"
  options={[
    'Application Load Balancer（ALB）',
    'Network Load Balancer（NLB）',
    'Amazon CloudFront',
    'Gateway Load Balancer（GWLB）',
  ]}
  answer={1}>

**正解：B**

**NLB** 運作在第 4 層，具備超高效能、超低延遲，且可指派**靜態／彈性固定 IP**，完全符合「極高 TCP 效能 + 固定 IP 白名單」需求。ALB 是第 7 層、無法提供固定 IP；CloudFront 是內容傳遞網路；GWLB 用於串接第三方網路設備。

</Quiz>

<Quiz
  qnum={3}
  total={12}
  question="某電商網站白天流量高、深夜幾乎沒人。公司希望依實際流量自動增減 EC2 數量，以「最具成本效益」的方式維持效能，且不需人工介入。最合適的做法是？"
  options={[
    '固定開啟尖峰所需的最大台數',
    '在 Auto Scaling Group 設定目標追蹤策略，維持平均 CPU 使用率在設定值',
    '請工程師每天手動在尖峰前開機、離峰後關機',
    '改用運算能力最大的 EC2 機型',
  ]}
  answer={1}>

**正解：B**

**目標追蹤**策略會依指標（如平均 CPU）自動 scale out／in，流量低時縮減、只為需要的量付費，最符合「最具成本效益且免人工」。A 永遠跑最大量、浪費成本；C 需人工且無法應付突發；D 仍是單點且成本高。

</Quiz>

<Quiz
  qnum={4}
  total={12}
  question="某訂單系統在促銷時瞬間湧入大量請求，常壓垮後端服務。公司希望「解耦前後端、在尖峰時不遺失任何請求」，並讓後端依自身處理能力消化。最合適的做法是？"
  options={[
    '提高資料庫的最大連線數上限',
    '在前後端之間加入 Amazon SQS 佇列作為緩衝',
    '用 Amazon SNS 把每筆請求即時推播給後端',
    '把後端換成運算能力更大的 EC2 機型',
  ]}
  answer={1}>

**正解：B**

**SQS** 佇列是典型的緩衝／解耦方案：請求先進佇列排隊、不會遺失，後端（可搭配 Auto Scaling）**依自己步調拉取**處理，尖峰不會直接壓垮後端。SNS 是即時推播、無法緩衝（C 錯）；A、D 治標不治本。

</Quiz>

<Quiz
  qnum={5}
  total={12}
  question="某公司在兩個 Region 各有一套環境：主要環境與待命環境。公司要求當主要環境的健康檢查失敗時，使用者流量能「自動」導向待命環境，恢復後再切回。應使用 Route 53 的哪種設定？"
  options={[
    '加權路由，兩邊各設 50%',
    '故障轉移（Failover）路由搭配健康檢查',
    '簡單路由直接指向主要環境',
    '地理位置路由依使用者所在國家分流',
  ]}
  answer={1}>

**正解：B**

**故障轉移路由 + 健康檢查**是主備（Active/Passive）自動切換的標準做法：健康檢查發現主站異常即自動把流量導向待命站。加權是按比例分流、不會自動容錯；簡單路由無健康檢查；地理位置路由以使用者位置為依據，皆不符需求。

</Quiz>

<Quiz
  qnum={6}
  total={12}
  question="某內部報表系統可容忍「數小時」的復原時間，資料每日備份一次即可。公司希望災難復原方案的「平時成本最低」。最合適的 DR 策略是？"
  options={[
    'Multi-Site Active/Active（多站同時運作）',
    'Warm Standby（縮小版持續運作）',
    'Pilot Light（核心常開、其餘待命）',
    'Backup & Restore（平時只備份，需要時再還原）',
  ]}
  answer={3}>

**正解：D**

題目強調「可容忍數小時 RTO」且要「平時成本最低」，**Backup & Restore** 正是四大策略中成本最低者（平時只付備份儲存費），代價是復原最慢——完全符合需求。其餘三者越即時、平時成本越高。此題考 **RTO 與成本的取捨**。

</Quiz>

<Quiz
  qnum={7}
  total={12}
  question="某正式環境的 RDS 資料庫，公司要求「在主執行個體發生故障時能自動容錯移轉」、將停機時間降到最低。應啟用下列何者？"
  options={[
    '建立一個 Read Replica（唯讀複本）',
    '啟用 Multi-AZ 部署',
    '增加資料庫的儲存空間',
    '改為每 5 分鐘建立一次手動快照',
  ]}
  answer={1}>

**正解：B**

**RDS Multi-AZ** 會同步複寫到另一個 AZ 的備援執行個體，主庫故障時**自動容錯移轉**，停機極短——正是高可用需求。Read Replica 是非同步、用於讀取擴展，不會自動接手（A 錯）；C、D 都無法達成自動容錯移轉。

</Quiz>

<Quiz
  qnum={8}
  total={12}
  question="某報表系統對 RDS 產生大量「唯讀查詢」，拖慢了主資料庫的寫入效能。公司希望「分攤讀取流量」且盡量不影響主資料庫。最合適的做法是？"
  options={[
    '啟用 Multi-AZ 部署，讓備援執行個體分攤讀取',
    '建立一個或多個 Read Replica，把報表的唯讀查詢導向複本',
    '把資料庫換成更大機型後就不再調整',
    '暫時關閉報表功能',
  ]}
  answer={1}>

**正解：B**

**Read Replica** 專為**讀取擴展**設計：建立複本並把唯讀查詢導過去，即可分攤主庫負載。注意 **Multi-AZ 的備援平時不分擔讀取**（A 是常見誘答）；C 治標、D 不可行。

</Quiz>

<Quiz
  qnum={9}
  total={12}
  question="某公司要讓根網域 example.com（zone apex）指向一個 Application Load Balancer，並符合 AWS 最佳實務。應建立下列哪種 DNS 記錄？"
  options={[
    '指向 ALB DNS 名稱的 CNAME 記錄',
    '指向 ALB 的 Route 53 Alias 記錄',
    '寫死 ALB 目前 IP 的 A 記錄',
    '指向 ALB 的 TXT 記錄',
  ]}
  answer={1}>

**正解：B**

**根網域（zone apex）不能用 CNAME**（DNS 規範限制），須使用 Route 53 的 **Alias** 記錄指向 ALB 等 AWS 資源；Alias 查詢免費。ALB 的 IP 會變動，不能寫死 A 記錄（C 錯）；TXT 記錄與網域導向無關（D 錯）。

</Quiz>

<Quiz
  qnum={10}
  total={12}
  question="某公司要將一個三層式 Web 應用程式設計成高可用，以承受「單一可用區故障」。下列哪兩項措施能直接達成此目標？（選兩項）"
  options={[
    '將 EC2 的 Auto Scaling Group 設定為橫跨多個可用區',
    '為後端的 RDS 資料庫啟用 Multi-AZ 部署',
    '把所有資源集中在單一可用區以降低延遲',
    '改用運算能力更大的單一 EC2 機型',
    '關閉負載平衡器的健康檢查以避免誤判',
  ]}
  answer={[0, 1]}>

**正解：A、B**

高可用的關鍵是**跨多個 AZ 消除單點故障**：讓 ASG 橫跨多 AZ（A）保障運算層、RDS 啟用 Multi-AZ（B）保障資料層，兩者都能承受單一 AZ 故障。C 集中單一 AZ 正好製造 SPOF；D 垂直擴展單台仍會壞；E 關閉健康檢查會讓流量送到故障目標，反而更糟。

</Quiz>

<Quiz
  qnum={11}
  total={12}
  question="某系統在「訂單成立」時要同時通知多個下游服務，且要求「即使某個下游服務暫時離線，也不能遺失通知訊息」。下列哪兩項組合最適合？（選兩項）"
  options={[
    '建立一個 Amazon SNS 主題，讓訂單服務在事件發生時發布訊息',
    '讓每個下游服務各自以一個 SQS 佇列訂閱該 SNS 主題（扇出模式）',
    '讓訂單服務逐一同步呼叫每個下游服務的 API',
    '用單一共用資料庫欄位當旗標，讓下游輪詢',
    '把所有下游處理邏輯直接寫進訂單服務裡',
  ]}
  answer={[0, 1]}>

**正解：A、B**

**SNS + 多個 SQS 的扇出（fan-out）**：SNS 負責一對多廣播，每個下游各掛一個 SQS 佇列當緩衝——下游離線時訊息仍留在各自佇列，上線後再消化，**不會遺失**。C、E 是緊耦合，任一下游慢或掛都拖垮主流程；D 輪詢旗標既不即時也不可靠。

</Quiz>

<Quiz
  qnum={12}
  total={12}
  question="某公司希望一組 EC2 車隊能「自動替換故障的執行個體」並「依流量自動調整數量」，全程免人工。下列哪兩項設定能共同達成？（選兩項）"
  options={[
    '使用 Auto Scaling Group，並設定目標追蹤擴展策略維持目標指標',
    '將 ASG 的健康檢查搭配 ELB，使不健康的執行個體被自動終止並替換',
    '停用健康檢查，避免執行個體被誤判而終止',
    '把期望容量（desired）固定設為等於最大容量（max）',
    '改採垂直擴展，流量變大時換更大的機型',
  ]}
  answer={[0, 1]}>

**正解：A、B**

**目標追蹤（A）** 讓 ASG 依指標自動 scale out／in；**ELB 健康檢查（B）** 讓 ASG 偵測到不健康的執行個體時自動終止並補新機——兩者合起來同時滿足「自動調整數量」與「自動替換故障」。C 關掉健康檢查會留著故障機；D 等於永遠跑最大量、失去彈性；E 垂直擴展單台仍是單點。

</Quiz>
