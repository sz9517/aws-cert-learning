# 備份與災難復原：天塌下來也救得回來

> 高可用（多 AZ）顧的是「一台機器壞掉」，但如果**整個區域（Region）** 發生大地震、大停電呢？這就要靠備份與災難復原（DR）計畫。這篇教你用兩個指標衡量、用四種策略在「復原速度」和「成本」之間做取捨。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **備份（Backup）**：把資料**另外複製一份存起來**，原始資料壞了或被誤刪時可以還原。
- **災難復原（DR, Disaster Recovery）**：當**整個機房／區域級**的大災難發生時，讓系統在另一個地方重新站起來的**整套計畫**。
- **RPO（Recovery Point Objective，復原點目標）**：你能接受**遺失多少時間的資料**。RPO = 1 小時，代表最糟會丟掉最近 1 小時的資料。
- **RTO（Recovery Time Objective，復原時間目標）**：你能接受**系統停機多久**。RTO = 2 小時，代表災難後最多 2 小時內要恢復服務。
- **快照（Snapshot）**：對硬碟（EBS）在某個時間點拍的「**存檔照片**」，可用來還原或複製硬碟。

</Vocab>

## 為什麼要做災難復原？（先懂「意義」再記策略）

很多人把 DR 當成「多花錢買保險」，考前死背四種策略卻說不出為什麼要選它。先把「意義」想通，後面策略自然記得住。

- **一次區域級災難，可能讓公司直接消失。** 不是機器重開就好——想像電商在雙十一當天，整個主區域（Region）停電好幾個小時：訂單進不來、金流斷掉、客服被灌爆。有研究估計，關鍵系統每停機 1 小時，中大型企業的損失動輒數萬到數十萬美元，還不算商譽與客戶流失。DR 要擋的就是這種「全毀」等級的事。
- **高可用（多 AZ）擋不住這種災難。** 多 AZ 是把機器分散在同一個 Region 的不同機房，擋得住「一間機房跳電」；但如果是**整個 Region**（天災、大規模斷電、海底電纜斷、設定爆炸連鎖）出事，多 AZ 的副本全在同一個 Region 裡，一起陪葬。DR 的核心動作因此是**跨 Region**——把命脈放到另一個地理位置。
- **DR 的本質是「花多少錢，換多快復原、少丟多少資料」。** 你不可能無限投錢，所以要先量化「能丟多少資料（RPO）」「能停多久（RTO）」，再挑一個剛好夠用、又付得起的策略。這就是下面整篇的主線。

<Analogy title="🏢 生活比喻：DR 就像幫重要資料買保險">

你不會為一支 100 元的隨身碟買保險，但會為「唯一一份客戶名單」想辦法多存幾份、放不同地方。DR 也一樣：**越重要、停了越痛的系統，越值得花錢買「快速復原」**；無關緊要的測試環境，壞了重建就好，不用砸錢。重點不是「要不要做 DR」，而是「每個系統各該做到哪個等級」。

</Analogy>

## 一句話先懂：RPO vs RTO

這是**整篇最常考**的一組觀念，用一條時間軸就懂：

```
        ← RPO（往回看，能丟多少資料）        → RTO（往前看，多久要復原）
  ───────┬──────────────────┬──────────────────────┬────────→ 時間
      上次備份            💥 災難發生              系統恢復服務
```

- **RPO 往「過去」看**：從災難點回推到「上一次備份」之間的資料會不見。**備份越頻繁，RPO 越小（丟得越少）。**
- **RTO 往「未來」看**：從災難發生到服務恢復要花多久。**架構越即時待命，RTO 越短（停機越短）。**

<Analogy title="🎮 生活比喻：打電動的存檔">

- **RPO** = 你「**多久存一次檔**」。每 5 分鐘存一次，主機當機最多重打 5 分鐘（丟 5 分鐘進度）。
- **RTO** = 當機後「**多久能重新開始玩**」。開機 30 秒就能繼續 = RTO 30 秒；要重灌遊戲 2 小時 = RTO 2 小時。

你想「幾乎不丟進度、而且秒開」當然最爽，但那要花更多錢（更頻繁存檔＋更好的設備）。DR 策略就是在這兩者和預算之間做選擇。

</Analogy>

## 四大災難復原策略（速度 vs 成本的取捨）

從「最便宜但最慢」到「最貴但最快」，由上往下排：

| 策略 | 白話 | 平時成本 | 復原速度（RTO） | 適合 |
| --- | --- | --- | --- | --- |
| **Backup & Restore**（備份還原） | 平時只存備份，災難後**從零重建** | 最低 | 最慢（數小時～數天） | 預算優先、可容忍較長停機 |
| **Pilot Light**（引導燈） | 核心（如資料庫）在他區**長期小火慢跑**，其餘災難時才開 | 低 | 較快（數十分鐘～數小時） | 關鍵資料要即時、其餘可快速拉起 |
| **Warm Standby**（溫備援） | 他區跑一套**縮小版、隨時運轉**的完整系統，災難時放大 | 中高 | 快（數分鐘） | 停機要很短的正式系統 |
| **Multi-Site Active/Active**（多站點雙活） | 兩區**同時全速運作**、同時服務流量 | 最高 | 幾乎零停機 | 不能停、要求最嚴苛 |

:::tip[💡 考試重點]
- 題目強調「**成本最低／預算有限**」又能接受較長復原 → **Backup & Restore**。
- 題目要「**幾乎零停機／最高可用／RTO 趨近 0**」→ **Multi-Site Active/Active**（其次 Warm Standby）。
- 看到 **RPO** → 問的是「**能丟多少資料**」→ 靠**備份頻率／複寫**解決。
- 看到 **RTO** → 問的是「**能停機多久**」→ 靠**待命架構的即時程度**解決。
- 「核心資料庫先在備援區小規模常態運行、其餘關機省錢」= **Pilot Light** 的招牌描述。
:::

### 四種策略逐一看：為什麼選它、優缺點、何時別用

上面那張表是速查，但考試常問「**為什麼這題要選 Pilot Light 而不是 Warm Standby**」。把四種策略各自的「招牌特徵」與取捨想清楚，才答得準。

#### 1. Backup & Restore（備份還原）— 最便宜、最慢

- **它在幹嘛**：平時什麼都不開，只固定把資料備份（快照、AWS Backup）並**複製到另一個 Region**。災難發生後，才在備援區**從零開始**：開機器、還原資料、接網路、切流量。
- **為什麼選它**：成本幾乎只有「備份存在 S3」的錢，是四種裡最省的。對「停機幾小時甚至一兩天也還好」的系統（內部報表、非即時批次、開發測試）綽綽有餘。
- **優點**：平時成本最低、架構最單純、幾乎零維運。
- **缺點**：RTO 最長（數小時～數天，看你要重建多少東西）；一切都要「現場重建」，出錯機率高，所以**更要演練**。
- **何時別用**：營收型、面向客戶、停一下就賠錢的系統——別為省那點錢換來幾小時停機。

#### 2. Pilot Light（引導燈）— 只讓「核心」長明

- **它在幹嘛**：名字來自瓦斯爐的「**長明小火**」。平時在備援區**只讓最關鍵、最難重建的部分長期小規模運轉**——通常是**資料庫**（持續把主區資料複寫過去）。其餘的應用伺服器平時**關著**，災難時才快速開起來、接上那顆早就同步好的資料庫。
- **為什麼選它**：資料庫是最花時間重建與同步的東西，讓它「永遠醒著」就省掉復原時最痛的一段；其餘無狀態的應用層開起來很快。用中等成本換到明顯更短的 RTO。
- **優點**：資料幾乎即時（RPO 小）、成本比 Warm Standby 低（應用層平時不開）。
- **缺點**：災難時仍要「把應用層拉起來並擴到正式規模」，RTO 還是有數十分鐘～數小時；架構比 Backup & Restore 複雜。
- **何時別用**：要求「幾分鐘內就好」的系統——應用層冷啟與擴容來不及，該升級到 Warm Standby。
- **招牌考題描述**：「**核心資料庫在 DR 區持續同步、其餘元件平時關閉以省錢**」= Pilot Light。

#### 3. Warm Standby（溫備援）— 整套都在跑，只是縮小版

- **它在幹嘛**：備援區跑一套**功能完整但規模縮小**的系統（例如正式用 10 台，這邊只開 1～2 台），**隨時都在運轉並接收資料**。災難時不用「開機」，只要**把規模放大（scale up/out）並把流量切過來**。
- **為什麼選它**：和 Pilot Light 最大差別是「**應用層也一直活著**」，所以不必等冷啟動，復原只剩「放大 + 切流量」，RTO 可壓到數分鐘。
- **優點**：RTO 短（數分鐘）、切換風險低（平時就在跑，等於天天在驗證備援環境可用）。
- **缺點**：平時要一直付「縮小版整套系統」的錢，比 Pilot Light 貴。
- **何時別用**：預算吃緊又能忍受數十分鐘停機（退回 Pilot Light）；或反過來，連幾分鐘都不能停（升到 Multi-Site）。

#### 4. Multi-Site Active/Active（多站點雙活）— 兩邊同時全速服務

- **它在幹嘛**：兩個（以上）Region **同時全規模運作、同時服務真實流量**，資料雙向／即時同步。某區掛掉時，流量自動全導到另一區，使用者幾乎無感。
- **為什麼選它**：這是唯一能做到「RTO／RPO 趨近 0」的等級——因為「備援區」本來就在正式服務，根本不存在「切換啟動」這段。
- **優點**：幾乎零停機、幾乎零資料遺失；平時兩區分攤流量還能順便就近服務各地使用者。
- **缺點**：**最貴**（養兩套全速環境）、**最複雜**（跨區資料一致性、衝突解決、流量路由都是硬功夫）。
- **何時別用**：絕大多數系統其實用不到——別為了帳面好看硬上雙活，把預算與團隊心力燒在不需要的地方。
- **招牌考題描述**：「**不能有任何停機 / 最高可用 / RTO 趨近 0**」= Multi-Site（其次 Warm Standby）。

:::info[🔑 一句話抓重點：四種策略其實是同一條軸上的四個刻度]
從 Backup & Restore → Pilot Light → Warm Standby → Multi-Site，一路上**平時成本越來越高、RTO／RPO 越來越小（越即時）**。你不是在「選一個最好的」，而是在「為這個系統選一個剛好夠用、又付得起」的刻度。選型口訣：**先問能丟多少（RPO）、能停多久（RTO），再看預算，往上找第一個同時滿足的策略**——能用便宜的就別用貴的。
:::

## 備份的實際工具

- **EBS 快照（Snapshot）**：對 EBS 硬碟拍存檔照片，**存放在 S3**（由 AWS 代管），而且是**增量備份**——第一次拍完整份，之後只存「有變動的部分」，省空間省錢。
- **AMI（Amazon Machine Image）**：把整台 EC2（含系統與資料）打包成映像檔，之後可一鍵開出一模一樣的新機器。
- **跨區域複寫（Cross-Region）**：把快照／備份**複製到另一個 Region**，才擋得住「整個區域級」災難——備份跟正本放同一區，那區全毀就一起陪葬。
- **AWS Backup**：一個**集中管理**所有備份的服務，用排程與政策統一備份 EBS、RDS、DynamoDB、EFS 等，不用每個服務各自設定。

## 實務應用：不只是考試

<Scenario title="真實情境：老闆問「機房燒掉怎麼辦？」">

你負責的系統資料都在東京區。老闆問：「如果東京整個區域出大事，我們多久能恢復？會丟多少訂單資料？」——這就是在問你的 **RTO 和 RPO**。你需要：(1) 定時對資料庫與硬碟做快照、(2) 把快照**複製到另一個 Region**、(3) 依預算選一種 DR 策略。下面先帶你做最基礎的 EBS 快照與跨區複製。

</Scenario>

### 🛠️ 動手做：建立 EBS 快照並複製到另一個區域

1. 主控台搜尋 `EC2` → 左側 **Elastic Block Store › 磁碟區（Volumes）**
2. 勾選要備份的磁碟區 → **動作 › 建立快照** → 加個描述 → 建立
3. 左側 **快照（Snapshots）** 看到剛建立的快照，狀態變 `completed`
4. 選該快照 → **動作 › 複製快照** → **目的地區域**選另一個 Region（例如從東京複到新加坡）→ 複製
5. 這樣即使東京整個區域出事，新加坡還有一份可還原

```bash
# 建立快照
$ aws ec2 create-snapshot --volume-id vol-0abc123 --description "db-backup"

# 把快照複製到另一個 Region（跨區異地備援的關鍵一步）
$ aws ec2 copy-snapshot --source-region ap-northeast-1 \
    --source-snapshot-id snap-0abc123 --region ap-southeast-1
```

**預期結果**：`create-snapshot` 會立刻回傳一包 JSON，裡面有新的 `SnapshotId`（像 `snap-0abc123`）、`State` 一開始是 `pending`；過幾分鐘再查 `aws ec2 describe-snapshots --snapshot-ids snap-0abc123`，`State` 變成 `completed`、`Progress` 到 `100%` 就代表好了。`copy-snapshot` 會回傳**目的地區域**的一個**新的** `SnapshotId`（跟來源不同），切到新加坡區的主控台 **Snapshots** 就能看到它。驗證重點：這份快照確實躺在**另一個 Region**，東京整區出事時它不受影響。

:::tip[💡 真的要「做一次還原演練」才算數]
備份複製完只是一半。**實際還原一次**才知道救不救得回來：用該快照「建立一個新的磁碟區（volume）或直接啟動一台新 EC2」，開機進去確認資料完整、服務起得來、步驟文件寫得對。把這個還原演練**排進行事曆定期做**（例如每季一次），並記錄從「宣告災難」到「服務恢復」花了多久——這個實測時間，就是你真正的 RTO。
:::

<Cost>

**策略越即時待命，平時的帳單越貴**：Backup & Restore 平時幾乎只付「快照存在 S3」的錢（最便宜）；Multi-Site 則要長期養兩套全速運作的環境（最貴）。快照是增量的、只存變動量，相對便宜；但**跨區複製的資料傳輸與另一區的儲存會額外計費**。別為了省小錢而不跨區——那等於沒有災難復原能力。

</Cost>

:::warning[🚑 常踩雷]
- **只備份、從來不演練還原（最致命）**：備份檔案損毀、權限不對、或還原步驟沒人會做，等真的出事才發現「救不回來」——**沒測過還原的備份，等於沒有備份**。一定要定期做還原演練，並記下實測復原時間。
- **把 RPO 和 RTO 搞混**：這是考試與面試最常被電的地方。**RPO = 能丟多少「資料」（往過去看、看備份頻率）；RTO = 能停多久「服務」（往未來看、看架構即時程度）**。記法：R**P**O 的 P 是 **Point（資料的點）**、R**T**O 的 T 是 **Time（停機的時間）**。
- **快照跟正本放同一個 Region**：那個 Region 整個掛掉時，備份也一起沒了。**DR 一定要跨 Region。**
- **只跨區、沒跨帳號**：帳號被盜、憑證外洩、或有人（或勒索軟體）把整個帳號的快照刪光時，同帳號裡的備份照樣一起沒。重要備份應**複製到另一個 AWS 帳號**（或用 AWS Backup 的 Vault Lock／跨帳號備份），做到「連自己人誤刪或被攻破也救得回」。
- **快照沒加密**：含客戶資料、個資的快照若沒開 EBS 加密，複製到別區／別帳號時等於把明文資料攤開，審計與合規（如個資法）會出事。**建快照前先讓來源磁碟區啟用加密**；`copy-snapshot` 時也可用 `--encrypted --kms-key-id` 在複製當下加密，且**加密快照無法被改回未加密**。
- **把高可用當成災難復原**：多 AZ 只能擋「單一機房」故障，擋不了「整個區域」級災難，兩者要分開規劃。
- **RPO／RTO 定得太嚴卻不給預算**：要求「零丟失、秒復原」就得用 Multi-Site，成本最高，要先對齊預算。
:::
