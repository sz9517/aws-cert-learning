# ELB：幫你的網站「自動分流、不怕某台當機」

> 本篇帶你搞懂三種負載平衡器（ALB／NLB／GWLB）怎麼選，這是 Domain 2 高可用架構裡最常考的選型題。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **負載平衡器（Load Balancer）**：站在使用者和你後端伺服器「**中間的櫃台**」，把湧進來的流量平均分給後面每一台伺服器。
- **可用區（AZ, Availability Zone）**：同一個區域（Region）裡**實體分開的機房**。一個 AZ 停電，另一個 AZ 還能照常運作。
- **目標群組（Target Group）**：負載平衡器後面「**一群要收流量的伺服器**」的名單（可以是 EC2、IP 或 Lambda）。
- **健康檢查（Health Check）**：負載平衡器定期「**敲門問還活著嗎？**」，壞掉的伺服器就不再分流量給它。

</Vocab>

## 為什麼需要它？先講一個會出事的例子

假設你的購物網站只跑在**一台** EC2 上。雙十一流量暴增，這台扛不住就當機，全站掛掉；就算流量正常，哪天這台所在的機房（AZ）停電，網站一樣全黑。

解法是：**開多台 EC2、分散在不同 AZ**，前面擺一個<Term en="Elastic Load Balancing" desc="站在使用者和後端伺服器中間，自動把流量平均分給多台伺服器的服務。">ELB</Term>當櫃台。使用者只連到 ELB，ELB 再把每一筆請求分給還活著的伺服器。某台掛了、某個 AZ 停電，ELB 自動跳過它——使用者完全無感。這就是「高可用」。

## 一句話先懂 ELB

**ELB（Elastic Load Balancing）** 自動把進來的流量分散到多台後端，並透過**健康檢查**只把流量送給正常的目標，是 AWS 達成高可用與水平擴展的入口。

<Analogy title="🏢 生活比喻：把 ELB 想成餐廳門口的帶位員">

- **帶位員（ELB）** 站在門口，客人一來就帶到「目前有空、服務正常」的桌子。
- **多張桌子（多台 EC2）** 分散在不同包廂（不同 AZ），一間包廂冷氣壞了，帶位員就不往那帶。
- **巡桌確認（健康檢查）**：帶位員定時去看每桌狀況，桌子出問題就暫時不帶客人過去。
- 客人全程只認「門口的帶位員」，完全不用知道自己被帶到第幾桌——這就是 ELB 幫你隱藏後端細節。

</Analogy>

## 三種負載平衡器怎麼選（最重要的一張表）

| 類型 | 運作層級 | 看得懂什麼 | 最適合 | 固定 IP |
| --- | --- | --- | --- | --- |
| **ALB**（Application LB） | 第 7 層（應用層） | HTTP／HTTPS、網址路徑、主機名稱 | 一般網站、API、微服務（依路徑/網域分流） | ❌（給 DNS 名稱） |
| **NLB**（Network LB） | 第 4 層（傳輸層） | TCP／UDP、連線 | 極高效能、低延遲、遊戲/金融、需要固定 IP | ✅（每個 AZ 一個靜態/彈性 IP） |
| **GWLB**（Gateway LB） | 第 3/4 層 | IP 封包 | 串接第三方**網路資安設備**（防火牆、IDS/IPS） | — |

<Term en="Application Load Balancer" desc="第 7 層負載平衡器，看得懂 HTTP，可依網址路徑或主機名稱分流。">ALB</Term> 的強項是「**聰明分流**」：`/api/*` 送到 API 伺服器、`/images/*` 送到圖片伺服器，或依網域把 `shop.example.com` 和 `blog.example.com` 分開。<Term en="Network Load Balancer" desc="第 4 層負載平衡器，處理 TCP/UDP，效能極高、延遲極低，可提供固定 IP。">NLB</Term> 不看內容、只看連線，所以**快到可以處理每秒數百萬請求**，而且能給你**靜態 IP**。

## 為什麼要負載平衡？（高可用到底在講什麼）

很多人背「ELB = 分流」，但不懂**為什麼非它不可**。白話講，負載平衡一次解決三件單台伺服器做不到的事：

- **高可用（High Availability）**：單台機器一定會壞——不是程式當掉就是機房（AZ）停電。ELB 把流量分散到**不同 AZ 的多台**，任何一台或一整個 AZ 掛掉，ELB 靠**健康檢查**自動跳過它，使用者完全無感。這就是「高可用」的具體意義：**不是不會壞，而是壞了也不中斷服務。**
- **水平擴展（Horizontal Scaling）**：流量變大時，與其把單台機器換更貴的（垂直擴展，有上限且要停機），不如**多開幾台一樣的機器**掛到 ELB 後面（水平擴展）。ELB 是水平擴展的入口，常和 **Auto Scaling** 搭配——流量高自動加機器、流量低自動減機器。
- **隱藏後端細節**：使用者只連「ELB 的一個位址」，後面有幾台、換了哪台、哪台在修，使用者都不用知道。你可以在背後滾動更新、替換故障機器，前台零感知。

:::info[🔑 一個容易混的觀念：負載平衡 ≠ 自動擴展]
ELB 負責「把流量**分給**現有的健康機器」，但它**自己不會新增或移除機器**。真正「流量大就加機器、流量小就減機器」的是 **Auto Scaling**。考試常把兩者綁在一起：**ELB（分流）+ Auto Scaling（自動增減）+ 多 AZ** 才是完整的高可用彈性架構。
:::

## ALB vs NLB vs GWLB：為什麼選誰、何時用哪個

上面那張表是速查；這一段把三者的**取捨**講清楚，考試的「選型題」靠的就是這個。

### ALB（第 7 層 / 應用層）—— 一般網站與 API 的預設首選

- **為什麼選它**：它**看得懂 HTTP/HTTPS 的內容**，所以能做「聰明的事」：依網址路徑（`/api`、`/images`）或主機名稱（`shop.` vs `blog.`）分流、把 HTTPS 憑證掛在上面統一解密、依 HTTP 標頭／查詢字串做規則、原生支援 WebSocket 與重新導向。目標可以是 EC2、IP，甚至 **Lambda**。
- **優點**：功能最豐富、最適合微服務與容器（ECS/EKS）；憑證集中管理；請求層級的細緻分流與記錄。
- **缺點／限制**：只處理 HTTP/HTTPS（**不能**跑純 TCP/UDP）；因為要解析第 7 層內容，**延遲比 NLB 高**、每秒處理量不如 NLB；**沒有固定 IP**，只給你一個 DNS 名稱。
- **何時別用**：需要**固定／靜態 IP**、**極低延遲**、**每秒數百萬連線**、或要跑 **非 HTTP 協定**（遊戲、MQTT、資料庫連線）時——這些都該換 NLB。

### NLB（第 4 層 / 傳輸層）—— 要快、要固定 IP、要跑非 HTTP

- **為什麼選它**：它**只看連線（TCP/UDP），不解析內容**，所以又快又輕，延遲極低、能扛每秒數百萬請求；而且**每個 AZ 給你一個靜態 IP（可綁彈性 IP）**，這是 ALB 做不到的。
- **優點**：效能／延遲天花板最高；有固定 IP（適合**防火牆白名單**或對方只肯放行特定 IP 的情境）；原生支援 TCP/UDP 與 TLS 直通。
- **缺點／限制**：**看不懂 HTTP 內容**，沒有依路徑／主機名稱分流、沒有 WebSocket 感知等第 7 層功能；要做內容分流就得自己在後端處理。
- **何時別用**：你只是要架一般網站／REST API、想依路徑或網域分流、想把憑證掛在 LB 上統一管理——這些 **ALB 更省事**，不必為了「聽起來比較快」硬上 NLB。

### GWLB（第 3/4 層）—— 專門串接第三方資安「虛擬設備」

- **為什麼選它**：它**不是拿來服務一般使用者流量的**，而是把流量**透明地導流**去經過第三方的**虛擬網路設備**（防火牆、IDS/IPS、深度封包檢測），檢查完再送回原路。你可以在不改變現有路由架構的前提下，把一排資安設備「串」進流量路徑。
- **優點**：集中部署與擴展第三方資安設備；用 GENEVE 協定把流量封裝轉送，設備進出一個位址即可。
- **缺點／限制**：用途很窄，一般應用根本用不到；要搭配會跑在它後面的資安設備廠商方案。
- **何時用（考試關鍵字）**：題目一出現「**第三方防火牆／入侵偵測／流量檢測設備**」「**透明地讓流量先過安全設備**」，答案幾乎都是 **GWLB**。

<Scenario title="真實情境：同一個團隊，三種需求各該選誰">

- 「我們是電商網站，`/api` 要給後端服務、`/` 給前端，還要掛 HTTPS 憑證」→ **ALB**（第 7 層分流 + 憑證）。
- 「我們做線上遊戲／即時語音，要 UDP、延遲越低越好，而且合作方的防火牆只肯放行**固定 IP**」→ **NLB**（第 4 層 + 靜態 IP）。
- 「資安團隊要求所有進出流量都先經過我們買的第三方防火牆設備」→ **GWLB**（串接虛擬資安設備）。

</Scenario>

:::tip[💡 考試重點]
看到關鍵字直接對應，幾乎是送分：
- 題目講 **HTTP／HTTPS、依路徑或網域分流、微服務** → **ALB**
- 題目講 **TCP/UDP、超高效能、超低延遲、需要「固定／靜態 IP」或「白名單 IP」** → **NLB**
- 題目講 **串接第三方防火牆／入侵偵測設備** → **GWLB**
- 題目講 **要同時用到多個 AZ 達成高可用** → ELB 一定要在**建立時勾選 ≥ 2 個 AZ**（最常被忽略的設定）
:::

## 實務應用：不只是考試

<Scenario title="真實情境：你的 API 三不五時就有人回報『連不上』">

查了半天發現：你只開一台 EC2 跑 API，部署新版本重啟的那幾秒、或機器偶發當機，使用者就斷線。老闆要求「**部署不要再斷線、單台掛掉要自動頂上**」。——答案就是：多台 EC2 分散 AZ + 前面掛一個 ALB，健康檢查自動把流量導到正常的機器。下面帶你做一次。

</Scenario>

### 🛠️ 動手做：建立一個橫跨兩個 AZ 的 ALB

1. 先在**兩個不同 AZ** 各開一台 EC2（例如 `ap-northeast-1a` 與 `1c`），都裝好同一個網站。
2. AWS 主控台搜尋 `EC2` → 左側 **目標群組（Target Groups）** → **建立目標群組**，類型選 `Instances`，把兩台 EC2 都加進去，健康檢查路徑填 `/health`（或 `/`）。
3. 左側 **負載平衡器（Load Balancers）** → **建立 Application Load Balancer**。
4. **網路對應**：勾選**至少兩個 AZ**（這步就是高可用的關鍵！）。
5. **監聽器（Listener）**：`HTTP:80` → 轉送到剛剛的目標群組。建立。
6. 建好後複製 ALB 的 DNS 名稱貼到瀏覽器，重整幾次會分流到不同機器。接著手動把一台 EC2 關機，網站**依然正常**——流量自動全導到另一台。

```bash
# 查看目標群組健康狀態，壞掉的目標會顯示 unhealthy
$ aws elbv2 describe-target-health \
    --target-group-arn <你的目標群組ARN>
```

**預期結果**：剛掛上去時目標會是 `initial`，通過幾次健康檢查後轉成 `healthy`；你手動關掉其中一台後，再查這個指令，那台會變成 `unhealthy`，而瀏覽器重整**完全不會連到那台**（ELB 自動跳過），網站照常。

### 🛠️ 進階：幫 ALB 掛 HTTPS 憑證（最常見的正式需求）

正式網站幾乎都要 HTTPS。做法是**把憑證掛在 ALB 上**，由 ALB 統一解密後再用 HTTP 轉給後端（後端不必各自管憑證）：

1. 到 **AWS Certificate Manager（ACM）** 申請或匯入你網域的憑證（ACM 公有憑證免費、可自動續約）。
2. 在 ALB 新增一個 **`HTTPS:443` 監聽器**，選剛剛那張 ACM 憑證，轉送到目標群組。
3. 再把原本的 **`HTTP:80` 監聽器改成「重新導向到 HTTPS:443」**，讓所有人自動升級到加密連線。

**預期結果**：瀏覽器開 `https://你的網域` 會看到鎖頭、無憑證警告；開 `http://` 會被自動轉到 `https://`。
> ⚠️ 憑證要掛在 **ALB** 上（NLB 若要卸載 TLS 走的是 TLS 監聽器，設定不同）；ACM 憑證**所在區域必須和 ALB 同一區**，否則監聽器裡選不到那張憑證。

### 🛠️ 需要「同一使用者固定連到同一台」？開黏性 Session

購物車、登入狀態若存在單台伺服器的記憶體裡，使用者下一個請求被分到別台就會「被登出／購物車空了」。ALB 的**黏性 Session（Sticky Sessions）**會用 cookie 把同一使用者固定綁到同一台目標：在目標群組的 **Attributes** 開啟 `Stickiness`，選 ALB 產生的 cookie 並設有效期。
> 但更好的做法是**讓後端無狀態**（session 放 ElastiCache／DynamoDB），這樣任何一台都能服務任何使用者，黏性就不再需要——這也是考試偏好的「正解方向」。

<Cost>

ALB／NLB 本身**按小時 + 流量（LCU）計費**，不是免費；但相較於「全站掛掉的損失」非常划算。練習完記得**刪掉 ALB 與測試用 EC2**。EC2 用 Free Tier 的 `t2.micro`，ALB 沒有免費額度，用完就刪最保險。

</Cost>

:::warning[🚑 常踩雷]
- **只掛一個 AZ**：那就失去高可用的意義了，單一 AZ 停電照樣全掛。ELB 一定要跨 ≥ 2 個 AZ。
- **健康檢查路徑設錯**：填了一個會回 404 的路徑（或填了要登入才看得到的頁），結果**所有目標都被判定 unhealthy**，ELB 直接回 **503 Service Unavailable**。健康檢查路徑要選一個「不需驗證、輕量、永遠回 200」的端點（常做一個 `/health`）。
- **忘了開跨區負載平衡（Cross-Zone Load Balancing）**：關閉時，流量**先平均分到各 AZ**，再由各 AZ 內部分給自己的目標——若各 AZ 的機器數量不一樣，就會**分不均**（機器少的那區每台被打爆）。**ALB 預設開啟且免費**；**NLB 預設關閉**，要手動開（NLB 跨區傳輸可能另計跨 AZ 流量費）。看到「各 AZ 機器數不同卻想平均分攤」就想到它。
- **黏性 Session（Sticky Session）用錯地方**：開了黏性就是「同一人固定連同一台」，那台一掛，綁在它上面的使用者 session 直接消失；而且會造成**分流不均**。正解方向是**讓後端無狀態**（session 外放 ElastiCache／DynamoDB），非不得已才開黏性。
- **需要固定 IP 卻用了 ALB**：ALB **只給 DNS 名稱、IP 會變**。對方防火牆要你提供「可白名單的固定 IP」時，必須改用 **NLB**（每個 AZ 一個靜態／彈性 IP）。
- **HTTPS 憑證掛錯地方或跨區**：要在 LB 卸載 TLS 時，憑證掛在 **ALB 的 HTTPS 監聽器**（或 NLB 的 TLS 監聽器）；且 **ACM 憑證必須與 LB 同一個區域**，否則監聽器選不到憑證、建立失敗。
- **Security Group 沒放行**：後端 EC2 的 SG 要允許來自「ELB 的 SG」的流量，否則健康檢查永遠失敗。
- **誤用 ALB 處理純 TCP 遊戲流量**：需要超低延遲或固定 IP 時應選 NLB。
:::
