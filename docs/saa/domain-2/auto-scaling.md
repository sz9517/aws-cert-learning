# Auto Scaling：讓伺服器數量「自動增減」

> 本篇教你怎麼讓系統在尖峰自動加機器、離峰自動關機器，是 Domain 2（彈性）最核心的考點之一。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **EC2（Elastic Compute Cloud）**：AWS 上「租來的一台伺服器」，你的網站或程式跑在它上面。
- **執行個體（Instance）**：一台正在運行的 EC2，就是「一台機器」。
- **CPU 使用率**：機器有多忙的指標，愈接近 100% 代表快撐不住了。
- **AZ（Availability Zone，可用區）**：同一個地區（Region）裡「彼此獨立的機房」，一個壞了另一個還在。

</Vocab>

## 為什麼需要 Auto Scaling？

想像你開一家手搖飲店：

- **平日下午**客人稀稀落落，排 1 位店員就夠了。
- **週末放學時段**人潮爆滿，只排 1 位店員會大排長龍、客人跑光。
- 但如果你為了週末「永遠排 5 位店員」，平日就在**付錢給發呆的員工**。

伺服器也一樣。流量有尖峰、有離峰，如果固定開一堆機器，離峰時就是在燒錢；如果只開一兩台，尖峰一來就被流量打垮。**Auto Scaling 就是幫你「客人多就自動加人、客人少就自動遣散」**，兼顧穩定與省錢。

### 不就是「手動開關機器」就好了嗎？為什麼非得用 ASG？

你當然可以自己盯著儀表板，尖峰來了手動多開幾台、離峰了再手動關掉。但實務上這幾乎行不通，這也是 ASG 存在的理由：

| 項目 | 手動開關機器 | 用 ASG |
| --- | --- | --- |
| **反應速度** | 尖峰是半夜突然來的，等你醒來看到警報、登入開機，服務早就掛了好幾分鐘 | CloudWatch 一偵測到指標超標，**幾十秒內自動**開機，不用人在場 |
| **機器掛掉怎麼辦** | 得有人發現、手動補一台 | ASG **自動偵測不健康並補一台**（自我修復） |
| **半夜 / 假日** | 沒人值班就沒人處理 | 24 小時自動運作，不用排班 |
| **會不會手滑** | 手動容易開錯機型、忘了掛負載平衡器、關錯台 | 一切照**啟動範本**與策略走，結果可預期 |
| **省錢** | 離峰常常忘了關、或懶得關，一直燒錢 | 離峰**自動縮減**，不用記得去關 |

:::info[🔑 一句話抓重點]
ASG 把「要不要加減機器、加減幾台、怎麼加」這件事，從**靠人判斷＋手動操作**，變成**靠指標自動執行**。它真正賣的不是「省錢」，而是「**不用人盯著、還能自我修復**」——省錢只是順便。
:::

## 一句話先懂 Auto Scaling

**EC2 Auto Scaling** 會根據你設定的條件（例如 CPU 太高）**自動增加或減少 EC2 執行個體的數量**，讓系統永遠維持「剛剛好」的運算量。

<Analogy title="🍢 生活比喻：手搖飲店的彈性排班">

- **Auto Scaling Group（ASG，自動擴展群組）** = 這家店的「排班制度」，負責決定現在該有幾個店員。
- **Launch Template（啟動範本）** = 「新店員的標準訓練手冊」，規定每位新進店員（新機器）用什麼機型、什麼系統映像、掛哪個安全群組。
- **最小 / 期望 / 最大容量** = 「最少留幾人、平常排幾人、最多能加到幾人」。
- **擴展策略（Scaling Policy）** = 「什麼情況要加人、什麼情況可以放人回家」的規則。

</Analogy>

## 三個關鍵容量參數

這是**考試最愛考的細節**，一定要分清楚：

| 參數 | 意思 | 舉例 |
| --- | --- | --- |
| **最小容量（Minimum）** | 無論多離峰，至少保留幾台（守住底線） | 2 |
| **期望容量（Desired）** | 平常想維持的台數，ASG 會努力湊到這個數字 | 2 |
| **最大容量（Maximum）** | 再怎麼尖峰也不會超過幾台（守住荷包上限） | 10 |

:::tip[💡 考試重點]
- ASG 會**持續把實際台數拉回「期望容量」**；若一台機器掛了，ASG 會自動補一台到期望數。
- 設 `min=2` 且分散在**兩個以上 AZ**，就算整個 AZ 掛掉，另一個 AZ 仍有機器 → 這就是「高可用」。
- **擴展（Scale out）＝加機器**；**縮減（Scale in）＝關機器**。注意不要和「垂直擴充（換更大台）」搞混，ASG 做的是**水平擴展**。
:::

## 三種擴展策略，怎麼選？

| 策略 | 怎麼運作 | 什麼時候用 |
| --- | --- | --- |
| **目標追蹤（Target Tracking）** | 你只設一個目標值（例如平均 CPU 維持 50%），AWS 自動加減機器去逼近它 | **最常用、最省心**，考試預設首選 |
| **階梯式（Step Scaling）** | 依指標超標的「幅度」分級加機器（例：CPU>60% 加 1 台、>80% 加 3 台） | 需要更精細控制擴展幅度時 |
| **排程式（Scheduled）** | 按「時間表」預先加減（例：每天 18:00 先加到 6 台） | **可預測**的尖峰，例如每天下班時段、電商檔期 |

:::tip[💡 考試重點]
題目若說「**想維持某個指標在固定水準**、設定愈簡單愈好」→ 選 **目標追蹤（Target Tracking）**。
題目若說「**流量尖峰時間固定可預測**（例如每天早上 9 點）」→ 選 **排程式（Scheduled）**。
還有一種 **預測式擴展（Predictive Scaling）**：用機器學習看歷史流量，**提前**把機器準備好，適合週期性、可預測的負載。
:::

### 動態 vs 排程 vs 預測式，到底怎麼選？（白話版）

這三種其實是在回答不同的問題，先用一句話分清楚：

- **動態擴展（Dynamic）= 看「現在」**：依即時指標（CPU、請求數）**事後反應**。包含「目標追蹤」與「階梯式」兩種。
- **排程擴展（Scheduled）= 看「時鐘」**：你早就知道幾點會忙，**時間到就先加好**，完全不看指標。
- **預測式擴展（Predictive）= 看「歷史規律」**：AWS 用機器學習從過去幾週的流量，**預測明天**幾點會忙，**提前**暖機。

| 類型 | 好處 | 壞處 / 限制 | 什麼時候用它 |
| --- | --- | --- | --- |
| **動態（目標追蹤 / 階梯）** | 不用預測，流量怎麼變都跟得上；設定直覺 | **是「事後反應」**：指標先飆高、機器才開，而新機器開機＋通過健康檢查要幾分鐘，這段空窗期可能先卡一下 | 流量**沒有固定規律**、說來就來（突發社群分享、不可預期的尖峰） |
| **排程（Scheduled）** | **提前**把機器備好，尖峰一到就滿血，沒有開機空窗 | 你得**自己知道**尖峰時間；時間寫死，臨時提早或延後的尖峰它幫不上 | 尖峰時間**固定可預測**（每天 09:00 上班、週五晚上、電商檔期開賣） |
| **預測式（Predictive）** | 兼顧前兩者：**自動學**出規律並提前暖機，不用你手動排時間 | 需要**累積約兩週的歷史資料**才準；只適合**有週期規律**的負載，對全新或無規律流量沒用 | 流量**有規律但你懶得手動排**，或想讓 AWS 自動抓出每日/每週節奏 |

:::tip[💡 考試重點：三種擴展的關鍵字對照]
- 題幹出現「**即時 / 依目前 CPU / 無法預測何時尖峰**」→ **動態（通常選目標追蹤）**。
- 題幹出現「**每天固定時間 / 已知的尖峰時段 / cron**」→ **排程式**。
- 題幹出現「**週期性且想在尖峰前先備好機器 / 用歷史資料預測**」→ **預測式**。
- 三者**可以疊用**：平常用目標追蹤兜底、已知大檔期加排程先暖機，這在真實架構很常見（本篇情境就是這樣做）。
:::

### 目標追蹤 vs 階梯式，取捨在哪？

兩者都是「動態擴展」，但控制方式不同，考試很愛讓你二選一：

| 面向 | 目標追蹤（Target Tracking） | 階梯式（Step Scaling） |
| --- | --- | --- |
| **你要設什麼** | 只設**一個目標值**（CPU 維持 50%），其餘交給 AWS | 自己設**多段門檻與對應動作**（>60% 加 1、>80% 加 3） |
| **像什麼** | 像冷氣的**溫控**：設定 25 度，它自己調 | 像手動**分段開關**：你規定每一段該做什麼 |
| **好處** | 最省心、最不會設錯，官方與考試**預設首選** | 可依「超標幅度」做**不同力道**的反應，更精細 |
| **壞處 / 限制** | 幅度由 AWS 決定，你較難精細控制 | 要自己調門檻，**設不好反而抖動**或反應不足 |

:::info[🔑 怎麼選一句話]
**先用目標追蹤**（九成情況夠用且最安全）；只有當「不同超標程度要用不同力道加機器」這種精細需求出現時，才考慮階梯式。考題若沒特別強調精細分級，答案幾乎都是**目標追蹤**。
:::

## ASG 怎麼和 ELB、健康檢查合作？

ASG 很少單獨出現，它和 <Term en="Elastic Load Balancing" desc="彈性負載平衡器，把流量平均分給後面多台機器。">ELB</Term> 是黃金搭檔：

- ASG 新開的機器會**自動註冊**到 ELB，立刻開始分擔流量；縮減時也會先從 ELB 取消註冊再關機。
- ASG 可改用 **ELB 健康檢查**：當某台機器被 ELB 判定「不健康」（例如回應逾時），ASG 會**自動終止它並補一台新的**——這就是系統「自我修復」的關鍵。

:::warning[🚑 常踩雷：健康檢查型態一定要改成 ELB]
ASG 預設只做 **EC2 健康檢查**——它只看「這台機器的底層有沒有活著」（開機、系統狀態檢查有沒有過）。問題是：**機器開著、但上面的網站應用程式當掉了**（例如 Web 服務 crash、一直回 500），EC2 檢查照樣判它「健康」，流量繼續被導進這台壞掉的機器。

正解是把 ASG 的健康檢查型態設成 **ELB（`ELB` health check type）**，讓它改看「負載平衡器能不能正常打通應用層」。這樣應用程式層一掛，ASG 才會**真的把它換掉**。考題只要出現「機器還活著但服務沒回應、ASG 卻不換機器」，答案八成就是**健康檢查沒設成 ELB 型**。
:::

老闆抱怨：「平常好好的，一到週年慶首頁就打不開，但我又不想整年都開 10 台機器燒錢。」你的答案就是這篇：把網站放進 **ASG（min=2, max=10）**、用**目標追蹤把 CPU 維持在 50%**，再對週年慶當天加一條**排程式**先暖機。下面帶你做一次基本設定。

</Scenario>

### 🛠️ 動手做：建立一個 CPU 目標追蹤的 ASG

1. 登入 AWS 主控台 → 搜尋 `EC2` → 左側選單找到 **啟動範本（Launch Templates）** → **建立啟動範本**
2. 選好 AMI（系統映像，例如 Amazon Linux）、機型 `t2.micro`、安全群組 → 建立
3. 左側選單點 **Auto Scaling 群組** → **建立 Auto Scaling 群組** → 選剛剛的啟動範本
4. 網路步驟**勾選兩個以上的子網路（分屬不同 AZ）**，讓機器跨 AZ 分散
5. 容量設定：**最小 2、期望 2、最大 10**
6. 擴展策略選 **目標追蹤**，指標選 **平均 CPU 使用率**，目標值填 **50**
7. 建立完成。可用壓力測試工具灌流量，觀察機器數量自動往上長：

```bash
# 查看目前 ASG 裡有幾台機器、分別在哪個 AZ
$ aws autoscaling describe-auto-scaling-groups \
    --auto-scaling-group-names my-web-asg \
    --query "AutoScalingGroups[0].Instances[].{Id:InstanceId,AZ:AvailabilityZone,State:LifecycleState}"
```

**預期結果**：剛建好、流量還低時，你會看到**兩台**機器（因為期望容量 = 2），分散在兩個 AZ、狀態都是 `InService`：

```json
[
  {"Id": "i-0a1b2c3d", "AZ": "ap-northeast-1a", "State": "InService"},
  {"Id": "i-0e4f5g6h", "AZ": "ap-northeast-1c", "State": "InService"}
]
```

灌入壓力測試、CPU 衝破 50% 幾分鐘後再查一次，就會看到清單變多（例如 4～6 台），而且有些是 `Pending`（正在開機、還沒接流量）。流量退去後，機器會慢慢被標成 `Terminating` 直到縮回期望容量。

### 🛠️ 進階：改用「階梯式」策略，按超標幅度分段加機器

如果你要的是「CPU 稍微高加一點、爆高就狠狠加」，就用階梯式。做法是先建一條綁 CloudWatch 警報的 `StepScaling` 策略：

```bash
# 建立一條階梯式擴展策略：以「CPU 相對 50% 的超標幅度」分段加機器
# 0~20（即 CPU 50~70%）加 1 台；20 以上（CPU >70%）加 3 台
$ aws autoscaling put-scaling-policy \
    --auto-scaling-group-name my-web-asg \
    --policy-name cpu-step-out \
    --policy-type StepScaling \
    --adjustment-type ChangeInCapacity \
    --metric-aggregation-type Average \
    --step-adjustments \
        MetricIntervalLowerBound=0,MetricIntervalUpperBound=20,ScalingAdjustment=1 \
        MetricIntervalLowerBound=20,ScalingAdjustment=3
```

**預期結果**：指令會回傳這條策略的 `PolicyARN`。接著你把這個 ARN 設成某個 CloudWatch「CPU > 50%」警報的動作，之後 CPU 落在哪一段，ASG 就加對應台數。查警報狀態確認它真的在跑：

```bash
$ aws cloudwatch describe-alarms --alarm-names high-cpu \
    --query "MetricAlarms[0].{State:StateValue,Actions:AlarmActions}"
# 正常會看到 State 在 OK / ALARM 之間切換；ALARM 時就會觸發上面的策略加機器
```

:::info[🔑 兩種動態策略別混用在同一指標]
同一個指標（如平均 CPU）**不要同時**掛目標追蹤又掛階梯式，兩套邏輯會互相打架、造成忽加忽減。要嘛整組用目標追蹤，要嘛整組用階梯式。
:::

<Cost>

Auto Scaling 這個**服務本身免費**，你只要付「實際開出來的 EC2」費用。它真正的省錢價值在於**離峰自動縮減**——不用整天養一堆閒置機器。練習完記得把 ASG 的**期望/最大容量調成 0 或直接刪除 ASG**，否則它會一直幫你維持機器而持續計費。善用 **Free Tier** 的 `t2.micro`。

</Cost>

:::warning[🚑 常踩雷]
- **只放在單一 AZ**：那個 AZ 一掛，整個服務跟著掛，等於沒做到高可用。永遠跨至少 2 個 AZ。
- **健康檢查沒設成 ELB 型**：預設的 EC2 檢查看不到「機器活著但應用程式當掉」，壞機器會一直收流量。對掛在負載平衡器後面的服務，把型態改成 **ELB**（詳見上面的健康檢查段）。
- **最大容量設太小**：尖峰時想加機器卻卡在上限，照樣被打垮。反過來**最大設太大**又可能被突發流量（或被攻擊）拖著無限加機器、帳單爆炸——記得搭配預算告警。
- **min / max / desired 設錯**：三者有「`min ≤ desired ≤ max`」的隱含關係。常見災情是 **`desired` 不小心設得比實際需要高**（例如手滑設 10），ASG 就會乖乖幫你長到 10 台一直計費；或 **`min` 設太高**，離峰想省錢卻怎麼也縮不下去（ASG 會守住 min 的底線不往下砍）。
- **冷卻時間（Cooldown）沒設好**：剛加完機器、指標還沒反應，系統又急著再加一批，造成「忽多忽少」的抖動。給它一點緩衝時間讓新機器先發揮作用。
- **縮容太快、砍到還在服務的機器**：縮減（scale in）若太積極，流量只是短暫回落就急著關機，結果流量又上來、剛關的機器白關了；更糟的是**直接終止還有使用者連線在上面的機器**造成請求被切斷。對應解法：用**連線耗盡 / 連線排除（deregistration delay）**讓機器關機前先把現有連線處理完，並對縮容設合理的冷卻，必要時用**執行個體保護（instance scale-in protection）**保住關鍵機器不被縮容選中。
- **把擴展當成修 Bug 的方法**：程式本身有記憶體洩漏，加再多機器也只是延後崩潰、多燒錢。
