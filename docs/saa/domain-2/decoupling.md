# 解耦架構：讓系統「一個壞掉，其他照跑」

> 本篇教你用 SQS 與 SNS 把系統拆開，這是 Domain 2（彈性）最愛考的題型之一。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **緊耦合（Tightly Coupled）**：A 直接呼叫 B，B 一掛掉 A 就跟著卡住或報錯，像兩個齒輪死死咬在一起。
- **解耦（Decoupling）**：在 A 和 B 中間放一個「緩衝」，就算 B 暫時掛了，訊息也先存著不會掉，B 好了再慢慢處理。
- **SQS（Simple Queue Service）**：AWS 的「**訊息佇列**」，像一個**排隊的信箱**，發送方丟訊息進去，接收方自己來「拉」出來處理。
- **SNS（Simple Notification Service）**：AWS 的「**通知／廣播服務**」，像一個**群組公告**，一則訊息同時「推」給所有訂閱者。

</Vocab>

## 一句話先懂「為什麼要解耦」

<Scenario title="真實情境：購物網站大特賣當機了">

你的下單流程是「網頁 → 直接呼叫 → 處理訂單的伺服器」。平常沒事，但雙 11 瞬間湧入 10 倍流量，處理訂單的伺服器被塞爆、整個掛掉，**連帶讓前面的網頁也卡住，客人連「加入購物車」都做不了**。這就是緊耦合的惡夢：一個環節壞，全線崩。

</Scenario>

**解法**：在中間放一個 <Term en="Simple Queue Service" desc="AWS 的訊息佇列，像排隊的信箱，發送方丟訊息、接收方自己拉出來處理。">SQS</Term> 佇列。網頁只要把訂單「丟進佇列」就立刻回覆客人「已收到」，後面的伺服器再依自己的速度慢慢拉出來處理。流量暴衝時，佇列會幫你**把尖峰的水量先存起來**，伺服器不會被沖垮。這招叫 **削峰填谷（buffering）**。

<Analogy title="🏣 生活比喻：郵局信箱 vs 社區廣播">

- **SQS＝公寓的信箱**：郵差（發送方）把信投進你的信箱就走，你（接收方）有空再自己下樓「領」出來。信會乖乖等著，不會因為你還沒領就消失。**一對一、用拉的**。
- **SNS＝社區廣播器**：管理員喊一次「包裹到囉」，**整棟樓所有住戶同時聽到**。訊息是「推」出去的，一次通知一大群。**一對多、用推的**。

</Analogy>

## 同步 vs 非同步：解耦的本質

| | 同步（緊耦合） | 非同步（解耦） |
| --- | --- | --- |
| 做法 | A 呼叫 B，站在原地等 B 做完 | A 把工作丟進佇列就走，不等 |
| B 掛掉時 | A 跟著失敗 | 訊息留在佇列，B 復原後照常處理 |
| 流量暴衝 | B 被沖垮，A 也卡死 | 佇列當緩衝，B 依能力慢慢消化 |

## SQS vs SNS：最常考的對照

| 項目 | SQS（佇列） | SNS（發布/訂閱） |
| --- | --- | --- |
| 模式 | 一對一，接收方**主動拉**（pull） | 一對多，**主動推**（push）給訂閱者 |
| 訊息留存 | 會留著等人領（最長 14 天） | 推完就沒了，沒訂閱者就收不到 |
| 典型用途 | 緩衝、削峰、背景工作佇列 | 即時通知、扇出、一事件多處理 |
| 接收方 | 通常是 EC2/Lambda 來拉 | Email、簡訊、Lambda、SQS… |

### 為什麼要解耦？不解耦會怎樣（白話）

你心裡可能會想：「A 直接呼叫 B 不是最簡單嗎？幹嘛中間還多塞一個佇列？」這是最該想清楚的「為什麼」。

**不解耦（A 直接呼叫 B）會遇到三個問題：**

1. **一個掛，全線掛**：B 當機或變慢，A 站在原地等、跟著卡死，使用者整頁轉圈圈。壞掉的範圍會「傳染」。
2. **流量一尖峰就崩**：瞬間湧進 10 倍請求，B 來不及處理就被沖垮，連帶把 A 也拖垮。
3. **擴充被綁死**：A 和 B 的處理速度被硬綁在一起，B 慢 A 就得等，沒辦法各自依自己的步調擴充。

**解耦（中間放佇列／主題）帶來的好處：**

- **故障隔離**：B 掛了，訊息乖乖留在佇列，A 照樣收單、照樣回覆使用者「已收到」，B 復原後再補做，一筆都不掉。
- **削峰填谷**：佇列把尖峰的量先存起來，B 依自己的能力穩穩消化，不會被瞬間流量沖垮。
- **各自擴充**：A 只管丟、B 只管拉，兩邊可以各自依負載調整機器數量，互不牽制。

**代價（解耦不是免費的）**：多了一個元件要管、訊息變成**非同步**（丟進去不會馬上有結果，要另外設計怎麼拿回處理結果），而且要面對「訊息可能重複、順序可能亂」這些分散式系統的新問題（下面的機制就是在處理這些）。所以**不是每件事都要解耦**——即時要回傳結果、且 B 很穩的簡單呼叫，直接同步呼叫反而單純。

:::info[🔑 一句話抓重點]
解耦的本質是把「**同步等待**」換成「**非同步緩衝**」：用「多管一個佇列、結果要晚一點拿」這個代價，換到「不互相拖垮、能扛尖峰、能各自擴充」。考題只要出現**削峰、怕後端被沖垮、要故障隔離**，心裡就要浮現 SQS。
:::

### SQS vs SNS 到底怎麼選？（最常混的決策）

兩者名字都很像、都在「中間傳訊息」，但解決的是**完全不同**的問題。選錯是考試與實務都常見的坑。用一個問題就能分：

> **「這則訊息，是只要有『一個』工人做掉就好，還是要『每個』關心的人都收到一份？」**

- 只要**有人做掉就好**（一份工作、一個消費者處理）→ **SQS**。訊息像待辦清單上的一張工單，被誰領走做完就消失。
- 要**每個訂閱者都收到一份**（同一件事，多個系統各自反應）→ **SNS**。訊息像廣播，一次推給所有訂閱者，彼此獨立。

| 你想要的效果 | 選誰 | 為什麼 |
| --- | --- | --- |
| 把工作排隊、慢慢消化、怕後端被沖垮 | **SQS** | 訊息會留存等人拉，天生就是緩衝 |
| 一個事件同時通知很多對象（Email＋Lambda＋…） | **SNS** | 一對多推播，一次扇出給所有訂閱者 |
| 下游暫時掛了也不能掉訊息 | **SQS**（或 SNS+SQS） | SQS 會保留訊息；SNS 單用會「推完就沒」 |
| 只是即時通知、沒收到也無所謂 | **SNS** | 推播最輕量，不需要保留 |

:::info[🔑 常被問：為什麼不乾脆都用 SNS 就好？]
因為 **SNS 不保留訊息**。它在「推送的那一刻」把訊息送給當下的訂閱者，沒訂閱者（或訂閱者剛好掛了）就**永遠收不到**，訊息直接消失。你要的「保證下游收得到、還能依自己速度慢慢處理」只有 SQS 做得到。這也是下面「SNS + SQS 扇出」存在的根本原因。
:::

### 標準 vs FIFO 的取捨（為什麼不一律用 FIFO？）

既然 FIFO「保證順序、保證不重複」聽起來比較高級，為什麼不每次都用 FIFO？因為**那個保證是有代價的**：

- **吞吐量差很多**：標準佇列幾乎沒有上限（每秒可達幾乎無限）；FIFO 有明確上限（未開批次預設每秒 300 則、開高吞吐批次後較高，但仍遠低於標準）。要爆量時 FIFO 會變瓶頸。
- **為了保證順序，處理會被「排隊」**：同一個 `MessageGroupId` 的訊息必須照順序一則一則處理完才換下一則，等於犧牲了部分平行度。
- **多數情境其實不需要嚴格順序**：很多工作（寄信、產縮圖、推播）誰先誰後根本沒差，硬套 FIFO 只是白白降速。

所以原則是：**預設先用標準佇列（便宜、快、好擴充），只有在「順序錯了會出事」或「同一筆重複處理會出事」時才動用 FIFO**。

| 想一想 | 答案 | 選擇 |
| --- | --- | --- |
| 訊息處理順序顛倒會造成錯誤嗎？ | 不會 → | **標準** |
| 同一筆被處理兩次會造成錯誤嗎？（且你不想自己做冪等） | 不會 / 我會自己做冪等 → | **標準** |
| 以上任一個「會」 | 例如金流、庫存扣減、訂單狀態機 → | **FIFO** |

:::tip[💡 考試重點：標準 vs FIFO 關鍵字]
- 題目強調「**高吞吐量 / 爆量 / 順序不重要**」→ **標準佇列**。
- 題目強調「**順序必須保持 / 絕不能重複處理 / 交易、金流、庫存**」→ **FIFO 佇列**。
- 注意：標準佇列是「**至少一次（at-least-once）**」送達，所以**本來就可能重複**；若你用標準佇列又怕重複，正解是「**自己把處理做成冪等**」，不一定要換 FIFO。
:::

### SQS 兩種佇列：標準 vs FIFO

| | 標準佇列（Standard） | FIFO 佇列 |
| --- | --- | --- |
| 順序 | **不保證**先進先出 | **嚴格**先進先出（First-In-First-Out） |
| 重複 | 可能極少數重複送達（at-least-once） | **精準一次**，不重複 |
| 吞吐量 | 幾乎無上限，超高 | 有上限（較低） |
| 何時用 | 順序不重要、要爆量 | 金流、訂單編號等**順序與不重複很重要**時 |

:::tip[💡 考試重點]
- 題目出現「**緩衝、削峰填谷、背景處理、怕流量暴衝沖垮後端**」→ 選 **SQS**。
- 題目出現「**一個事件要同時通知很多個對象／一對多推播／扇出（fan-out）**」→ 選 **SNS**。
- 題目要「**又要廣播、又要每個下游各自有緩衝不掉訊息**」→ 經典答案是 **SNS + 多個 SQS（扇出模式）**：SNS 推一次，每個 SQS 各收一份、各自慢慢處理。
- 題目強調「**訊息不能重複、順序不能亂**」（例如交易、庫存扣減）→ 選 **FIFO 佇列**。
:::

### 為什麼要 SNS + SQS 扇出？（這題超愛考）

這是 SAA 最經典的組合題之一，務必搞懂「為什麼要把兩個疊起來」。

**情境**：一筆「訂單成立」要同時觸發三件事——通知出貨、開發票、送去做數據分析。三個系統各做各的，而且**任何一個都不能漏掉訂單**。

**只用 SNS 行不行？** 不行。SNS 能一次推給三個訂閱者（這點它很強），但 SNS **不保留訊息**：如果「發票系統」當下剛好掛了，那筆推播對它來說就**永遠消失**了，之後補不回來。

**只用 SQS 行不行？** 也不行。SQS 是一對一，一則訊息被一個消費者領走就沒了，沒辦法「同一筆同時給三個系統各一份」。你得自己寫程式複製三份丟三個佇列，又醜又容易漏。

**所以答案是 SNS + SQS：**
- **SNS 負責「扇出」**：訂單事件推一次，自動複製給所有訂閱的佇列。
- **每個下游各掛一個 SQS**：出貨、發票、分析**各自有一個佇列**，各收一份、各自緩衝、各自依速度處理。某個系統掛了，訊息乖乖留在它自己的佇列裡等它復原，**一筆都不掉**。

| | 只有 SNS | 只有 SQS | **SNS + SQS（扇出）** |
| --- | --- | --- | --- |
| 一對多廣播 | ✅ | ❌（要自己複製） | ✅ |
| 下游掛了不掉訊息 | ❌（推完就沒） | ✅ | ✅ |
| 各下游獨立緩衝、各自步調 | ❌ | 單一佇列可以 | ✅ 每個下游一條 |

**何時用 / 何時別用：**
- **用它**：一個事件要觸發**多個獨立系統**，且每個系統都要**可靠收到、各自緩衝**（電商下單、IoT 事件分發、資料多處落地）。
- **別用它（殺雞用牛刀）**：只有一個消費者 → 直接用 SQS 就好，不必架 SNS；只是純通知、沒收到也無所謂 → 直接用 SNS 就好，不必掛 SQS。

:::info[🔑 一句話記住扇出]
**SNS 管「分發給誰」，SQS 管「可靠收下與緩衝」**——疊在一起就同時拿到「廣播」＋「不掉訊息＋各自步調」。考題看到「**一個事件、多個下游、每個都不能漏、各自處理**」，答案幾乎都是 SNS + 多個 SQS。
:::

## 兩個一定要懂的機制

- **可見逾時（<Term en="Visibility Timeout" desc="訊息被某個接收方拉走處理時，暫時對其他人「隱形」的一段時間，避免被重複領取。">Visibility Timeout</Term>）**：某台伺服器拉走一則訊息開始處理時，這則訊息會先「隱形」一段時間，避免別台也拉到同一則、重複處理。**設太短** → 第一台還沒做完，訊息又變可見被別人拉走 → **重複處理**；**設太長** → 處理失敗時要等很久才會重新出現。
- **死信佇列（<Term en="Dead-Letter Queue" desc="專門收那些一直處理失敗的訊息的獨立佇列，方便事後排查，避免壞訊息無限重試卡住整條佇列。">DLQ, Dead-Letter Queue</Term>）**：某則訊息重試很多次都失敗（例如格式壞掉），就把它丟到一個專用的「死信佇列」隔離起來，方便你事後查，也避免它無限重試卡住整條線。

## 實務應用：不只是考試

<Scenario title="真實情境：訂單尖峰削峰">

雙 11 下單量是平常的 20 倍。你把流程改成「網頁 → 丟進 SQS → 訂單伺服器自己拉」。尖峰時佇列暫存了 50 萬筆訂單，伺服器用穩定的速度慢慢消化，**全程沒有一筆訂單掉失，網頁也一路順暢**。這就是 SQS 當緩衝的威力。

</Scenario>

### 🛠️ 動手做：建一個 SQS 佇列並送收訊息

1. 登入 AWS 主控台 → 搜尋列輸入 `SQS` → 進入 Simple Queue Service
2. 點 **建立佇列**，類型選 **標準（Standard）**，命名為 `my-first-queue` → 建立
3. 進入佇列，右上角點 **傳送並接收訊息**
4. 在「訊息內容」輸入 `Hello Queue`，按 **傳送訊息**
5. 往下在「接收訊息」區按 **輪詢訊息（Poll for messages）**，就會看到剛剛那則訊息被「拉」出來

**預期結果**：按下輪詢後，「接收訊息」清單會跳出一列，點開可看到 `Body` 就是你剛打的 `Hello Queue`。這時佇列頂部的「可用訊息數」會從 1 變回 0（訊息被你領走了）。想親眼看到「可見逾時」的效果：領出訊息後**先別刪它**，過幾秒重新整理，它會從「處理中（In flight）」變回「可用」又能被領一次——這正是逾時到了訊息重新現身的畫面。

也可以用 CLI 體驗「丟」和「拉」是分開的兩個動作：

```bash
# 丟一則訊息進佇列（發送方）
$ aws sqs send-message \
    --queue-url https://sqs.ap-northeast-1.amazonaws.com/123456789012/my-first-queue \
    --message-body "Hello Queue"

# 接收方自己來「拉」訊息
$ aws sqs receive-message \
    --queue-url https://sqs.ap-northeast-1.amazonaws.com/123456789012/my-first-queue
```

**預期結果**：`send-message` 會回一段 JSON，含 `MessageId` 與 `MD5OfMessageBody`，代表訊息已進佇列。`receive-message` 則會回傳一則訊息，裡面有 `Body`（`Hello Queue`）和一個 `ReceiptHandle`（收據把手）——注意這就體現了「SQS 是用**拉**的」：不執行 `receive-message`，訊息只會乖乖躺在佇列裡，SQS **不會主動推給你**。若要真正把訊息從佇列移除，還得用那個 `ReceiptHandle` 呼叫 `aws sqs delete-message`；沒刪的話，可見逾時一到它就會再次可被領取。

<Cost>

SQS 與 SNS 都有**免費方案額度**（各每月 100 萬次請求），一般練習幾乎不會產生費用。超過後也是以「每百萬次請求」計價，非常便宜。真正要留意的是你**拉訊息的 EC2**可能計費，練習完記得關掉。

</Cost>

:::warning[🚑 常踩雷]
- **可見逾時設太短** → 第一台還在處理，訊息就重新可見被第二台拉走，變成**同一筆訂單處理兩次**。原則：Visibility Timeout 要 ≥ 你處理一則訊息最久需要的時間。
- **沒做冪等（Idempotency）** → 標準佇列本來就是「至少一次」送達，**重複是常態不是意外**。如果你的處理沒做成「同一則做兩次結果一樣」（例如用訂單 ID 去重、先查有沒有處理過），就會出現重複扣款、重複出貨。別指望佇列幫你保證不重複——那是**你程式**的責任。
- **沒設死信佇列（DLQ）** → 一則壞訊息無限重試，不斷佔用資源、吃掉吞吐量，還可能把整條佇列拖垮。正式環境務必設 DLQ。
- **以為 SQS 會主動推** → SQS 是**拉（pull）**模型，訊息不會自己跑到你的伺服器，一定要有人持續 `receive-message`／輪詢去拿。沒人拉，訊息就一直躺著（最長留 14 天後消失）。要「有事件自動觸發」請改用 Lambda 事件來源映射或 SNS 推播。
- **扇出漏設權限** → 做 SNS + SQS 扇出時，只「訂閱」還不夠：每個 SQS 佇列的**存取政策（Access Policy）**必須明確允許那個 SNS 主題來 `SendMessage`，否則 SNS 推出去會被佇列擋下、訊息**靜默消失**，而且常常沒有明顯報錯，超難查。用主控台訂閱時勾「啟用原始訊息傳遞／自動設定佇列政策」通常會幫你補；用 CLI/IaC 務必自己把佇列政策加對。
:::
