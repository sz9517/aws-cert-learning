# 運算選型：同一件事，到底該用 EC2、Lambda 還是容器？

> 本篇帶你搞懂三大運算選擇（EC2／Lambda／容器）各自的甜蜜點，以及 EC2 執行個體家族怎麼對應工作負載。這是 Domain 3 最常考、也最實用的「依效能需求與營運負擔選型」題。

<Vocab title="📌 先認識這篇會出現的名詞（完全沒碰過也能懂）">

- **運算（Compute）**：就是「**幫你跑程式的機器**」。你的程式要有地方執行，CPU、記憶體就是這台機器的馬力與桌面空間。
- **執行個體（Instance）**：你在 AWS 租來的一台**虛擬電腦**。開機就計費、關機就省錢，可大可小。
- **無伺服器（Serverless）**：不是真的沒有伺服器，而是「**伺服器由 AWS 幫你顧**」——你只管寫程式、丟上去跑，不用開機、不用修補、不用擴充。
- **容器（Container）**：把程式連同它需要的環境「**打包成一個標準貨櫃**」，搬到哪台機器上都跑得一模一樣。
- **營運負擔（Operational Overhead）**：為了讓系統活著，你要花的「**雜事成本**」——修補系統、擴充機器、換壞掉的硬碟。越少越輕鬆。

</Vocab>

## 為什麼需要選型？先講一個選錯會很痛的例子

假設你要做一個「上傳圖片就自動產生縮圖」的功能。流量很不固定：有時一小時幾張、有時突然湧進上千張。

如果你傻傻開一台 <Term en="Elastic Compute Cloud" desc="AWS 的虛擬伺服器，你租一整台機器，開著就計費。">EC2</Term> 整天開著等，沒人上傳時這台機器**空轉燒錢**；真的湧進上千張時，一台又**扛不住**。這種「短、零碎、事件觸發」的工作，用 <Term en="AWS Lambda" desc="無伺服器運算服務，有事件才執行你的程式碼，按實際執行時間計費，沒事就不收錢。">Lambda</Term> 幾乎完美——有圖片上傳才跑、沒事就不收錢、瞬間自動擴充到上千個。

反過來，如果你要跑一套「要裝特殊驅動、要完整 OS 控制、而且一跑就是好幾小時」的科學運算，硬塞進 Lambda 反而會卡在**執行時間上限**。選錯運算，不是多花錢就是做不到。**選型的核心，就是在「效能需求」與「營運負擔」之間找平衡點。**

## 一句話先懂這三個選擇

- **EC2**：你租**一整台虛擬電腦**，完全掌控、什麼都能裝，但開機、修補、擴充都要自己顧。
- **Lambda**：你只丟**一段程式碼**，有事件才跑、按毫秒計費，伺服器完全交給 AWS，但單次執行有時間上限。
- **容器（ECS／EKS／Fargate）**：把程式**打包成貨櫃**，比整台 EC2 輕、比 Lambda 更能長跑；用 <Term en="AWS Fargate" desc="無伺服器的容器執行引擎，你只管容器，底層伺服器完全由 AWS 管理。">Fargate</Term> 還能連底層伺服器都不用管。

<Analogy title="🏢 生活比喻：租房 vs 叫外送 vs 共享廚房">

- **EC2 = 租一整間房子**：鑰匙在你手上，想怎麼裝潢、裝什麼家電都行，但水電維修、打掃全得自己來（自己顧 OS、修補、擴充）。
- **Lambda = 叫外送**：肚子餓（有事件）才點，吃多少付多少，廚房長怎樣你完全不用管；但一份餐份量有上限（執行時間上限），不適合「吃一整天的流水席」。
- **容器 = 共享廚房租攤位**：你帶著自己的食材貨櫃（映像檔）進場就能開煮，比租整間房輕巧；用 Fargate 等於「連攤位的瓦斯爐、抽油煙機都有人維護」，你只負責煮。

</Analogy>

## EC2 執行個體家族：按工作負載挑「機型」

EC2 不是只有一種機器，而是分成好幾個「家族」，每個家族把某種資源**加強**。挑錯家族，就像用跑車去載貨、用貨車去飆速——錢花了效果卻差。

| 家族 | 代表系列 | 強在哪 | 最適合的工作負載 |
| --- | --- | --- | --- |
| **通用型** | T、M | CPU／記憶體均衡 | 一般網站、小型資料庫、開發測試 |
| **運算最佳化** | C | CPU 馬力最強 | 高效能運算 HPC、批次運算、遊戲伺服器、影像編碼 |
| **記憶體最佳化** | R、X | 記憶體超大 | 大型記憶體內資料庫（如 SAP HANA）、即時大數據分析、快取 |
| **儲存最佳化** | I、D | 本機硬碟快又大 | 高 IOPS 的 NoSQL、資料倉儲、巨量日誌處理 |
| **GPU／加速運算** | P、G | 有顯示卡（GPU） | 機器學習訓練、深度學習推論、繪圖渲染、影片轉檔 |

<Term en="Compute Optimized" desc="CPU 運算力最強的 EC2 家族，代表是 C 系列，適合吃 CPU 的工作。">C 系列</Term> 的重點是「**算得快**」；<Term en="Memory Optimized" desc="記憶體容量特別大的 EC2 家族，代表是 R、X 系列，適合吃記憶體的工作。">R／X 系列</Term> 的重點是「**裝得多**」（記憶體）；<Term en="Storage Optimized" desc="本機硬碟讀寫又快又大的 EC2 家族，代表是 I、D 系列。">I／D 系列</Term> 的重點是「**讀寫硬碟快**」；<Term en="Accelerated Computing" desc="配有 GPU 顯示卡的 EC2 家族，代表是 P、G 系列，適合 AI 與繪圖。">P／G 系列</Term> 的重點是「**有顯示卡幫忙算**」。

:::tip[💡 考試重點]
看到關鍵字直接對應運算選擇，幾乎是送分：
- 題目講 **「不想管伺服器」「按用量付費」「短任務、事件驅動」「幾秒內跑完就結束」** → **Lambda**
- 題目講 **「需要完整 OS 控制」「要裝特殊軟體／驅動」「長時間執行」「特殊授權」** → **EC2**
- 題目講 **「已經容器化」但「不想管底層節點／伺服器」** → **Fargate**（搭 ECS 或 EKS）
- 題目講 **「高效能運算 HPC」「節點間要超低延遲」** → **cluster placement group ＋ 加強網路（如 Elastic Network Adapter）**，機型選 **運算最佳化 C 系列**
- EC2 家族對應：**吃 CPU → C**、**吃記憶體 → R／X**、**吃硬碟 IO → I／D**、**要 GPU → P／G**
:::

## EC2 vs Lambda vs 容器：核心差異一次看

| 比較項 | EC2 | Lambda | 容器（ECS／EKS + Fargate） |
| --- | --- | --- | --- |
| 你要管什麼 | 整台機器（OS、修補、擴充） | 只管程式碼 | 只管容器（Fargate 連節點都不用管） |
| 計費方式 | 開機就計費（秒／時） | 按實際執行時間與記憶體 | 按容器用的 CPU／記憶體時間 |
| 執行時間 | 無上限，可一直跑 | 單次最長 15 分鐘 | 無上限，可長跑 |
| 啟動速度 | 開機要幾十秒～分鐘 | 有「冷啟動」延遲（首次略慢） | 容器啟動快，比開 EC2 快 |
| OS 控制 | 完整掌控 | 完全碰不到 | 容器層級可控 |
| 最適合 | 長跑、特殊軟體、要完整控制 | 零碎、事件驅動、流量忽高忽低 | 微服務、已容器化、要可攜性 |

這裡兩個最常考的限制要記牢：Lambda 有<Term en="Cold Start" desc="Lambda 很久沒被呼叫時，第一次啟動需要額外準備時間，造成首次回應稍慢。">冷啟動</Term>（閒置後第一次呼叫會稍慢）與**單次最長 15 分鐘**的執行時間上限；超過這個時間或需要長時間常駐的工作，就該往 EC2 或容器走。

## 放置群組 Placement Group：控制機器「擺在哪」

一般開 EC2，AWS 會幫你隨便擺。但有些工作對「機器之間的距離」很敏感，這時用 <Term en="Placement Group" desc="控制一群 EC2 在機房裡實體擺放位置的策略，可追求低延遲或高容錯。">放置群組</Term> 來指定擺法：

- **cluster（叢集）**：把一群 EC2 **塞進同一個機架、靠超近**，追求**節點間超低延遲、超高網路頻寬**——這正是 <Term en="High Performance Computing" desc="用大量機器協同運算的高效能運算，節點間需要頻繁快速通訊。">HPC 高效能運算</Term> 要的。
- **spread（分散）**：把機器**刻意分開擺**在不同硬體上，一台硬體壞了也不會全倒，追求**高容錯**。
- **partition（分區）**：介於兩者之間，分成多個區塊，常用於大型分散式系統（如 Hadoop、Kafka）。

:::tip[💡 考試重點：HPC 關鍵字組合]
看到 **「HPC」「節點間超低延遲」「緊密耦合的平行運算」** → 答案組合是 **cluster placement group ＋ 運算最佳化 C 系列 ＋ 加強網路**。看到 **「要避免單點故障、分散風險」** → **spread placement group**。
:::

## 實務應用：不只是考試

<Scenario title="真實情境：老闆說『帳單暴增，但機器大半時間在空轉』">

你查帳單發現：公司有三台 EC2 整天開著，其實只有「使用者上傳檔案時」才需要做轉檔，一天大概只忙 2 小時，其餘 22 小時都在空轉燒錢。同時另一組「每月一次、要跑 3 小時」的報表批次，卻因為塞進 Lambda 一直撞到 15 分鐘上限而失敗。

解法：**轉檔那種零碎事件改用 Lambda**（有檔案才跑、省掉 22 小時空轉）；**要跑 3 小時的批次改回 EC2 或容器**（不受 15 分鐘限制）。一來一回，帳單降、任務也不再失敗。下面帶你把轉檔搬上 Lambda 試試。

</Scenario>

### 🛠️ 動手做：用 Lambda 取代一台空轉的 EC2

1. AWS 主控台搜尋 `Lambda` → **建立函式** → 選 **從頭開始撰寫**，執行環境選 `Python` 或 `Node.js`。
2. 在程式碼區貼上你的轉檔／處理邏輯，按 **Deploy** 部署。
3. **新增觸發條件（Trigger）**：選 `S3`，指定一個儲存貯體，事件類型選 `PUT`（有檔案上傳就觸發）。
4. 調整 **一般組態**：記憶體給 `512 MB`、逾時（Timeout）設 `1 分鐘`（記住最多只能 15 分鐘）。
5. 丟一個檔案到該 S3 儲存貯體，到 **監控（Monitor）→ CloudWatch 日誌** 看函式自動被觸發執行。
6. 確認沒問題後，把原本那台空轉的 EC2 **關機或刪除**，省下 22 小時的費用。

```bash
# 查看 Lambda 函式的設定（記憶體、逾時、執行環境）
$ aws lambda get-function-configuration \
    --function-name 你的函式名稱
```

<Cost>

**Lambda 有每月免費額度**（100 萬次請求 ＋ 40 萬 GB-秒），零碎工作常常根本不用錢。**EC2** 只要開著就計費，空轉也照收，所以「用不到卻開著」是最常見的浪費。**Fargate** 按容器用的 vCPU／記憶體時間計費，比自己維運整群 EC2 省心。練習完記得把測試用的 EC2、Lambda 觸發的 S3 物件清一清。

</Cost>

:::warning[🚑 實務常見錯誤]
- **把長跑工作硬塞 Lambda**：撞到 15 分鐘上限就失敗，長跑請改用 EC2 或容器。
- **EC2 整天開著空轉**：零碎、不固定的工作該用 Lambda 或自動擴展，別讓機器乾等。
- **選錯執行個體家族**：記憶體內資料庫塞進一般通用型，記憶體不夠一直當；應選 R／X 記憶體最佳化。
- **HPC 忘了放置群組**：只開一堆高效能 EC2 卻沒用 cluster placement group，節點間延遲拉高，效能大打折扣。
- **以為 Fargate 完全不用設定**：你仍要定義容器要用多少 CPU／記憶體，給太少一樣會被 OOM 殺掉。
:::
