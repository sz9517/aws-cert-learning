# 實戰架構 1：三層式高可用網站

> 前面你一個一個認識了 EC2、ALB、Auto Scaling、RDS、CloudFront……這一篇要把它們「組成一個完整架構」。這正是 SAA 考試最核心的能力：不是背單一服務，而是知道**怎麼把它們拼起來解決一個真實需求**。

:::note[💬 這篇怎麼讀]
先看情境（我們要解決什麼），再看整體架構圖，然後逐層理解「為什麼選這個服務」。看到帶<Term desc="像這樣！滑鼠移到有虛線的名詞上（手機點一下）就會跳出白話解釋。">虛線底線的名詞</Term>可以把滑鼠移上去看白話解釋。
:::

## 需求情境

<Scenario title="真實情境：主管丟給你一個動態網站要上雲">

你是一家電商的工程師，主管說：「我們的購物網站要搬到 AWS。有三個硬要求——

1. **高可用**：半夜某個機房跳電，網站不能整個掛掉。
2. **能隨流量擴展**：平日人少、週年慶爆量，系統要自己撐住又不能平時一直燒錢。
3. **安全**：資料庫絕對不能直接暴露在公開網路上。」

這不是靠「某一個厲害的服務」就能解決的，而是要用一套**分層架構**把多個服務組起來。這就是業界最經典的範本——**三層式架構（Three-Tier Architecture）**。

</Scenario>

<Analogy title="🏢 比喻：把網站想成一棟有門禁的辦公大樓">

- **接待大廳與警衛（對外層）**：訪客只能走正門、先經過警衛，不能直接衝進辦公室。這就是 ALB——唯一對外的入口。
- **辦公室員工（應用層）**：真正做事的人在裡面的樓層，外人進不去，只接待大廳派下來的工作。這就是放在私有子網路的 EC2。
- **保險庫（資料層）**：公司最重要的資料鎖在最裡面的保險庫，只有特定員工能開，訪客連門都看不到。這就是私有子網路裡的 RDS。

一層一層往裡走，越裡面越安全——這就是「分層」的精神。

</Analogy>

## 架構總覽

整套架構由上到下是這樣運作的：使用者的請求先經過 DNS 找到網站，靜態資源（圖片、CSS、JS）走 CDN 就近送達，動態請求則進到跨多個可用區的負載平衡器，分給私有子網路裡會自動增減的伺服器，最後讀寫同樣在私有子網路、且有備援的資料庫。

```text
                      使用者（瀏覽器）
                            |
                            v
                  +---------------------+
                  |  Route 53 (DNS)     |  把網域解析到下面的資源
                  +---------------------+
                            |
             +--------------+--------------+
             |                             |
             v                             v
     +----------------+           +------------------+
     | CloudFront     |           | 動態請求          |
     | (CDN / 邊緣)    |           |                  |
     +----------------+           |                  |
             |  靜態資源                 |
             v                          |
         +-------+                      |
         |  S3   | 圖片/CSS/JS            |
         +-------+                      |
                                        v
  ===================== VPC =============================
  |                                                     |
  |   公有子網路 (Public Subnet, 跨多個 AZ)                 |
  |   +-----------------------------------------------+ |
  |   |   ALB (應用程式負載平衡器, 橫跨 AZ-a / AZ-b)       |<--- 唯一對外入口
  |   +-----------------------------------------------+ |
  |        |                           |                |
  |        v                           v                |
  |   私有子網路 AZ-a              私有子網路 AZ-b          |
  |   +--------------+           +--------------+        |
  |   | EC2 (Web/App)|           | EC2 (Web/App)|  <-- Auto Scaling 群組
  |   +--------------+           +--------------+        |
  |        |                           |                |
  |        +-------------+-------------+                |
  |                      v                              |
  |   資料層 (私有子網路, 跨 AZ)                            |
  |   +-----------------------------------------------+ |
  |   |  RDS 主資料庫 (AZ-a)  --同步複製-->  待命 (AZ-b)   | |
  |   |              RDS Multi-AZ                      | |
  |   +-----------------------------------------------+ |
  |                                                     |
  |   私有子網路 ----> NAT Gateway (公有子網路) ----> 網際網路 |
  |   （EC2 要更新套件、呼叫外部 API 時走這條，單向對外）        |
  =======================================================
```

:::info[🔑 看圖抓三個重點]
1. **對外的只有 CloudFront 和 ALB**：EC2 與 RDS 都躲在**私有子網路**，外面連不到。
2. **每一層都跨多個 AZ**：ALB、EC2（Auto Scaling）、RDS（Multi-AZ）都橫跨 AZ-a 與 AZ-b，任何一個可用區掛掉都還撐得住。
3. **私有子網路靠 NAT Gateway 單向對外**：伺服器要下載更新、呼叫外部 API 時出得去，但外面進不來。
:::

## 逐層選型理由

| 層 | 用什麼 | 為什麼 |
| --- | --- | --- |
| **DNS** | <Term en="Amazon Route 53" desc="AWS 的 DNS 服務，把網域解析到資源，並可做健康檢查與流量路由。">Route 53</Term> | 把網域指到 CloudFront／ALB；支援健康檢查，能在資源異常時自動切換 |
| **內容傳遞** | <Term en="Amazon CloudFront" desc="內容傳遞網路（CDN），把內容快取到全球邊緣節點就近送達。">CloudFront</Term> + <Term en="Simple Storage Service" desc="AWS 的雲端檔案倉庫，放圖片、影片、網站靜態檔等。">S3</Term> | 靜態資源（圖片、CSS、JS）放 S3、經 CDN 快取就近送達；全球快、又替後端省流量與負載 |
| **對外入口 / 負載平衡** | <Term en="Application Load Balancer" desc="第七層（HTTP/HTTPS）負載平衡器，把流量分散到多台後端。">ALB</Term> | 唯一對外的入口，橫跨多個 AZ；把流量平均分給後端、對後端做健康檢查、能終止 HTTPS |
| **Web／應用層** | <Term en="Elastic Compute Cloud" desc="AWS 上租來的雲端伺服器，程式跑在上面。">EC2</Term> + <Term en="Auto Scaling" desc="依流量自動增減伺服器數量的機制。">Auto Scaling</Term> | 跑應用程式本體，放在**私有子網路**；用 Auto Scaling 群組依流量自動增減執行個體數，兼顧撐量與省錢 |
| **資料層** | <Term en="Relational Database Service" desc="代管式關聯式資料庫，如 MySQL、PostgreSQL。">RDS</Term>（Multi-AZ） | 代管關聯式資料庫，放在**私有子網路**；開啟 Multi-AZ 後會在另一個 AZ 自動維持同步待命副本，主庫故障時自動切換 |
| **私有子網路對外** | <Term en="NAT Gateway" desc="讓私有子網路的資源可以單向連到網際網路的代管閘道。">NAT 閘道</Term> | 讓私有子網路的 EC2 能下載更新、呼叫外部 API；是**單向**出站，外部無法主動連進來 |
| **網路底座** | <Term en="Virtual Private Cloud" desc="你在 AWS 裡的私人虛擬網路。">VPC</Term> + 公有／私有子網路 | 所有資源的地基；用公有／私有子網路做分層隔離，是整個架構安全性的根本 |

## 為什麼這樣設計？（白話講清楚每個決策）

上面的表格告訴你「用什麼」，這一段告訴你**「為什麼非這樣不可」**。考試最愛考的就是這些「為什麼」，而不是服務名字本身。

### 為什麼要「分三層」，不乾脆一台機器全包？

最直覺的做法，是開一台 EC2 把網頁、程式邏輯、資料庫全裝在上面。能動，但問題很大：

- **牽一髮動全身**：改個前端要重開機，連帶把資料庫也弄斷線。三個職責綁死在一台機器上，沒辦法各自升級、各自擴充。
- **沒辦法只擴充該擴充的那層**：週年慶時真正吃力的是「應用層」的運算，但資料庫其實還好。全包在一台的話，你只能整台一起換大台，白白浪費。分層之後，應用層可以加到 10 台、資料庫維持 1 主 1 備，各自調整。
- **安全面全破**：資料庫跟對外網頁跑在同一台、同一個網路位置，等於把保險庫擺在接待大廳。分層的本質，是讓「越敏感的東西，離網際網路越遠」。

:::info[🔑 一句話抓重點]
分層不是為了好看，是為了**讓每一層可以各自擴充、各自升級、各自設定安全邊界**。這三件事，單機架構一件都做不到。
:::

### 為什麼 ALB + Auto Scaling 要「跨多個 AZ」？

<Term en="Availability Zone" desc="可用區；同一區域內實體隔離的機房，各自有獨立電力與網路。">可用區（AZ）</Term> 可以想成「同一個城市裡、但彼此實體隔開的不同機房」。跨 AZ 的理由有兩個，對應兩個不同的需求：

- **ALB 跨 AZ 是為了「容錯」**：如果 ALB 和所有 EC2 都只擺在 AZ-a，那 AZ-a 整個機房跳電，網站就整個消失。把 ALB 設定成橫跨 AZ-a / AZ-b，再讓 Auto Scaling 在兩個 AZ 各放幾台 EC2，就算一整個 AZ 掛掉，ALB 會把流量全導到還活著的那個 AZ，使用者幾乎無感。
- **Auto Scaling 是為了「彈性 + 自動補位」**：它做兩件事——流量高自動加機器、某台 EC2 當掉自動補一台新的。注意「加機器」和「補位」是一體兩面：Auto Scaling 群組永遠努力維持「健康執行個體數量 = 你設定的目標」。

:::tip[💡 為什麼是「ALB + ASG」這個組合，不是只用其中一個？]
**只有 ALB、沒有 ASG**：ALB 會把掛掉的機器踢掉，但不會「生」一台新的補回來——久了健康機器越來越少。**只有 ASG、沒有 ALB**：ASG 會維持機器數量，但流量沒有東西幫你平均分配、也沒有統一的健康檢查入口。兩個要合起來，才有「自動分流 + 自動補位 + 自動擴縮」的完整閉環。
:::

### 為什麼資料庫要開 Multi-AZ？

資料是整個系統**最不能掉、也最難重建**的東西。EC2 掛了 Auto Scaling 補一台就好（反正無狀態）；但資料庫掛了、資料又沒有即時備援，等於整間店關門。RDS Multi-AZ 的做法是：在**另一個 AZ** 維持一份**同步複製**的待命副本，主庫一出事就**自動切換（failover）**過去，過程不用人半夜爬起來手動救。

:::warning[🚑 最常見的混淆：Multi-AZ ≠ 唯讀副本]
**Multi-AZ 是為了「高可用」**：待命副本平時**不對外服務**，純粹待命，主庫掛了才頂上。**唯讀副本（Read Replica）是為了「分擔讀取流量」**：它會對外、可以被查詢，但主庫掛掉它**不會**自動變主庫。考題問「資料庫高可用」選 Multi-AZ；問「讀取太慢要分流」才選 Read Replica。兩個常被故意放在同一題裡混淆你。
:::

## 每個選擇的取捨與替代方案（為什麼不用 X）

考試常把「正確答案」和「看起來也行、但這題不對」的選項擺在一起。懂得「為什麼不用 X」，比背「要用 Y」更能拿分。

| 這裡的選擇 | 常見的替代方案 | 為什麼這題選前者、不選後者 |
| --- | --- | --- |
| **ALB（第七層）** | <Term en="Network Load Balancer" desc="第四層（TCP/UDP）負載平衡器，極高吞吐、超低延遲，但不看 HTTP 內容。">NLB</Term>（第四層） | 一般網站要看 HTTP 路徑／主機名稱做路由、要終止 HTTPS → 選 **ALB**。只有在「極高吞吐、超低延遲、要固定 IP、或非 HTTP 協定（如遊戲、IoT）」時才選 NLB。 |
| **EC2 + Auto Scaling** | 單純開固定幾台 EC2 | 固定台數要嘛尖峰不夠用、要嘛離峰浪費錢，而且掛了不會自動補。除非流量「完全可預測且恆定」，否則一律 **ASG**。 |
| **EC2 + ASG（本篇）** | <Term en="AWS Lambda" desc="無伺服器運算，有事件才跑、按用量計費，自動擴充、免管伺服器。">Lambda</Term>／Fargate（無伺服器） | 若是「傳統、長時間運行的 Web 應用、需要常駐」→ EC2 很合適。若能拆成「事件驅動、短任務」→ 無伺服器更省心（見下一篇架構）。本篇刻意用 EC2，是為了帶你看懂最經典的 VPC 分層。 |
| **RDS（關聯式）** | <Term en="DynamoDB" desc="AWS 的全代管 NoSQL 資料庫，毫秒延遲、幾乎無限擴充，但不是關聯式。">DynamoDB</Term>（NoSQL） | 購物網站有訂單、會員、商品的**關聯與交易（transaction）** → 選 **RDS**。若資料是「key-value、超大量、要極致水平擴充」才考慮 DynamoDB。 |
| **RDS Multi-AZ（高可用）** | RDS 唯讀副本 | 目標是「主庫掛了自動頂上」→ **Multi-AZ**。目標是「讀取分流」才用唯讀副本。兩者可**同時**使用，但解決的是不同問題。 |
| **NAT 閘道（私有子網路出站）** | 把 EC2 丟到公有子網路、給公開 IP | 給公開 IP 等於「為了讓它能出門，乾脆把大門敞開」——攻擊面大增。正解是**留在私有子網路，靠 NAT 單向出站**：出得去、進不來。 |
| **CloudFront + S3（靜態資源）** | 所有請求都打到 EC2 | 讓 EC2 吐圖片／CSS 又慢又貴又增加負載。靜態資源交給 **CDN + S3**，EC2 只處理真正的動態邏輯。 |

:::info[🧭 取捨題的通用解法]
看到「哪個方案最適合」的題目，先問自己三件事：**(1) 需求是高可用、彈性、還是省錢？(2) 這是有狀態還是無狀態？(3) 流量可預測嗎？** 把題幹的關鍵詞對到這三個軸，淘汰掉「解錯問題」的選項，答案通常就剩一個。
:::

## 三個 Well-Architected 面向怎麼體現

AWS 的[架構完善框架](https://aws.amazon.com/architecture/well-architected/)有多個支柱，這套架構一次就體現了最常考的三個。

### 1. 高可用（可靠性）

- **跨多個可用區部署**：ALB、EC2、RDS 都橫跨至少 2 個 AZ。單一 AZ 整個停電，服務照跑。
- **ALB + Auto Scaling 群組**：ALB 只把流量送給健康的執行個體；某台 EC2 掛了，Auto Scaling 會自動補一台新的上來。
- **RDS Multi-AZ**：資料庫在另一個 AZ 維持同步的待命副本，主庫故障時**自動切換**，不用人工介入。

### 2. 安全

- **分層的<Term en="Security Group" desc="套在資源上的虛擬防火牆，控制進出流量。">安全群組（Security Group）</Term>**：ALB 只開放外部的 443；EC2 只接受「來自 ALB 安全群組」的流量；RDS 只接受「來自 EC2 安全群組」的流量。一層只信任上一層。
- **Web／應用層在私有子網路**：EC2 沒有公開 IP，外部無法直接連到，大幅縮小攻擊面。
- **只有 ALB 對外**：整個系統對網際網路暴露的入口被收斂到一個，容易集中防護（例如前面再掛 WAF）。

### 3. 成本

- **Auto Scaling 離峰縮回**：週年慶自動加機器撐量，離峰自動縮回來，不必為尖峰流量「養一整年的機器」。
- **S3 + CloudFront 省傳輸**：靜態資源交給 CDN 快取、由 S3 供應，省下後端 EC2 的運算與對外傳輸費用，還跑得更快。

:::tip[💡 一句話串起來]
**高可用靠「跨 AZ + 自動補位」，安全靠「分層 + 把東西藏進私有子網路」，成本靠「用多少、長多少」。** 這三句能講清楚，你就抓到了這張架構圖的靈魂。
:::

## 常見考題角度

SAA 很愛針對這張經典架構出情境題。先看懂「問的其實是哪一層」，答案方向就很清楚。

| 題目這樣問 | 其實在考 | 答案方向 |
| --- | --- | --- |
| 「如何讓這網站**撐住單一 AZ 故障**？」 | 高可用 / 跨 AZ | 把 ALB、EC2（Auto Scaling）、RDS 都**部署到多個 AZ**；只開在單一 AZ 的選項一定是錯的 |
| 「**資料層**如何做到高可用？」 | RDS 備援 | 開啟 **RDS Multi-AZ**（同步待命副本、自動切換）；注意這是為了「高可用」，不是為了「分擔讀取」（那是唯讀副本 Read Replica） |
| 「尖峰流量會把網站**塞爆**，怎麼辦且不想平時燒錢？」 | 彈性 / 成本 | **ALB + Auto Scaling 群組**，依指標自動增減 EC2 |
| 「**資料庫不能暴露在公開網路**，怎麼配置？」 | 安全 / 網路 | RDS 放**私有子網路**，用安全群組只開放來自應用層的連線 |
| 「如何讓**全球使用者**載入更快、又減輕後端負擔？」 | 傳遞 / 成本 | 靜態資源用 **S3 + CloudFront（CDN）** 快取就近送達 |
| 「私有子網路裡的 EC2 要**下載更新**，又不想被外部連進來？」 | 網路 / 安全 | 走 **NAT 閘道**（單向出站） |

:::info[🧭 抓題訣竅]
看到「容忍單一機房故障」「highly available」→ 想**跨 AZ / Multi-AZ**；看到「尖峰塞爆」「省離峰成本」→ 想 **Auto Scaling**；看到「不能暴露在公開網路」→ 想**私有子網路 + 安全群組**。把關鍵詞對應到層，是情境題拿分的捷徑。
:::

:::warning[🚑 常踩雷]
這張架構圖畫對很容易，**真正扣分的都是這些「看起來有做高可用，其實留了一個死穴」的細節**：

- **只擺在單一 AZ（單點故障）**：ALB、EC2、RDS 任何一個只開在一個 AZ，整個「高可用」就破功了。最常見是「ALB 跨 AZ 了，但 Auto Scaling 群組只設定 AZ-a」——那個 AZ 一掛，ALB 後面一台健康機器都沒有。**三層都要跨至少 2 個 AZ**，缺一不可。
- **安全群組「層層放行」變成「層層敞開」**：分層安全的精神是「一層只信任上一層」。常見的雷是圖省事，把 EC2、RDS 的安全群組直接開 `0.0.0.0/0`（所有來源），或 RDS 直接開放整個 VPC。正解是**用安全群組「互相指定」**：EC2 只收「來源 = ALB 的安全群組」、RDS 只收「來源 = EC2 的安全群組」。指定安全群組 ID，而不是 IP 範圍。
- **把資料庫放到公有子網路**：這是最嚴重的雷。RDS 只要落在公有子網路、又給了公開存取，等於把保險庫搬到大街上，全世界都能嘗試連線爆破。**資料庫永遠放私有子網路、關閉公開存取**，只讓應用層的安全群組連得到。
- **Session 存在單機（有狀態 EC2）**：很多人把登入狀態、購物車存在某一台 EC2 的本機記憶體。結果 Auto Scaling 一縮機器、或 ALB 把你的下一個請求導到另一台，使用者就「莫名其妙被登出、購物車清空」。**應用層要做成無狀態**：session 外放到 <Term en="ElastiCache" desc="AWS 代管的記憶體快取服務（Redis／Memcached），常用來存 session、熱資料。">ElastiCache</Term>（如 Redis）或 DynamoDB，EC2 才能被安心地隨時增減、汰換。
:::
