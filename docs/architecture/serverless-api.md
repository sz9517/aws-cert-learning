# 實戰架構 2：最少營運負擔、最省成本的無伺服器 API

> 本篇帶你把一個常見需求——「流量忽高忽低、團隊很小、要最省心又最省錢的 REST API 後端」——一步步拆成一套<Term en="Serverless" desc="不是真的沒有伺服器，而是伺服器由 AWS 幫你顧,你只管寫程式、丟上去跑,按用量計費。">無伺服器</Term>架構。這也是 SAA 考試「最少營運負擔」「流量不可預測」這類情境題最愛的標準答案。

<Scenario title="真實情境：三人小團隊要上線一個 REST API 後端">

你和另外兩位同事要做一個待辦清單 App 的後端 API。使用者數量還沒起來，流量**忽高忽低**：平常一天只有零星幾十筆請求，但一被社群分享到就可能瞬間湧進上萬筆。團隊很小，**沒有專職維運人員**，老闆的要求很直接：「**營運負擔越少越好、成本越省越好**，別讓我們為了沒人用的時段付整台伺服器的錢。」

這種需求，傳統「開一台 <Term en="Elastic Compute Cloud" desc="AWS 上租來的一整台雲端伺服器,開著就計費。">EC2</Term> 整天開著等」幾乎必輸——離峰時空轉燒錢、尖峰時又可能被塞爆。下面這套無伺服器架構，正是為這種情境量身打造。

</Scenario>

## 架構總覽

先看整張圖，再逐塊拆解。使用者從瀏覽器進來，前端靜態檔由 CDN 就近送達,API 請求則走一條「驗證 → 入口 → 運算 → 資料」的無伺服器鏈路：

```text
                    ┌─────────────────────────────────────────┐
                    │                使用者 (瀏覽器)             │
                    └───────────────────┬─────────────────────┘
                                        │
                      ┌─────────────────┴──────────────────┐
                      │                                     │
              (靜態前端檔)                            (API 請求)
                      │                                     │
                      ▼                                     ▼
          ┌───────────────────┐                 ┌───────────────────┐
          │    CloudFront     │                 │  Amazon Cognito   │
          │   (CDN 邊緣節點)   │                 │    (使用者驗證)    │
          └─────────┬─────────┘                 └─────────┬─────────┘
                    │                            驗證通過,發權杖
                    ▼                                     ▼
          ┌───────────────────┐                 ┌───────────────────┐
          │        S3         │                 │   API Gateway     │
          │  (靜態網站檔案)    │                 │   (託管 API 入口)  │
          └───────────────────┘                 └─────────┬─────────┘
                                                          │
                                                          ▼
                                                ┌───────────────────┐
                                                │      Lambda       │
                                                │  (商業邏輯,按用量) │
                                                └─────────┬─────────┘
                                                          │
                                   ┌──────────────────────┼─────────────────┐
                                   ▼                                        ▼
                         ┌───────────────────┐                  ┌───────────────────┐
                         │     DynamoDB      │                  │   EventBridge     │
                         │ (無伺服器 NoSQL)   │                  │ (可選:觸發非同步)  │
                         └───────────────────┘                  └─────────┬─────────┘
                                                                          ▼
                                                                  ┌───────────────┐
                                                                  │ 另一個 Lambda  │
                                                                  │ (背景工作)     │
                                                                  └───────────────┘
```

一句話讀圖：**前端靜態檔**放 <Term en="Simple Storage Service" desc="AWS 的雲端檔案倉庫,可當靜態網站的來源。">S3</Term>、由 <Term en="Amazon CloudFront" desc="內容傳遞網路(CDN),把內容快取到全球邊緣節點就近送達。">CloudFront</Term> 全球加速；**API 請求**先經 <Term en="Amazon Cognito" desc="託管的使用者註冊/登入與身分驗證服務,發放存取權杖。">Cognito</Term> 驗證身分,再進 <Term en="Amazon API Gateway" desc="託管的 API 入口,負責收請求、驗權、限流並轉給後端。">API Gateway</Term> 這道「大門」,由它呼叫 <Term en="AWS Lambda" desc="無伺服器運算,事件觸發、按毫秒計費、自動擴縮。">Lambda</Term> 跑商業邏輯,資料讀寫 <Term en="Amazon DynamoDB" desc="無伺服器 NoSQL 資料庫,個位數毫秒延遲,支援隨需容量。">DynamoDB</Term>。需要「寄信、產報表」這類不必即時回應的工作,就丟給 <Term en="Amazon EventBridge" desc="事件匯流排,讓服務之間以事件非同步解耦觸發。">EventBridge</Term> 觸發另一個 Lambda 在背景處理。

:::info[🔑 整條鏈路沒有一台伺服器要你顧]
從入口、運算到資料庫,全部是**託管的無伺服器服務**——不用開機、不用修補 OS、不用設定自動擴縮群組。沒人用的時段,幾乎不產生費用;流量暴衝時,各服務自己擴。這正是「最少營運負擔」的精髓。
:::

## 每個元件的選型理由

| 元件 | 角色 | 為什麼在此最合適 |
| --- | --- | --- |
| **API Gateway** | 託管的 API 入口 | 幫你收請求、驗權杖、限流、轉送到後端,免自己架 Web 伺服器;天生搭 Lambda,完全無伺服器 |
| **Lambda** | 跑商業邏輯的運算 | 按實際執行時間計費、**閒置不收錢**、流量一來**自動擴縮**到數千併發,團隊只管寫程式 |
| **DynamoDB** | 無伺服器 NoSQL 資料庫 | 用**隨需(On-Demand)容量模式**,流量忽高忽低也免預先規劃容量;個位數毫秒延遲,免維運機器 |
| **Cognito** | 託管使用者驗證 | 註冊、登入、權杖發放一次搞定,免自己寫一套帳密系統;可直接把權杖交給 API Gateway 驗 |
| **S3 + CloudFront** | 前端靜態檔託管與全球加速 | S3 放 HTML/JS/CSS 近乎無限且極便宜,CloudFront 快取到邊緣節點讓全球使用者都載得快 |
| **EventBridge（可選）** | 非同步工作的觸發器 | 把「寄信、產報表」等不必即時的工作與主流程**解耦**,主 API 回應更快,背景自己慢慢跑 |

:::tip[💡 怎麼記這條鏈路]
背一條口訣:**「靜態走 S3＋CloudFront、動態走 Cognito → API Gateway → Lambda → DynamoDB、非同步交給 EventBridge」**。考試看到「無伺服器 REST API」的情境,十之八九就是這幾塊的組合。
:::

## 為什麼「無伺服器」在這個情境最合適

<Analogy title="🚰 比喻:裝冷熱水機 vs 叫桶裝水外送">

辦公室要供水,有兩種做法。一種是**自己裝一台冷熱水機**（EC2）：買機器、接水電、定期換濾心、清水垢——不管有沒有人喝,電費和保養費每月照付。另一種是**口渴才叫桶裝水外送**（無伺服器）：喝多少叫多少,沒喝就不花錢,機器維護、擴充通通是供應商的事。

小團隊、流量不固定的情境,顯然「喝多少付多少、什麼都不用顧」的外送模式更划算、更省心。這就是無伺服器在這裡勝出的理由。

</Analogy>

無伺服器在這個情境的三大甜蜜點:

- **零閒置成本**:沒人呼叫 API 的時段,Lambda 不執行就不收錢、DynamoDB 隨需模式也只按實際讀寫計費。離峰的 22 小時不再為空轉付費。
- **自動擴縮**:被社群瘋傳、瞬間湧進上萬筆請求時,Lambda 自動擴到數千個併發、DynamoDB 隨需容量自動吸收尖峰,團隊**不用半夜起來加機器**。
- **最少維運**:沒有作業系統要修補、沒有自動擴展群組要調、沒有資料庫要備份主機——三人團隊把力氣全放在產品功能上。

:::note[⚠️ 誠實說:無伺服器也有要注意的地方]
它不是萬靈丹,下面幾點務必心裡有數:

- **Lambda 冷啟動**:很久沒被呼叫後,第一次執行要額外幾百毫秒到數秒做準備,首次回應會稍慢(對延遲極敏感的場景要留意,可用「預置併發」緩解)。
- **單次最長 15 分鐘**:Lambda 一次執行有時間上限,**不適合長時間運算**(如跑 3 小時的批次)。
- **不適合長連線/常駐工作**:像即時影音轉碼、長時間 WebSocket 常駐、重度 CPU 的科學運算,硬塞進 Lambda 會卡上限或變貴,這類該回頭用 EC2 或容器。
:::

## 對比:如果改用 EC2 方案,差在哪?

同樣一個 API 後端,若改用傳統「EC2ELB＋Auto Scaling＋自建資料庫」方案,成本與營運負擔的差別很明顯——這正是 Domain 3(效能)與 Domain 4(成本)最愛考的取捨:

| 比較項 | 無伺服器方案 | EC2 傳統方案 |
| --- | --- | --- |
| 離峰成本 | 幾乎為零(沒請求就不收錢) | 機器開著就計費,空轉照付 |
| 應付尖峰 | 自動擴縮,免設定 | 要自己設 Auto Scaling 群組與策略,且擴機要暖機時間 |
| 營運負擔 | 幾乎為零(全託管) | 要修補 OS、管安全性更新、顧資料庫備份與高可用 |
| 擴充速度 | 瞬間(秒級) | 新 EC2 開機＋暖機要數十秒到數分鐘 |
| 適合誰 | 流量不固定、團隊小、求省心 | 流量穩定高、要完整控制、長時間常駐運算 |

結論:**流量忽高忽低＋團隊小＋求最省成本與維運**的這個情境,無伺服器幾乎穩贏;反過來,若流量長期穩定在高點、又需要完整 OS 控制或長時間運算,EC2/容器才會更合適。選型永遠是「看情境」,不是「哪個比較潮」。

## 常見考題角度

:::tip[💡 考試這樣問,你就這樣答]
把情境關鍵字對應到答案,幾乎是送分:

- **「要最少營運負擔的 REST API 後端選什麼?」** → **API Gateway ＋ Lambda**(全託管、免管伺服器、按用量)。看到「minimal operational overhead」「serverless」幾乎就是這組。
- **「流量不可預測的資料庫該選什麼容量模式?」** → **DynamoDB 隨需(On-Demand)容量模式**。流量**可預測且穩定**才選「佈建(Provisioned)容量」較省;**不可預測**就選隨需,免規劃、免因預估失準而限流或浪費。
- **「使用者驗證/登入不想自己寫一套?」** → **Amazon Cognito**(託管使用者池與權杖)。
- **「前端靜態網站要全球載得快又便宜?」** → **S3 存放 ＋ CloudFront 加速**。
- **「主 API 不想被寄信/產報表這類慢工作拖慢?」** → 用 **EventBridge(或 SQS)非同步解耦**,丟給背景的 Lambda 處理。
:::
