# 實戰架構 3：事件驅動解耦

> 本篇把 SQS、SNS、EventBridge 組起來，做出一個「削峰、容錯、各下游互不影響」的訂單系統。這是 SAA 最愛考的架構題型之一。

## 需求情境：訂單尖峰把下游打垮

<Scenario title="真實情境：下單一多，庫存、通知、分析全卡住">

你負責一個電商的訂單系統。平常相安無事，但一遇到大特賣，下單量暴增 20 倍。問題是：每次下單後，程式要**同步**依序去做三件事——扣庫存、寄出貨通知、寫一筆分析資料。只要其中一個下游（例如分析系統）變慢或掛掉，整條下單流程就跟著卡住，客人連「結帳」都按不下去。

你的目標很清楚：**削峰**（尖峰流量先緩衝，不要一次沖垮下游）、**容錯**（任一下游掛掉不能讓訂單掉失）、**各下游互不影響**（庫存慢不該拖累通知與分析）。

</Scenario>

<Analogy title="🍜 生活比喻：餐廳的出餐單">

想像一家忙碌的餐廳。客人點完餐，服務生不會站在廚房門口等菜做好才去招呼下一桌——他把**點單夾在出餐夾上**（丟進佇列）就立刻回去服務。廚房（下游）照自己的節奏一張張做。就算甜點師傅今天手慢，也不影響熱炒師傅出菜。這正是「事件驅動解耦」：下單這個**事件**被記錄下來，各個廚房各自認領、各做各的、互不拖累。

</Analogy>

## 架構總覽

完整版用 **SNS 扇出** 搭配 **多條 SQS 佇列**，讓一個訂單事件同時餵給多個互不影響的下游：

```text
                                  ┌─────────────┐   ┌──────────────┐
                            ┌───► │ SQS：庫存佇列 │──►│ 消費者 Lambda │──┐
                            │     └─────────────┘   └──────────────┘  │
 ┌──────────┐  ┌────────┐  │     ┌─────────────┐   ┌──────────────┐  │  ┌───────────┐
 │  下單 API │─►│ Lambda │─►│SNS ├───► │SQS：通知佇列 │──►│ 消費者 Lambda │──┼─►│ DynamoDB  │
 │(API GW)  │  │ 發布事件│  │主題│     └─────────────┘   └──────────────┘  │  │ (訂單/狀態)│
 └──────────┘  └────────┘  │(扇出)                                         │  └───────────┘
                            │     ┌─────────────┐   ┌──────────────┐  │
                            └───► │ SQS：分析佇列 │──►│  消費者 EC2   │──┘
                                  └─────────────┘   └──────┬───────┘
                                                           │ 處理一直失敗的訊息
                                                           ▼
                                                     ┌──────────┐
                                                     │ DLQ 死信  │
                                                     │  佇列     │
                                                     └──────────┘
```

流程說明：

1. 客人下單打到 **API Gateway**，由後面的 **Lambda** 把「訂單成立」當成一個**事件**發布到 **SNS 主題**。生產者到這裡就結束了，立刻回覆客人「已收到」。
2. SNS 主題**扇出（fan-out）**：把同一個事件複製一份給每條訂閱的 **SQS 佇列**（庫存、通知、分析各一條）。
3. 每條佇列後面有各自獨立的**消費者**（Lambda 或 EC2），依自己的速度**拉**訊息出來處理，最後寫入 **DynamoDB**。
4. 某則訊息一直處理失敗（例如格式壞掉的毒丸訊息），重試超過次數就被丟進 **DLQ 死信佇列**隔離，不會卡住整條線。

:::tip[💡 單純版：只用 SQS 削峰]
如果你只有「一個下游、只想削峰緩衝」，根本不需要 SNS。直接把流程做成「API Gateway → Lambda → **一條 SQS 佇列** → 消費者」就好。佇列替你把尖峰的洪水先存著，消費者用穩定的速度慢慢消化。**要廣播給多個下游才需要 SNS 扇出。**
:::

## 關鍵服務對比：SQS vs SNS vs EventBridge

這三個是解耦題的常客，考試最愛要你分辨「這情境該選哪一個」。

| 項目 | <Term en="Simple Queue Service" desc="AWS 的訊息佇列，像排隊的信箱，發送方丟訊息、接收方自己拉出來處理。">SQS</Term> | <Term en="Simple Notification Service" desc="AWS 的發布/訂閱通知服務，一則訊息同時推給所有訂閱者。">SNS</Term> | <Term en="Amazon EventBridge" desc="無伺服器事件匯流排，依規則把事件路由到不同目標，深度整合各 AWS 服務事件。">EventBridge</Term> |
| --- | --- | --- | --- |
| 模式 | 佇列，一對一 | 發布/訂閱，一對多 | 事件匯流排，依規則路由 |
| 傳遞方式 | 消費者**主動拉**（pull） | **主動推**（push）給訂閱者 | 依**規則**比對後推給目標 |
| 典型用途 | 緩衝、削峰、背景工作 | 扇出、一事件通知多個對象 | 依事件內容路由、整合 AWS 服務事件 |
| 訊息留存 | 會留著等人領（最長 14 天） | 推完就沒了（除非接 SQS） | 事件暫態，可搭配重試與 DLQ |
| 下游／目標 | EC2、Lambda 來拉 | SQS、Lambda、Email、簡訊… | Lambda、SQS、SNS、Step Functions、許多 AWS 服務 |

:::info[🔑 一句話抓重點]
- **SQS**：我要一個「緩衝信箱」，把工作先存著、讓後端慢慢消化（**削峰**）。
- **SNS**：我要「廣播」，一個事件同時通知很多個對象（**扇出**）。
- **EventBridge**：我要依「事件長什麼樣」決定送去哪，還要接 AWS 服務本身發出的事件（例如 EC2 狀態改變、S3 上傳）自動觸發流程。
:::

## 為什麼解耦能提升可靠與擴展

把生產者和消費者用佇列／主題隔開，好處是連鎖的：

- **生產者不被消費者拖累**：下單 API 把事件丟出去就回覆客人，不必站在原地等庫存、通知、分析做完。下游再慢，前台照樣秒回。
- **訊息持久、不遺失**：訊息乖乖留在 SQS 佇列裡（最長 14 天）。某個消費者掛掉重開後，照樣把累積的訊息補處理完，**一筆都不會掉**。
- **各下游獨立擴縮**：分析系統慢，就只替分析那條佇列的消費者加機器，完全不影響庫存與通知。每條線各自依自己佇列的長度去 Auto Scaling。
- **DLQ 隔離毒丸訊息**：一則永遠處理不了的壞訊息（<Term en="Poison Pill Message" desc="內容或格式有問題、不管重試幾次都會失敗的訊息，會不斷重試卡住佇列。">毒丸訊息</Term>）被自動丟到 **DLQ 死信佇列**隔離，不會無限重試、不會拖垮整條佇列，你也能事後單獨撈出來排查。

<Analogy title="🚰 比喻：佇列就像蓄水池">

尖峰流量像暴雨。沒有蓄水池，暴雨直接灌進下水道（下游）就會溢出來。佇列就是那個蓄水池：先把水存起來，再以下水道能承受的穩定流速放出去。雨下得再大，系統也只是「晚一點處理完」，而不是「整個崩潰」。

</Analogy>

## 常見考題角度

:::tip[💡 考試重點：看到關鍵字直接對應]
- 「一個事件要**同時廣播**給很多個下游／**一對多**／**扇出（fan-out）**」→ 選 **SNS**（通常再接多條 SQS，讓每個下游各有緩衝）。
- 「要**削峰、緩衝**、怕尖峰流量**沖垮後端**、背景工作」→ 選 **SQS**。
- 「又要廣播、又要每個下游各自**緩衝不掉訊息**」→ 經典答案 **SNS + 多條 SQS 扇出**。
- 「要依**事件內容**路由、或要接 **AWS 服務本身發出的事件**自動觸發（排程、S3 上傳、EC2 狀態變更）」→ 選 **EventBridge**。
- 「**失敗訊息**怎麼辦、怎麼避免壞訊息卡住整條佇列」→ 設定 **DLQ 死信佇列**。
:::

## 為什麼要這樣解耦？先講白話

很多人看到這張圖的第一個反應是：「不就扣庫存、寄通知、寫分析三件事嗎？直接在下單函式裡依序呼叫不就好了，幹嘛多搞 SNS、SQS、一堆佇列？」這問題問得很好，答案就是這篇的核心。

**同步直連**的意思是：下單函式親自、當場、依序把三個下游都呼叫完，等三個都回「OK」才回覆客人。它的致命傷有三個：

- **一慢全慢**：三個下游是「串」起來的，總回應時間等於三者相加。只要分析系統卡 3 秒，客人按「結帳」就得等 3 秒以上。
- **一死全死**：只要分析系統掛了拋錯，整個下單流程就失敗——結果連「扣庫存、寄通知」這兩個明明沒事的動作也一起回滾，訂單直接掉失。這叫**連鎖故障（cascading failure）**。
- **擴縮綁死**：三個下游被綁在同一支函式裡，沒辦法「只替慢的那個加機器」。

解耦就是把這條「串」剪開，中間塞一個緩衝層（佇列／主題）。下單函式只要把事件丟進去就閃人，剩下的三件事變成「各做各的、互不等待、互不牽連」。這就是為什麼要解耦：**把「同生共死」改成「各自獨立」。**

<Analogy title="🏢 生活比喻：同步直連像人工接力、解耦像投遞信箱">

同步直連像你親手把文件**依序**交給三個同事，而且要站在旁邊等每個人都簽完名才能走——其中一人請假（掛掉），你就卡死在那。解耦像你把文件投進三個**信箱**：丟完就走，每個同事上班後自己去信箱拿、自己的進度自己負責。一人請假，另外兩個照常處理，等他回來再補拿他那封就好。

</Analogy>

## 四個元件為什麼選它？優缺點與取捨

解耦題最常考的，不是「要不要解耦」，而是「這個情境該用哪個元件」。下面逐一講**為什麼是它、優點、缺點、什麼時候反而別用**。

### SQS：要的是「緩衝信箱」

- **為什麼是它**：你只想把尖峰的洪水先存著、讓後端用自己的節奏慢慢消化（削峰）。SQS 是**拉**模型，消費者有多少力氣就拉多少，天生就是流量的減壓閥。
- **優點**：訊息持久（最長 14 天）、保證至少送達一次、自帶重試與 DLQ、消費端可獨立 Auto Scaling。
- **缺點／限制**：標準佇列**不保證順序、可能重複投遞**（所以消費者一定要做冪等）；一條佇列基本上服務一組消費者，**不適合一對多廣播**。
- **什麼時候別用**：需要「一個事件同時通知很多個對象」時，硬用 SQS 要自己複製多份、很彆扭——那是 SNS 的場子。要求嚴格先進先出時才改用 **FIFO 佇列**（但吞吐量較低、要設 MessageGroupId）。

### SNS：要的是「廣播扇出」

- **為什麼是它**：一個事件要**同時**餵給多個互不相干的下游（庫存、通知、分析）。SNS 是**推**模型的發布／訂閱，一次發布、自動複製給每個訂閱者。
- **優點**：一對多扇出、訂閱者可隨時增減而生產者完全不用改、支援 Email／SMS／HTTP／Lambda／SQS 等多種訂閱端。
- **缺點／限制**：SNS **推完就忘**——若某個訂閱端當下掛掉沒收到，訊息就沒了（除非它後面接的是 SQS 來留存）。它本身**沒有佇列的緩衝與重放能力**。
- **什麼時候別用**：只有一個下游、只想削峰時，別硬加 SNS（純屬過度工程，見下）。要「廣播又要每個下游各自不掉訊息」時，正解是 **SNS 後面各接一條 SQS**，取兩者之長。

### EventBridge：要的是「依規則路由 + 接 AWS 原生事件」

- **為什麼是它**：你想依「事件長什麼樣」決定送去哪（規則比對），或要接 **AWS 服務本身發出的事件**（S3 上傳、EC2 狀態變更、排程 cron）自動觸發流程。這是 SNS／SQS 做不到的。
- **優點**：內容式規則路由、深度整合上百種 AWS 服務事件、支援排程、內建重試與 DLQ、還有 schema registry 幫你管事件格式。
- **缺點／限制**：吞吐與延遲不如 SNS／SQS「單純搬訊息」那麼極致；規則與事件格式一複雜，除錯會比單純佇列累。
- **什麼時候別用**：你只是要「A 丟訊息給 B」的單純點對點緩衝，用 SQS 就好，搬出 EventBridge 的規則引擎是殺雞用牛刀。

:::info[🔑 一句話記住怎麼選]
**要緩衝削峰 → SQS；要廣播扇出 → SNS；要依內容路由或接 AWS 原生事件 → EventBridge；三者失敗訊息都交給 DLQ。** 經典組合「SNS + 多條 SQS」= 既廣播又各自緩衝不掉訊息。
:::

## 解耦不是免費的：缺點與何時別過度解耦

解耦很香，但它**不是沒有代價**。考試與實務都會考「你是不是為了解耦而解耦」：

- **多了最終一致性**：事件丟出去就回覆客人「已收到」，但庫存其實還沒扣完。系統從「當場一致」變成「過一下才一致」（<Term en="Eventual Consistency" desc="資料不會在當下立刻一致，而是過一小段時間後各處才同步成最終狀態。">最終一致性</Term>）。要能接受「客人看到的狀態晚一點才更新」。
- **除錯與追蹤變難**：一個請求被拆成好幾段非同步處理，出事時要跨 SNS、SQS、多個消費者、DLQ 去追，沒有分散式追蹤（如 X-Ray）會很痛苦。
- **元件與成本變多**：多了主題、多條佇列、DLQ、對應的 IAM 權限與監控，維運面變大。
- **重複投遞是常態**：SQS 標準佇列至少送一次、SNS 也可能重送，消費者**一定要做冪等**，否則會重複扣庫存、重複寄通知。

:::tip[💡 何時「別」過度解耦]
- **只有一個下游、呼叫又快又穩**：直接同步呼叫就好，硬塞佇列只是增加延遲與維運負擔。
- **強一致、要當場給答案的流程**（如刷卡當下要回授權成功與否）：這種本來就需要同步等結果，非同步解耦反而壞事。
- **團隊還沒有監控／追蹤能力**：解耦後沒有可觀測性，出事會比同步直連更難查。
- 記住一句話：**解耦是用「複雜度」換「可靠與彈性」**。下游會慢、會掛、要獨立擴縮、要廣播給多人——值得換；反之就是過度工程。
:::

:::warning[🚑 常踩雷]
- **沒做冪等**：SQS 標準佇列「至少送一次」、SNS 也可能重送，同一則事件**本來就可能被處理多次**。消費者沒做<Term en="Idempotency" desc="同一事件被處理多次也不會造成重複的副作用，重試安全。">冪等</Term>（例如用訂單 ID 當去重鍵），結果重複扣庫存、重複寄出貨通知。**解耦系統「不重複」是幻想，程式要自己保證重試安全。**
- **可見性逾時（Visibility Timeout）設太短**：消費者從 SQS 拉到訊息後，這則訊息會被隱藏一段「可見性逾時」時間，期間不讓別人拿。若你的處理要 60 秒、逾時卻設 30 秒，訊息會在你還沒做完時**重新變可見被別人再拉一次**，造成重複處理。規則：**可見性逾時要設得比最長處理時間還長。**
- **SNS 扇出漏設權限**：SNS 要把訊息送進 SQS 佇列，得在**佇列的資源政策**上允許該 SNS 主題 `sqs:SendMessage`。只訂閱、沒開這條權限，訊息會**默默送不進去**（不會報錯在你臉上），下游一直收不到。EventBridge 送 SQS／Lambda 同理要開目標的資源政策。
- **過度工程化**：只有一個又快又穩的下游，卻硬搭 SNS + 多條 SQS + DLQ，徒增延遲、成本與除錯難度。**先問「下游會慢會掛嗎？要廣播嗎？要各自擴縮嗎？」都不是，就別解耦。**
:::

## 小結

事件驅動解耦的核心，就是「把一個動作變成一則事件，丟進中間層，讓各下游各自認領、各做各的」。記住這條黃金組合：**要廣播用 SNS、要緩衝用 SQS、要依規則路由用 EventBridge、失敗訊息交給 DLQ**。只要抓住這四個對應，解耦題幾乎都能秒選。
